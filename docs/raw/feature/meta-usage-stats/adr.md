# ADR: 메타 사용률·상대 SP 분포 데이터 수집

## 컨텍스트

- **PRD 요구:** 레귤레이션·매치 방식(Bo1/Bo3)·달력 월마다 상위권 래더 메타 통계 스냅샷을 만든다([PRD](./prd.md)). 스냅샷은 다음을 제공한다.
  - 사용률 순위
  - 대표 상대 세트(메가 포함)
  - 도구·특성·기술·SP 배분 분포와 자르기 전 전체 기준의 성격·SP 주변분포
  - 표본 지표와 동료

  상대 가정의 출처(래더·커스텀·SNS·구축 기사)를 구분하는 구조도 연다. 스냅샷 하나는 압축 전 1MB 이하이고, 같은 원천이면 바이트 단위로 같아야 한다.
- **현재 코드/데이터 제약:** 선행 단위([ADR](../champions-calc-data-core/adr.md))가 다음 계약을 이미 정했다. 이 ADR은 그 계약을 바꾸지 않고 그 위에 얹는다.
  - 게임 데이터 스냅샷: 레귤레이션 목록 + 레귤레이션별 정적 JSON, 저장소 커밋, 지연 로드(결정 6)
  - 식별자: Showdown id(결정 6)
  - 결정론: 고정 설정의 원천 시각, 키 정렬 직렬화, 동결(결정 6)
  - 세트 입력 계약: 원종 + 메가스톤 + `mega` 지정, 메가 해석은 "스톤 × 원종" 표, 메가는 폼 이름으로 판정(결정 2·5)
  - 라이선스·출처 고지 산출물(결정 7)

  지식 불변식도 지킨다: 결정론 스냅샷·동결, 메가는 폼 이름 판정, 메가 한국어명 규칙.
- **원천 제약:** Smogon chaos 원본은 Bo1-1760 15MB, Bo3-1760 5MB다. 브라우저에서 직접 받을 수 없다(CORS 없음). 전송은 압축되고 content-length가 없다. 원천을 실측한 결과는 다음과 같다([notes](./notes.md) "ADR 근거 실측").
  - 종 키는 표시 이름이고, 메가 폼은 별도 키다.
  - 메가 항목의 특성 분포는 메가 폼의 특성이다.
  - 같은 메가스톤을 쓰는 원종이 둘인 경우가 있다(냐오닉스 수컷·암컷).
  - 실데이터에도 폼 합산으로 생긴 특성 위반과 learnset 밖 기술이 소량 있다.
- **사용자 경험 제약:** 다음 단위 카드 화면이 탭 전환 전에 스냅샷 하나를 받아 상위 30마리의 대표 세트를 바로 계산해야 한다(50ms 이하, 네트워크 제외).
- **검증 제약:** 테스트는 네트워크 없이 돈다. 실제 2026-10 원천의 일부를 동결한 테스트 입력이 필요하다. 원본 전체(20MB)는 저장소에 넣지 않는다.

## 결정

### 결정 1. 원천: Smogon chaos JSON 1760 컷을 개발자 명령으로 받고, 해시·공개 시각을 별도 메타 설정에 고정한다

- 원천은 Smogon 월별 통계의 chaos JSON이다. 대상은 레귤레이션 대응 설정이 지정한 더블 포맷, 레이팅 컷은 1760 하나다. 다른 컷과 moveset·usage 텍스트는 쓰지 않는다.
- 수집은 개발자 명령(빌드 시)으로만 한다. 런타임은 원천에 접근하지 않는다.
- 메타 설정 파일을 게임 데이터 설정(`sources.config.json`)과 분리한다(`scripts/data/` 아래). 설정에는 두 가지를 둔다.
  - 레귤레이션 대응: 레귤레이션 id → 매치 방식별 원천 포맷 이름
  - 받은 원천 기록: (레귤레이션, 월, 매치 방식)마다 포맷·컷·URL, 압축 해제 본문의 sha256, 원천 공개 시각(기록할 때 응답의 Last-Modified 값)
- 기록과 생성을 분리한다.
  - **기록 모드:** 원천을 받아 해시와 공개 시각을 설정에 쓴다.
  - **생성 모드:** 커밋하지 않는 캐시(`.cache/` 아래)의 원천을 쓴다. 캐시가 없으면 받는다. 어느 쪽이든 기록된 해시와 다르면 실패한다. 해시가 기록되지 않은 원천으로는 생성하지 않는다.
  - 생성은 현재 시각과 네트워크 응답 헤더를 생성물에 쓰지 않는다. 공개 시각은 설정에 고정된 값만 옮긴다.
- **원천 형식 검증(실패 사유):** 실패하면 무엇이 달랐는지 출력한다.
  - 필수 필드 누락이나 타입 불일치
    - `info`: 포맷 이름, 컷, 컷 편차, 배틀 수
    - 종별 필드: 사용률, 비가중 출현 수, 특성·도구·SP 배분·기술·동료 분포
  - 형식 정보 불일치: 포맷 이름이 설정과 다름, 컷이 1760이 아님, 컷 편차가 0이 아님
  - 레귤레이션과 맞지 않음: 포맷이 그 레귤레이션의 대응 설정에 없음, 원천 월이 레귤레이션 기간과 겹치지 않음
  - SP 배분 키가 "성격:6개 정수" 형식이 아님
  - 종별 특성·도구·SP 배분 분포의 합이 서로 다름(상대 오차 1e-6 초과). 이 합이 점유율의 분모라서 형식 오류로 본다.
- 상성 정보(Checks and Counters), 테라 타입, 친밀도, Viability Ceiling은 읽지 않으므로 검증하지 않는다. 비어 있어도 정상이다.
- 값 단위 위반(미연결 이름, 규칙 위반 값)은 형식 오류가 아니다. 결정 4에서 리포트하고 제외한다.

### 결정 2. 저장 구조: 메타 인덱스 + (레귤레이션 × 월 × 매치 방식) 단일 JSON 파일, 지연 로드, 게임 데이터 스냅샷은 내용 해시로 참조

- **위치·키:** 게임 데이터 스냅샷 옆에 메타 디렉터리를 둔다(`src/data/meta/`).
  - 스냅샷 하나는 레귤레이션 디렉터리 아래의 파일 하나다. 파일 이름은 월과 매치 방식이다(예: `m-c/2026-10-bo3.json`).
  - 파일 안에 매니페스트와 종별 항목을 함께 둔다. 선택에 필요한 요약은 인덱스에 있으므로 매니페스트를 나눌 이유가 없다.
- **매니페스트 내용:**
  - 스키마 버전
  - (레귤레이션, 월, 매치 방식)
  - 원천: 포맷, 컷, URL, 해시, 공개 시각, 원천 배틀 수
  - 생성 파라미터: 결정 5의 기본값
  - 연결한 게임 데이터 스냅샷의 참조: 레귤레이션 id, 스키마 버전, `data.json` 바이트의 sha256

  생성 시각은 넣지 않는다.
- **메타 인덱스:** 레귤레이션마다 사용 가능한 (매치 방식, 월) 목록과 파일 위치를 담는다. 스냅샷마다 원천 URL과 설정에 기록한 원천 공개 시각도 담는다. 출처 고지의 입력이 된다.
  - 메타 생성 명령이 디스크에 있는 스냅샷 파일 전체에서 결정론적으로 다시 만든다. 그래서 지난 월 스냅샷도 인덱스에서 빠지지 않는다.
- **선택 규칙:** 데이터 접근층이 해석한다. 레귤레이션을 생략하면 게임 데이터 인덱스의 기본 레귤레이션을 쓴다.
  - 기본: 그 레귤레이션 Bo1의 가장 최근 월(사용자 결정: 0.5% 이상 종이 Bo1 79종으로 Bo3 68종보다 많아 카드 후보가 넓다)
  - Bo1이 없으면 Bo3의 가장 최근 월
  - 지정한 (매치 방식, 월)이 없으면 오류
- **지연 로드:** 기존 로더처럼 빌드 도구의 파일별 동적 import로 지정한 스냅샷 파일만 받고, 받은 결과를 캐시한다. 인덱스만 초기 번들에 들어간다.
- **보존·동결:**
  - 이미 있는 스냅샷 파일은 강제 옵션 없이 다시 만들지 않는다.
  - 게임 데이터 스냅샷이 다시 생성돼도 메타 스냅샷은 자동으로 다시 만들지 않는다.
  - 재현성 검증("같은 원천 → 같은 바이트")은 기록된 게임 데이터 해시가 현재 `data.json` 해시와 같은 메타 스냅샷에만 적용한다.
- **게임 데이터 해시 불일치 규칙:** M-C처럼 동결되지 않은 레귤레이션은 생성 명령을 다시 돌리거나 보정표만 더해도 `data.json` 해시가 바뀐다. 이때 이번 달 메타가 재현성 검증에서 조용히 빠지지 않게 다음을 강제한다.
  - **최신 월은 일치해야 한다:** 동결되지 않은 레귤레이션에서 매치 방식별 가장 최근 월의 메타 스냅샷은 기록 해시가 현재 `data.json` 해시와 같아야 한다. 다르면 테스트가 실패한다.
  - 운영 규칙: 게임 데이터 변경으로 해시가 바뀌면, 같은 변경 안에서 최신 월 메타 스냅샷을 강제 옵션으로 다시 만든다.
  - **지난 월은 남는다:** 지난 월 스냅샷과 동결된 레귤레이션의 스냅샷은 해시가 달라도 그대로 둔다. 테스트는 이것을 "다른 게임 데이터 기준"으로 구분해 보고만 한다.
  - **해시가 다른 스냅샷의 런타임 처리:**
    - 분포의 id가 현재 게임 데이터에 없으면 그 값은 원문 id를 이름 대신 표시하고 "이름 없음"으로 표시한다. 분포 값은 지우지 않는다.
    - 그런 스냅샷의 대표 세트가 코어 세트 검증에 실패하면 그 항목만 "가정 사용 불가"로 돌린다. 앱이 멈추지 않는다.
- **스키마 버전:** 데이터 접근층은 현재 스키마 버전의 메타 스냅샷만 읽고, 다른 버전은 명확한 오류로 거부한다.
  - 메타 생성 명령도 디스크에 다른 스키마 버전의 파일이 있으면 그 목록을 출력하고 실패한다. 강제 옵션으로 다시 만들어야 진행된다.
  - 게임 데이터 동결 스냅샷의 스키마 검사와 같은 방식이다. 여러 버전을 읽는 변환기는 두지 않는다.
- **리포트:** 게임 데이터 리포트 옆(`data/reports/meta/` 아래, 스냅샷별 디렉터리)에 둔다.
  - 연결·위반 리포트(결정 4)
  - 메가 점검
  - 보존 규칙 통계: 목표 도달·최대 개수 종 수, 누적 점유율
  - 파일 크기
- **출처 고지:** 라이선스 목록과 고지 파일은 지금처럼 게임 데이터 생성 명령만 쓴다.
  - **입력:** 기존 라이선스 모듈이 저장소(입력 루트)에 커밋된 메타 인덱스를 함께 읽는다. 그리고 Smogon 항목을 만든다.
    - 항목 내용: 원천 이름(Smogon University), 통계 링크, 인덱스에 있는 원천 월 목록, 각 월의 공개 시각
    - 출력 디렉터리가 아니라 입력 루트에서 읽는다. 그래서 빈 출력 디렉터리에서 생성해도 커밋본과 같은 바이트가 나온다.
    - 메타 설정의 원천 기록은 읽지 않는다. 기록만 하고 아직 생성하지 않은 월이 고지에 올라가지 않게 하기 위해서다.
  - **메타 생성 명령:** 고지 파일을 쓰지 않는다. 대신 "출처 고지 갱신 필요: 게임 데이터 생성 명령 실행"을 출력한다.
    - 고지를 갱신하지 않은 채 커밋하면, 기존 재현성 테스트("생성 결과 = 커밋된 고지 파일")가 실패한다. 그래서 누락이 드러난다.
  - 이렇게 하면 메타 생성 명령은 PokeAPI 라이선스 원문과 PokeAPI 캐시가 필요 없다. Smogon 캐시만으로 네트워크 없이 돈다.
- **직렬화:** 기존 키 정렬·들여쓰기 직렬화를 그대로 쓴다. 점유율은 반올림 규칙(결정 5)을 거친 값만 쓴다.

### 결정 3. 상대 세트 가정 계약: 출처를 단 가정 = 계산 코어 세트 + 근거 표시, 래더 외 출처는 별도 오버레이 파일

- **가정 하나의 계약:**
  - 대상 id: 레귤레이션 로스터의 종·폼 id(메가는 메가 폼 id). 메타 항목이 있는 종이면 메타 항목 id와 같다. 메타 항목이 없는 목록 밖 종도 같은 키로 가정을 받는다.
  - 계산 코어 세트: 선행 계약의 세트 입력 그대로다. 메가는 원종 + 메가스톤 + 메가 지정이다.
  - 출처
    - 종류: 래더 통계 / 사용자 커스텀 / SNS / 구축 기사
    - 설명: 래더는 원천·포맷·매치 방식·월·컷, 그 밖은 링크·작성자·작성일·메모
  - 의도 텍스트(선택)
  - 근거 표시
    - 최빈 조합: 래더 대표 세트. 실제 개체가 아니라 분포별 최빈값을 합친 것이다.
    - 관측 배분: 보존 spread 하나에 최빈 도구·특성·기술을 붙인 것
    - 출처 그대로: 커스텀·SNS·기사
  - 점유율(래더만)

  모든 출처의 가정이 같은 경로(세트 검증 → 계산 코어)로 들어간다.
- **메가 항목의 특성 기준(데이터 계약):** 메가 항목의 특성 분포는 원천 그대로 메가 폼의 특성이다. 대표 세트(가정)의 특성은 세트 입력 계약대로 원종의 특성이다. 두 값은 기준이 다르다는 것을 계약에 명시한다.
- **래더 대표 세트 구성:** 생성 단계에서 만들어 스냅샷에 담고, 생성 시 계산 코어의 세트 검증을 통과시킨다. 통과하지 못하면 생성이 실패한다. 동률은 id 순으로 정한다.
  - **일반 항목:** 다음을 합친다.
    - 점유율 1위 SP 배분(성격 포함)
    - 최다 도구. "도구 없음"이 최다면 도구를 비운다.
    - 최다 특성
    - 빈 칸을 뺀 최다 기술 4개

    값은 모두 결정 4의 위반 제외 후 남은 것에서 고른다.
  - **메가 항목:** 다음을 합친다.
    - 종: 게임 데이터 스냅샷의 폼 정보에서 얻은 원종
    - 도구: 그 폼의 메가스톤
    - 메가 지정
    - 원종 특성
    - SP 배분·기술: 메가 항목 분포의 최빈값

    원천의 메가 항목 특성 분포는 메가 폼의 특성이다(실측). 그래서 원종 특성은 이렇게 정하고 데이터에 근거를 표시한다.
    - 그 특성 분포의 최다 값이 원종에서도 쓸 수 있으면 그 값을 쓴다.
    - 아니면 원종의 첫 특성 슬롯을 쓴다.

    계산에서는 코어가 메가 폼 특성으로 바꾸므로 대미지·스피드 결과는 이 선택에 영향받지 않는다.
- **래더 외 출처:** 레귤레이션별 별도 오버레이 파일(가정 목록)로 둔다. 데이터 접근층이 (레귤레이션, 로스터 종·폼 id)로 래더 가정과 나란히 합친다. 래더 가정이 없는 종이면 오버레이 가정만 남는다.
  - 메타 스냅샷 파일·인덱스는 바뀌지 않는다.
  - 이 단위는 오버레이 파일을 만들지 않고, 테스트 입력 하나로 경로만 검증한다.
- **한국어 이름:** 메타 스냅샷에 넣지 않는다. 데이터 접근층이 같은 레귤레이션 게임 데이터 스냅샷의 이름을 붙인다. 메가는 메가 폼 종 이름이다(예: 메가리자몽Y). 한국어 매핑을 한 곳(게임 데이터)에만 둔다.
- **목록 밖 판별:** 로스터의 종(메가 폼 포함)을 조회하면 결과는 "래더 가정 있음(항목)"이나 "래더 가정 없음" 중 하나다. 없음은 오류가 아니라 명시 상태다.
  - "래더 가정 없음"인 종에는 통계 값도 자동 기본값도 만들지 않는다. 그 종의 가정은 커스텀 출처(오버레이)로만 들어온다(사용자 결정). 타겟 시 초기값 프리셋(해당 능력치 SP 32 / SP 32 + 성격 보정 / 무투자)은 데이터가 아니라 다음 단위 화면이 커스텀 가정을 채우는 방식으로 제공한다.

### 결정 4. 이름 연결: 원천 키를 Showdown id로 정규화해 게임 데이터 스냅샷에 조인하고, 메가는 폼 정보로 판정, 위반 값은 제외하고 종류별로 리포트

- **정규화:** 원천의 종·동료·도구·특성·기술 키를 선행 파이프라인과 같은 id 규칙(소문자 영숫자만 남김)으로 바꾼다. 그다음 같은 레귤레이션 게임 데이터 스냅샷에 조인한다. 표기가 다른 이름은 기존 별칭표(출처 메모 포함)에 더한다. 2026-10 실측에서는 별칭이 필요한 이름이 없었다.
- **메가:** 원천 키의 "-Mega" 문자열을 해석하지 않는다. 정규화 id로 찾은 종이 게임 데이터 스냅샷에서 메가 폼이면 메가 항목이다. 원종과 메가스톤은 그 종의 폼 정보와 메가 표에서 가져온다. 같은 스톤을 쓰는 원종이 둘이라도(냐오닉스) 폼 종이 원종을 정한다.
- **특수 키:**
  - 도구 "nothing"은 "도구 없음"이라는 정상 값이다.
  - 기술 빈 문자열은 빈 칸이다. 기술 분포에서 빼고, 개수를 리포트에 적는다.
- **위반 종류:** 판정 기준은 그 스냅샷의 레귤레이션 게임 데이터와 규칙값이다.
  - 미연결 이름: 종·동료·도구·특성·기술
  - 로스터 밖 종
  - 사용 불가 도구: 도구 로스터 밖
  - 사용 불가 특성: 그 폼의 특성 목록 밖. 메가 항목은 메가 폼 특성 목록으로 판정한다.
  - 배울 수 없는 기술: learnset 밖. 메가 항목은 원종 learnset으로 판정한다. 코어의 세트 기술 검증과 같은 기준이다.
  - 미지 성격
  - SP 규칙 위반 배분: 능력치당 상한 또는 합계 상한 초과
- **처리:** 위반 값은 스냅샷 데이터에서 뺀다.
  - 종 위반이면 그 항목 전체를 빼고, 순위는 제외 후에 매긴다. 순위는 사용률 내림차순이고, 동률이면 메타 항목 id 순이다.
  - 남은 값의 점유율은 다시 정규화하지 않는다. 분모는 원천의 종별 가중 출현 수 그대로이고, 그래서 원천 값과 소수 자리까지 대조할 수 있다.
  - 리포트에는 위반 종류별 개수, 종별 내역, 빠진 가중 점유율을 남긴다. 메가 점검(최다 도구가 그 메가스톤이 아닌 경우, 메가 폼 특성 밖 특성)도 같은 리포트에 남긴다.
  - 사용률 최소값 이상인 종이 미연결이면 경고 로그를 낸다. 생성은 계속한다.

### 결정 5. 기본값과 정의: 사용률 최소값 0.5%, SP 배분은 누적 80% 또는 최대 30개, 주변분포는 자르기 전 전체 기준

- **기본값:** 모두 메타 설정의 조정 가능한 값이고, 쓴 값은 매니페스트에 기록한다.
  - 사용률 최소값: 0.5%. 원천 사용률(0~1)이 0.005 미만이면 목록에서 뺀다. 2026-10 기준 Bo1 79종, Bo3 68종이다.
  - SP 배분 보존: 점유율 내림차순(동률은 키 순)으로 담는다. 누적 점유율이 80%에 도달하거나 30개에 이르면 멈춘다. 보존한 배분이 덮는 누적 점유율을 함께 담는다.
  - 도구 분포: 점유율 0.1% 이상
  - 기술 분포: 점유율 0.5% 이상
  - 특성 분포: 위반 제외 후 전부
  - 동료: 비율 상위 10
- **점유율 정의:** 종별 가중 출현 수(아래)를 분모로 한 비율이다. 저장할 때 소수 넷째 자리(0.01%p)로 반올림한다.
  - 기술 점유율은 "그 기술을 가진 개체 비율"이다.
  - 동료 비율은 원천 동료 가중값 ÷ 종 가중 출현 수다(원천 moveset 표기와 같다).
  - 사용률은 원천 값을 그대로 둔다. 원천 사용률은 가중 출현 수에 비례하지 않아서 다시 계산하지 않는다.
  - 누적 점유율 판정은 반올림 전 값으로 한다.
- **빠진 몫의 구분:** 도구·기술·SP 배분 분포마다 원천 대비 몫을 둘로 나눠 담는다. 그러면 "드문 값"과 "규칙 위반 값"을 구분할 수 있다.
  - 보존 누적 점유율: 남긴 값의 합. 기술은 개체당 4칸이라 최대 4다.
  - 위반 제외 점유율: 결정 4에서 뺀 값의 합

  꼬리 컷으로 빠진 몫은 원천 전체에서 두 값을 뺀 나머지다.
- **주변분포:** 위반 제외 후 남은 전체 SP 배분에서 집계한다. 보존 개수 상한과 무관하다.
  - 성격 분포
  - H·A·B·C·D·S 각각의 SP 값(0~32) 분포

  스피드 도구 점유율은 도구 분포에서 그대로 읽는다.
- **표본 지표:**
  - 종별 가중 출현 수 = 특성 분포 값의 합. 도구·SP 배분 분포의 합과 같고, 결정 1이 이 일치를 검증한다.
  - 종별 비가중 출현 수 = 원천 Raw count
  - 스냅샷 가중 배틀 수 추정 = 원천 전체 종의 가중 출현 수 합 ÷ 12(배틀당 2팀 × 6마리). 최소값으로 자르기 전 전체 종 기준이다. 2026-10 Bo1 약 6,358, Bo3 약 6,593이다.
  - 스냅샷 원천 배틀 수 = 원천 `number of battles`(컷 무관 월 전체, 비가중)
- **크기 근거:** 들여쓰기 직렬화 기준으로 Bo1 약 579KB, Bo3 약 390KB다(대표 세트·메타데이터 제외 실측). 그래서 1MB까지 40% 이상 여유가 있다.
  - 생성 명령은 스냅샷이 1MB를 넘으면 실패하고, 크기를 리포트에 남긴다.
  - 최소값을 0.25%로 낮추면 Bo1 756KB, 0.1%면 1,019KB로 기준을 넘는다.
- **로드 성능 측정 범위(PRD 50ms):** 같은 레귤레이션 게임 데이터 스냅샷은 이미 로드돼 있다고 보고, 그 로드는 측정에서 뺀다.
  - **시작:** 메타 스냅샷 본문을 받은 시점
  - **포함:** JSON 파싱, 순위 해석, 사용률 상위 30마리의 대표 가정 구성, 한국어 이름 조인, 그 30개 세트의 코어 세트 검증
  - **제외:** 네트워크와 대미지·스피드 계산

## 선택지

### 결정 1 (원천과 수집)

#### 선택지 1-A: Smogon chaos JSON 1760 컷 + 개발자 명령 수집 + 해시·공개 시각 고정 (채택)

- 장점:
  - 레귤레이션·매치 방식별 더블 통계다. SP 배분을 챔피언스 SP 단위의 전체 분포로 준다. 그래서 자르기 전 주변분포를 정확히 낼 수 있다.
  - 원본이 정적 파일이라 해시로 고정할 수 있다. 선행 단위의 "고정 설정 + 캐시 + 결정론" 방식을 그대로 따른다.
- 단점:
  - 원본이 커서 저장소에 넣을 수 없다. 재현하려면 캐시나 재다운로드가 필요하다.
  - 원천이 같은 URL의 파일을 다시 쓰면 해시 불일치로 실패한다(의도된 동작).
  - 이용 조건 공식 문구가 없다.

#### 선택지 1-B: Smogon moveset 텍스트를 파싱한다

- 장점: 파일이 작다(45~145KB).
- 단점:
  - SP 배분이 상위 일부만 실리고 비율이 반올림돼 있어 전체 기준 주변분포를 낼 수 없다.
  - 표 텍스트 형식이라 파싱이 취약하다. 표본 지표(`Avg. weight`)도 chaos 필드와 정의가 달라 대조하기 어렵다.

#### 선택지 1-C: 런타임에 브라우저에서 받는다

- 장점: 항상 최신이다.
- 단점: CORS가 없어 불가능하다. 원본 크기(최대 15MB)도 배포 기준과 맞지 않고, 재현성이 없다.

#### 선택지 1-D: 제3자 가공본(가공 통계 API, Pikalytics, 인게임 랭크 통계 사이트)

- 장점: 이미 요약돼 있어 처리가 적다.
- 단점:
  - 가공 기준(컷, 자르기)을 통제하지 못하고 버전을 고정할 수 없다.
  - Pikalytics 등은 PRD 비목표다. 인게임 랭크 통계 사이트는 약관이 경합 서비스의 데이터 취득을 금지한다.

#### 원천 설정 위치의 대안

- 별도 메타 설정 파일(채택): 메타 생성이 게임 데이터 생성과 독립적으로 돌고, 월마다 늘어나는 원천 기록이 게임 데이터 설정의 diff를 흐리지 않는다.
- 게임 데이터 설정에 합치기: 설정이 하나로 모인다. 다만 게임 데이터 생성의 검증 대상이 늘어난다. 메타 원천을 추가할 때마다 게임 데이터 설정이 바뀐다.

### 결정 2 (저장 구조)

#### 선택지 2-A: 메타 인덱스 + (레귤레이션 × 월 × 매치 방식) 단일 파일 + 지연 로드 + 게임 데이터 내용 해시 참조 (채택)

- 장점:
  - 앱이 지정한 스냅샷 하나만 받는다. 월이 늘어도 초기 로드가 커지지 않는다.
  - 지난 월 파일을 건드리지 않고 새 파일만 더해 보존한다.
  - 내용 해시로 "어느 게임 데이터 기준인가"를 정확히 판정한다. 같은 해시면 같은 원천이라는 정의가 명확하다.
- 단점:
  - 월마다 수백 KB 파일이 저장소에 쌓인다.
  - 게임 데이터 스냅샷을 다시 만들면 기존 메타 스냅샷의 기록 해시와 어긋날 수 있다.
    - 최신 월은 강제 재생성으로 맞춘다.
    - 지난 월은 리포트로 드러내는 것으로 감수한다.

#### 선택지 2-B: 레귤레이션 게임 데이터 스냅샷 디렉터리 안에 메타 파일을 함께 둔다

- 장점: 레귤레이션 단위로 모인다.
- 단점:
  - 게임 데이터 동결·재생성 규칙과 메타 보존 규칙이 같은 디렉터리에서 섞인다.
  - 게임 데이터 생성 명령이 메타 파일을 다룰지 경계가 흐려진다.

#### 선택지 2-C: 레귤레이션의 모든 월·매치 방식을 한 파일에 누적한다

- 장점: 파일 수가 적다.
- 단점: 1MB 기준을 곧 넘는다. 새 월을 더할 때마다 지난 데이터가 담긴 파일을 다시 써야 해서 보존·동결과 충돌한다.

#### 출처 고지 갱신 방식의 대안

- 게임 데이터 명령만 고지를 쓰고, 입력은 커밋된 메타 인덱스(채택):
  - 메타 명령이 PokeAPI 캐시에 의존하지 않는다.
  - 빈 출력 디렉터리 재현성 테스트와 양립한다.
  - 고지 누락은 기존 테스트가 잡는다.
  - 다만 메타 생성 뒤 게임 데이터 명령을 한 번 더 돌려야 한다.
- 메타 명령도 기존 라이선스 모듈을 불러 고지를 쓴다:
  - 한 번에 끝난다.
  - 다만 그 모듈이 PokeAPI 라이선스 원문을 요구한다. 그래서 메타 명령이 PokeAPI 캐시(없으면 네트워크)에 의존하게 되고, 결정 1의 "Smogon 캐시만으로 네트워크 없이" 전제가 깨진다.
- 메타 명령도 고지를 쓰되, PokeAPI 라이선스 원문을 저장소에 해시와 함께 고정한다:
  - 캐시 의존은 없어진다.
  - 다만 라이선스 원문의 진실원이 둘(캐시 원본, 저장소 사본)이 된다. 두 명령이 같은 파일을 쓰는 경로도 남는다.
- Smogon 고지를 별도 파일로 메타 명령이 쓴다:
  - 쓰는 주체가 명확히 나뉜다.
  - 다만 "기존 라이선스·출처 고지에 추가"(PRD)와 맞지 않고, 고지가 두 곳으로 갈라진다.
- 고지 입력을 메타 설정의 원천 기록으로 한다:
  - 인덱스 없이 읽을 수 있다.
  - 다만 기록만 하고 생성하지 않은 월이 고지에 올라간다.

#### 게임 데이터 해시 불일치 처리의 대안

- 최신 월은 일치를 테스트로 강제하고, 지난 월은 보고만 한다(채택): 이번 달 메타의 재현성 보장이 약해지지 않는다. 지난 월 보존 원칙도 지킨다.
- 불일치는 모두 보고만 한다: 보정표 하나만 추가해도 이번 달 메타가 재현성 검증에서 조용히 빠진다. PRD "재생성해도 차이 없음"이 약해진다.
- 게임 데이터 명령이 메타를 자동으로 다시 만든다: 두 생성 경로가 얽힌다. 그리고 지난 월까지 덮어써 보존과 충돌한다.

#### 게임 데이터 참조 방식의 대안

- `data.json` 내용 해시(채택): 선행 매니페스트에는 스냅샷 자체의 버전 번호가 없고, 원천 버전이 같아도 보정표가 바뀌면 내용이 달라진다. 내용 해시만 그 차이를 정확히 잡는다.
- 게임 데이터 매니페스트의 원천 식별자(패키지 버전·PokeAPI 커밋) 복사: 사람이 읽기 쉽다. 다만 보정표·추출 규칙 변경을 놓친다.

### 결정 3 (상대 세트 가정 계약)

#### 선택지 3-A: 가정 = 계산 코어 세트 + 출처·의도·근거 표시, 래더 대표 세트는 생성 시 계산·검증, 래더 외 출처는 오버레이 파일 (채택)

- 장점:
  - 어떤 출처든 같은 세트 계약으로 코어에 들어간다. 출처 종류가 늘어도 소비 코드가 바뀌지 않는다.
  - 래더 대표 세트는 생성 단계에서 검증하므로 잘못된 조합이 런타임에 처음 드러나지 않는다.
    - 계산할 때 코어가 세트를 검증하는 기존 동작은 그대로다.
    - 그 검증이 실패할 수 있는 경우는 오버레이 가정과, 게임 데이터 해시가 다른 스냅샷의 가정뿐이다. 이때만 "가정 사용 불가" 처리가 실제로 일어난다.
  - 오버레이로 더하므로 기존 스냅샷 파일이 바뀌지 않는다.
- 단점:
  - 대표 세트 구성 규칙이 바뀌면 메타 스냅샷을 다시 만들어야 한다.
  - 최빈 조합이 실제 개체와 다를 수 있다. 이 점은 근거 표시로 드러낸다.

#### 선택지 3-B: 스냅샷에는 분포만 두고 대표 세트는 런타임에 조립한다

- 장점: 구성 규칙을 바꿔도 스냅샷을 다시 만들 필요가 없다.
- 단점:
  - 잘못된 조합(예: 쓸 수 없는 특성)을 런타임에 처음 발견한다.
  - 다음 단위가 조립 로직까지 갖게 된다. 화면이 추가 가공 없이 써야 한다는 PRD 목표와 맞지 않는다.

#### 선택지 3-C: 출처별로 스키마를 따로 둔다(래더 전용 구조 + 커스텀 전용 구조)

- 장점: 출처마다 필요한 필드만 둔다.
- 단점: 소비 코드가 출처 종류마다 분기해야 해서, PRD 확장성 요구(소비 코드 불변)를 어긴다.

#### 메가 대표 세트 특성의 대안

- 원천 최다 특성이 원종에서 합법이면 그 값, 아니면 원종 첫 슬롯 + 근거 표시(채택): 원천 정보를 쓸 수 있는 경우 쓰고, 계산 결과에는 영향이 없다.
- 원천 최다 특성(메가 폼 특성)을 그대로 넣는다: 세트 계약상 원종 특성이어야 하므로 대부분 검증에 실패한다.
- 같은 스냅샷의 원종 항목(예: 메가가 아닌 리자몽)에서 최다 특성을 가져온다: 원종 항목이 없거나 표본이 매우 작은 경우가 많아 결과가 들쭉날쭉하다.

### 결정 4 (이름 연결)

#### 선택지 4-A: Showdown id 정규화 + 게임 데이터 조인 + 폼 정보로 메가 판정 + 위반 값 제외·리포트 (채택)

- 장점:
  - 실측상 별칭 없이 종·도구·특성·기술이 전부 연결됐다.
  - 메가 판정이 선행 불변식(폼 이름 판정)으로 만든 게임 데이터 폼 정보를 따른다.
  - 위반 값이 리포트로 드러나고 데이터에는 남지 않는다.
- 단점: 원천이 표기를 바꾸면 별칭표를 관리해야 한다.

#### 선택지 4-B: 원천 이름 문자열 규칙으로 메가·원종·스톤을 해석한다(예: "-Mega-Y" 접미 해석)

- 장점: 게임 데이터 없이도 해석된다.
- 단점:
  - 냐오닉스처럼 스톤이 같은 원종 둘을 구분하지 못한다. Z 메가 같은 새 접미가 나오면 규칙을 고쳐야 한다.
  - PRD와 선행 불변식이 금지한 방식이다.

#### 선택지 4-C: 위반 값이 하나라도 있으면 생성을 실패시킨다

- 장점: 데이터가 깨끗하다.
- 단점: 실데이터에 원천의 폼 합산 집계 같은 소량 위반이 매달 있다. 그래서 매달 생성이 막힌다.

#### 위반 제외 후 정규화의 대안

- 다시 정규화하지 않음(채택): 원천 값과 소수 자리까지 대조할 수 있고, 빠진 몫이 리포트에 그대로 남는다.
- 남은 값으로 다시 정규화: 합이 100%가 되어 보기 좋다. 다만 원천 대조가 어긋나고, 위반이 많은 종의 분포를 부풀린다.

### 결정 5 (기본값과 정의)

#### 선택지 5-A: 최소값 0.5% + 80%/30개 + 도구 0.1%·기술 0.5% (채택)

- 장점:
  - 200팀 중 1팀꼴 이상 쓰이는 종(Bo1 79, Bo3 68)을 담는다. 1% 경계 근처의 실전 종(파밀리쥐 0.98%, 파이어로 0.94% 등)이 빠지지 않는다.
  - 1MB 기준까지 40% 이상 여유가 있다.
  - 집중형 종은 80%에 도달하고(Bo1 54종), 분산형 종은 30개에서 멈춘다(Bo1 25종). 그래서 보존 배분이 카드 후보로 쓰기에 충분하다.
- 단점:
  - 0.5% 근처 종은 1760 컷 가중 때문에 표본 노이즈가 크다. 표시·경고 판단은 다음 단위에 넘긴다.
  - 분산형 종은 보존 배분이 원천의 일부만 덮는다(Bo1 최소 고릴타 43.9%, 어흥염 47.2%). 스피드 판단은 주변분포로 보완한다.

#### 선택지 5-B: 최소값 1%·2%

- 장점: 파일이 작고(80%×30 기준 Bo1 1% 462KB, 2% 398KB), 노이즈 큰 종이 줄어든다.
- 단점: 실전에서 만나는 종이 목록 밖으로 빠진다(Bo1 79 → 60 → 50). 크기 이점은 기준(1MB) 안에서 필요하지 않다.

#### 선택지 5-C: 최소값 0.1%·0.25% 또는 전체

- 장점: 목록 밖 종이 거의 없다.
- 단점: Bo1 0.1%는 1,019KB로 기준을 넘고, 전체는 1,586KB다. 0.25%(756KB)는 여유가 작다. 다음 달 종 수가 늘면 넘을 수 있다.

#### spread 보존 규칙의 대안

- 50%×10·50%×30: 채택안보다 Bo1 약 130~150KB, Bo3 약 90KB 작지만 1MB 기준 안에서는 필요 없는 절감이고 보존 배분이 적다. 다음 단위의 배분 후보가 부족하다.
- 70%×30: 80%×30보다 Bo1 기준 약 50KB 작다. 집중형 종의 꼬리 배분이 덜 남는다.
- 80%×10·80%×20: 분산형 종에서 금방 상한에 걸린다(Bo1 47종·34종). 상한이 사실상 규칙이 된다.

#### 직렬화의 대안

- 기존 들여쓰기 직렬화(채택): 선행 파이프라인과 같은 결정론 경로이고 diff 리뷰가 쉽다. 크기는 실측상 기준 안이다.
- 압축 직렬화: 크기가 절반 이하(Bo1 238KB)다. 다만 diff 리뷰가 어렵고 직렬화 경로가 둘이 된다. 크기 기준을 넘을 때의 대안으로 남긴다.

## 선택 근거

- **결정 1:** PRD는 자르기 전 전체 배분에서 낸 주변분포, 레귤레이션·매치 방식별 분리, 해시 고정 재현성을 요구한다. 이를 모두 만족하는 원천은 chaos JSON뿐이다. 브라우저 수집은 CORS로 불가능하므로 빌드 시 수집이 강제된다.
  - 기록·생성을 분리한 이유: 생성이 네트워크 응답 시각에 의존하지 않게 하고, 선행 단위의 "고정 설정값만 쓴다" 불변식을 메타 원천에도 적용하기 위해서다.
  - 형식 검증 범위: 실측한 원천 구조에서 계산에 쓰는 필드만 필수로 둔다. 쓰지 않는 필드(상성 정보 등)는 비어 있어도 통과시킨다. 원천의 형식 변화와 값 품질 문제를 구분하기 위해서다.
- **결정 2:** 스냅샷 단위가 (레귤레이션, 매치 방식, 월)이므로 파일도 그 단위로 나눴다. 그래야 보존(덮어쓰지 않음)과 지연 로드(하나만 받음)가 같은 경계에서 성립한다.
  - 메타를 게임 데이터 디렉터리와 분리한 이유: 두 데이터의 갱신 주기(월 vs 레귤레이션)와 동결 규칙이 다르기 때문이다.
  - 게임 데이터를 내용 해시로 참조한 이유: PRD의 "같은 원천 = 같은 통계 해시 + 같은 게임 데이터 버전"을 판정할 수 있는 유일한 값이기 때문이다.
  - 출처 고지는 게임 데이터 명령만 쓴다. 두 명령이 같은 파일을 서로 다르게 덮어쓰는 결정론 위반을 막기 위해서다.
    - 입력은 입력 루트의 커밋된 메타 인덱스다. 빈 출력 디렉터리 재현성 테스트와 양립하고, 생성된 월만 고지에 오른다.
    - 메타 명령이 고지를 쓰지 않으므로 PokeAPI 캐시가 필요 없다.
  - 최신 월 메타의 게임 데이터 해시 일치를 테스트로 강제하는 이유: 동결되지 않은 레귤레이션은 보정표 하나로도 해시가 바뀐다. 그때 이번 달 메타가 재현성 검증에서 조용히 빠지는 것을 막기 위해서다.
- **결정 3:** 다음 단위가 가정의 출처와 무관하게 같은 코드로 카드를 계산하려면 가정이 계산 코어 세트 계약을 그대로 품어야 한다. 출처 정보는 그 옆에 붙인다.
  - 대표 세트는 생성 시 검증해야 잘못된 조합을 생성 리포트 단계에서 잡는다. 런타임 성능 요구도 그래야 쉽게 맞춘다.
  - 메가 특성 규칙은 실측(메가 항목 특성 = 메가 폼 특성)에서 나왔다. 세트 계약(원종 특성)과 원천 정보 사이의 간극을 근거 표시로 메운다.
  - 한국어 이름을 게임 데이터에만 둔 이유: 메가 한국어명 불변식을 한 곳에서만 지키고, 스냅샷 크기를 줄이기 위해서다.
- **결정 4:** 정규화 조인만으로 2026-10 원천이 전부 연결됐다. 메가는 폼 정보로 판정해야 냐오닉스처럼 스톤을 공유하는 원종도 맞게 연결된다.
  - 위반 값을 제외하고 리포트하는 이유: 실데이터의 소량 위반(특성 3건, 기술 3건)이 생성을 막지 않게 하면서도, 대표 세트와 분포에 위반 값이 섞이지 않게 하기 위해서다.
  - 다시 정규화하지 않는 이유: PRD 수용 기준이 원천 값과의 직접 대조를 요구하기 때문이다.
- **결정 5:** 크기를 좌우하는 것은 종 수와 도구·기술 꼬리였고, spread 규칙의 영향은 작았다(Bo1 +149KB 범위). 그래서 종 수(최소값)는 실전 종을 놓치지 않는 선에서, spread 규칙은 넉넉하게 정했다.
  - 1MB 기준 안에서 다음 달 변동을 흡수할 여유를 남겼다.
  - 표본 지표는 원천 필드의 실측 정합(세 분포 합 일치, 배틀당 12마리)에서 정의했다. moveset 텍스트의 평균 가중치는 정의가 다르므로 쓰지 않는다.

## 결과

### 긍정적 영향

- 다음 단위가 스냅샷 하나를 받아 대표 세트를 그대로 코어에 넣을 수 있다. 출처 종류가 늘어도 같은 코드로 카드를 계산한다.
- 월별 메타 스냅샷이 원천 해시·공개 시각·게임 데이터 해시와 함께 보존된다. 어느 달 무엇을 기준으로 만든 가정인지 추적된다.
- 위반·미연결·메가 점검 결과가 리포트로 드러난다. 원천 표기가 바뀌거나 레귤레이션이 전환될 때 이상을 빨리 찾는다.
- 새 레귤레이션(M-D)은 대응 설정과 원천 기록만 더하면 생성된다.
- 성격·SP 주변분포가 전체 기준이라, 분산형 종의 스피드 분포도 보존 개수와 무관하게 정확하다.

### 부정적 영향 / 트레이드오프

- 원천 원본을 커밋하지 않으므로, 캐시가 없는 환경에서 재현하려면 원천을 다시 받아야 한다. 원천이 같은 URL의 파일을 바꾸면 그 달은 재현할 수 없다(해시 불일치로 드러남).
- 게임 데이터 스냅샷을 다시 만들면 기존 메타 스냅샷의 기록 해시와 어긋날 수 있다.
  - 최신 월은 같은 변경 안에서 강제 재생성해야 한다(테스트가 강제). 그래서 게임 데이터 보정 작업에 메타 재생성 절차가 따라붙는다.
  - 지난 월은 재현성 검증 대상에서 빠지고, 런타임 항목 단위 검증에 의존한다. 이름이 없는 id는 원문 id로 표시된다.
- 게임 데이터 생성 명령이 메타 인덱스를 읽게 된다. 그래서 고지 산출물(`licenses.json`, `THIRD_PARTY_NOTICES.md`)이 메타 생성 결과에 따라 바뀐다.
  - 메타 스냅샷을 더한 뒤에는 게임 데이터 명령을 다시 돌려야 고지가 맞는다.
  - 이 단계를 빠뜨리면 기존 재현성 테스트가 실패한다.
- 메타 스냅샷 스키마를 바꾸면 지난 월 파일도 모두 강제 재생성해야 한다. 그 원천이 캐시나 재다운로드로 확보되지 않으면 그 달은 버려야 한다.
- 대표 세트 구성 규칙이나 기본값을 바꾸면 메타 스냅샷을 강제 옵션으로 다시 만들어야 한다.
- 메가 대표 세트의 원종 특성은 대부분 가정(첫 슬롯)이다. 계산 결과에는 영향이 없지만, 원종 특성에 의존하는 다른 판단(등장 시 특성 등)에는 쓸 수 없다.
- 최소값 0.5% 근처 종은 1760 컷 가중 때문에 표본이 작고 노이즈가 크다.
- Smogon 통계 이용 조건은 공식 문구가 없어 관례적 출처 표기에 의존한다.
- 월마다 Bo1·Bo3 합쳐 약 1MB가 저장소에 쌓인다.

## 검증

- [ ] PRD 수용 기준 중 자동화할 수 있는 항목은 네트워크 없는 자동 테스트로 통과한다. 입력은 2026-10 M-C 원천 일부를 동결한 테스트 입력과 합성 원천이다. 아래는 이 ADR의 결정이 의도대로 동작하는지 따로 확인하는 항목이다.
- [ ] 결정 1:
  - 캐시가 있으면 네트워크 없이 생성된다.
  - 캐시 원천을 1바이트 바꾸면 해시 불일치로 실패한다.
  - 해시 미기록 원천으로는 생성되지 않는다.
  - 필수 필드 누락, 컷 불일치, 포맷 불일치, 기간 밖 월, 분포 합 불일치는 각각 원인을 출력하고 실패한다.
  - 상성 정보가 빈 원천은 정상 생성된다.
- [ ] 결정 2:
  - 같은 원천과 같은 게임 데이터 해시로 두 번 생성하면 바이트가 같다.
  - 이미 있는 스냅샷은 강제 옵션 없이 다시 만들어지지 않는다.
  - 인덱스는 디스크의 모든 스냅샷을 담는다.
  - 기본 선택은 Bo1 최근 월이고, Bo1이 없는 테스트 레귤레이션에서는 Bo3 최근 월이다.
  - 지정한 스냅샷 파일 하나만 로드된다.
  - 매니페스트의 게임 데이터 해시가 `data.json` 바이트 해시와 같다.
  - 게임 데이터 생성을 빈 출력 디렉터리에서 돌려도 고지 파일이 커밋본과 바이트 단위로 같다(커밋된 메타 인덱스 기준).
  - 메타 생성 명령은 PokeAPI 캐시 없이 네트워크 없이 성공하고, 고지 파일을 쓰지 않는다.
  - 메타 설정에 기록만 한 월은 고지에 나오지 않는다.
  - 동결되지 않은 레귤레이션에서 최신 월 메타의 게임 데이터 해시가 현재 `data.json`과 다르면 테스트가 실패한다. 지난 월이 다르면 보고만 한다.
  - 해시가 다른 합성 스냅샷에서 없는 id는 원문 id로 표시된다. 검증에 실패한 대표 세트는 "가정 사용 불가"가 되고 나머지 항목은 정상이다.
  - 다른 스키마 버전의 메타 파일은 로드가 거부되고, 생성 명령이 실패한다.
- [ ] 결정 3:
  - 상위 30마리 대표 세트가 코어 세트 검증을 통과한다.
  - 메가 대표 세트가 코어에서 메가 폼으로 해석된다(메가리자몽Y, 메가한카리아스Z, 메가냐오닉스 수컷·암컷).
  - 커스텀 출처 가정(의도 텍스트 포함) 테스트 입력이 같은 경로로 계산 결과를 낸다. 이때 메타 스냅샷 파일은 바뀌지 않는다.
  - 최소값 미만 종과 원천에 없는 로스터 종을 각각 조회하면 "래더 가정 없음"이 구분되고, 래더 출처 가정·분포·사용률·자동 기본 세트가 없다(오버레이가 없으면 가정 0개).
  - 최소값 미만 종에 커스텀 가정 하나를 오버레이로 주면 조회 결과가 "래더 가정 없음 + 커스텀 가정 1개"이고, 그 가정이 계산 코어에서 결과를 낸다.
  - 한국어 이름이 게임 데이터 매핑과 같다.
- [ ] 결정 4:
  - 합성 원천에 섞은 위반 값(로스터 밖 종, 사용 불가 도구·특성, learnset 밖 기술, 미연결 이름, SP 위반 배분)이 스냅샷에서 빠진다.
  - 리포트에 종류별 개수와 빠진 점유율이 남는다.
  - 남은 값의 점유율이 원천 값 ÷ 원천 가중 출현 수와 같다.
- [ ] 결정 5:
  - 보존 배분마다 "누적 ≥ 80%" 또는 "개수 = 30"이 성립한다.
  - 주변분포가 원천 전체 배분에서 직접 집계한 값과 같다(포푸니크 S=32 46.65%, 고집 54.44%).
  - 상위 5마리 표본 지표가 정의식대로 나온다.
  - 실제 M-C 2026-10 Bo1·Bo3 스냅샷이 각각 1MB 이하이고, 크기가 리포트에 기록된다.
  - 결정 5의 측정 범위(파싱·순위·대표 가정 구성·한국어 조인·코어 세트 검증, 게임 데이터 로드 제외)에서 중앙값이 50ms 이하다(측정 환경 기록).
  - 도구·기술·SP 배분마다 보존 누적 점유율과 위반 제외 점유율이 따로 나온다.
