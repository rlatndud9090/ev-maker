# ADR: 챔피언스 계산 코어(SP 어댑터·스피드 엔진)와 게임 데이터·한국어 매핑

> 작성 고도: ADR은 "어떤 구조를 왜 골랐나"의 근거 저널이다. 코드 스니펫·전체 설계문서를 본문에
> 넣지 않는다(과대 ADR) — 상세 구현은 코드·별도 설계문서로 내린다. 사람은 중립 역할어로만
> 지칭하고 개인 호칭·별명은 넣지 않는다. 참고: `harness/templates/examples/README.md`.

## 컨텍스트

- **PRD 요구:** 레귤레이션을 지정하면 다음을 계산하는 코어가 필요하다.
  - 실능치
  - 1타 확률과 그 구간
  - 스피드 비교와 추월 역산
  - SP 0~32 스윕

  레귤레이션별 게임 데이터 스냅샷(M-C, M-B), 전 항목 한국어 명칭, 개발용 확인 페이지도 만든다.
  브라우저 안에서 외부 호출 없이 동작하고 정적 파일로 배포할 수 있어야 한다([PRD](./prd.md)).
- **현재 코드/데이터 제약:** 저장소에 코드가 없다(첫 단위).
  - 계산 도구 `@smogon/calc` 0.12.0이 챔피언스(gen 0)를 지원하지만 실측에서 결함이 확인됐다([notes](./notes.md) "조사 결과", "ADR 근거 실측").
    - SP를 검증하지 않는다.
    - 사용 불가 도구와 존재하지 않는 특성명을 조용히 무시한다.
    - 메가 폼 8쌍을 잘못 해석한다.
    - 종마다 특성을 1개만 가진다. learnset이 없다.
    - 챔피언스 기술 11개의 타입이 비어 있고 변화기로 잡혀 대미지가 0으로 나온다.
    - 회복 도구가 있으면 몇 타 판정이 비어서 나온다.
    - 스피드 함수가 비공개이고 999 상한 버그가 있다.
  - 게임 데이터 원천 패키지 `@pkmn/mods`는 레귤레이션 전환을 늦게 반영할 수 있다.
    M-C 전환 때 약 7주 늦었다(평시 갱신은 Showdown과 1일 차이). 계산 도구 npm도 M-C 때 9일, M-B 때 약 3개월 늦었다.
  - PokeAPI 한국어는 기술·도구·성격·기본 종에서 결손이 없다.
    메가는 82개 중 40개, 특성은 3개, 일부 폼은 한국어가 비어 있다.
- **사용자 경험 제약:** 사용자는 한국어로 보고, 더블 기준으로 "1타에 쓰러뜨리는가·버티는가"와 그 확률 구간을 본다.
  M-C가 2026-12-02에 끝나므로 다음 레귤레이션 데이터를 빨리 넣을 수 있어야 한다.
- **검증 제약:**
  - 대미지 기준값은 계산 도구와 독립된 출처가 최소 1건 필요하다.
  - 계산 도구 수치와 스냅샷 수치의 차이, 한국어 대체 목록의 완전성을 자동 테스트로 드러내야 한다.

## 결정

### 결정 1. 기술 스택: Vite + React + TypeScript 정적 SPA, Vitest와 Playwright로 검증

- 앱은 정적 파일로 빌드되는 단일 페이지 앱이다. 단위 테스트는 Vitest, 확인 페이지 스모크 테스트와 브라우저 성능 측정은 Playwright로 한다.
  런타임(Node) 버전은 저장소에서 고정하고, 데이터 생성 스크립트도 같은 런타임에서 돈다.
- 코드는 네 층으로 나눈다.
  - 계산 코어
    - UI와 무관한 동기 순수 함수다. 로드가 끝난 스냅샷을 명시 인자로 받고, 전역 상태에 의존하지 않는다.
    - 세트는 레귤레이션 식별자를 가진다. 세트의 레귤레이션과 넘긴 스냅샷의 레귤레이션이 다르면 입력 오류로 거부한다.
    - 대전 조건의 기본값(더블)은 코어가 정한다.
    - 실능치는 앱 공식(PRD F2)이 단일 원천이다. 스피드·표시·스윕이 이 값을 쓰고, 엔진이 내부에서 계산한 실능치가 앱 값과 같은지 대조 테스트로 확인한다.
  - 스윕 계층: 칸마다 판정을 내는 함수를 받아 33칸 결과와 경계를 만든다. 대미지 판정(결정 3)과 행동 순서(결정 4)가 같은 칸 판정 인터페이스를 쓴다.
  - 데이터 접근층: 레귤레이션 목록과 기본 레귤레이션을 해석하고 스냅샷을 지연 로드한다.
  - 확인 페이지: 앞의 층만 호출한다.

### 결정 2. 계산 엔진: `@smogon/calc` 0.12.0을 정확히 고정하고, 대미지 공식만 맡기는 얇은 래퍼로 감싼다

- 대미지 수치(16단계 난수 배열)만 `@smogon/calc` 0.12.0 gen 0의 `calculate`에 맡긴다.
- 앱 도메인의 세트는 SP를 쓴다. 엔진의 EV 칸에 SP를 넣는 변환은 래퍼 경계 한 곳에서만 한다.
- 다음은 래퍼(앱)가 책임진다.
  - **입력 검증:** 스냅샷과 레귤레이션 규칙값을 기준으로 다음을 확인하고, 엔진의 조용한 무시나 예외에 의존하지 않는다.
    - 종·특성·도구·기술의 합법성
    - SP 범위와 합계
  - **메가 해석:** 엔진의 폼 해석 함수 대신 "스톤 × 원종 → 메가 폼" 표로 직접 해석한다.
    세트의 특성은 원종의 특성 목록으로 검증한다. 메가진화가 지정되면 엔진에는 메가 폼의 특성(스냅샷 값, 보정 우선)을 넘기고, 세트에 적은 원래 특성은 결과에 함께 남긴다.
  - **특성 전달:** 특성은 항상 명시적으로 넘기고, 엔진 데이터의 기본 특성 슬롯은 쓰지 않는다. 연속기 타수에 영향을 주는 특성도 엔진이 반영하도록 전달한다.
  - **수치 주입:** 다음 필드는 계산할 때 항상 스냅샷 값을 엔진 입력 경계에서 주입한다.
    - 종: 종족값, 타입
    - 기술: 위력, 타입, 분류, 타수, 대상

    엔진 API의 제약과 우회 방법은 notes에 둔다. 그 밖의 계산 요소는 엔진 데이터에 의존한다(기술 플래그, 부가효과, 반동, 종 체중, 도구·특성 효과).
    그래서 생성 리포트는 기술 플래그와 종 체중도 엔진과 대조해 차이를 드러낸다.
  - **범위기 대상 수:** 더블에서 대상 수 1은 대전 조건을 더블로 유지한 채 그 기술의 대상을 단일로 바꿔 표현한다.
- **엔진 미지원 항목:** 스냅샷의 합법 항목(종·도구·특성·기술) 중 엔진 데이터에 없는 항목이 있어도 스냅샷 생성은 성공한다.
  그 목록은 매니페스트에 "엔진 미지원"으로 기록하고 리포트로 경고한다. 그 항목으로 계산을 요청하면 "엔진 미지원" 오류로 거부한다.
  엔진 데이터에는 있지만 효과가 구현되지 않은 경우는 기계적으로 탐지할 수 없으므로 결과의 위험으로 남긴다.
  예외로, 위력 0 공격기는 생성 단계에서 엔진을 실제로 돌려 대미지가 0이면 엔진 미지원으로 기록한다(카운터, 분노의앞니, 일격기 등).
- 세트 검증은 엔진 미지원 기술을 기술 목록에 담았다는 이유만으로 거부하지 않는다. 그 기술로 대미지를 계산할 때만 거부한다. 그래야 그런 세트도 스피드 비교 등 다른 계산을 할 수 있다.
- **스피드 의존 기술:** 엔진이 대미지 안에서 스피드를 쓰는 기술·특성(일렉트릭볼, 자이로볼, 앙갚음, 분석)은 엔진이 쓴 스피드를 앱 스피드(결정 4)와 대조한다. 다르면(999 상한 등) "엔진 미지원"으로 거부한다.
  앱 스피드로 위력을 계산해 대리 기술로 넘기는 대안은 기술 플래그·고유 효과를 잃을 수 있어 택하지 않았다.
- **HP 가득일 때 1타를 막는 효과:** 1타 확률은 PRD F3 정의대로 HP가 가득한 방어측 기준이다.
  - 옹골참(틀깨기 공격자면 무시)과 기합의띠(서투름이면 무효): 첫 타를 HP − 1로 막은 분포로 계산한다.
  - 탈·아이스페이스: 틀깨기 공격자가 아니면 "엔진 미지원"으로 거부한다.

### 결정 3. 판정 모델: 1타 확률을 대미지 분포에서 직접 계산하고, 관점별 구간으로 매핑한다

- 엔진의 몇 타 판정 함수는 쓰지 않는다.
- 1타 확률은 대미지 분포에서 직접 계산한다. 급소 발생 확률은 섞지 않고(사용자가 급소 조건을 지정하면 급소가 적용된 분포로 계산한다), 턴 종료 효과는 반영하지 않는다.
  - 단타 기술: 16개 난수 중 방어측 HP 이상인 개수 ÷ 16
  - 연속기: 타별 분포를 합성(합성곱)한 합계 분포에서 낸 정확값
- 대미지 결과에는 타별 16단계 배열(타수 × 16)과 사용 타수를 그대로 담는다. 최소~최대 비율과 1타 확률은 합계 분포에서 낸다.
- **연속기 타수 규칙:** 엔진 기본 타수를 따르고, 계산에 쓴 타수를 결과에 담는다.
  - 고정 타수 기술: 데이터 값
  - 2~5회 기술: 3타. Skill Link가 있으면 5타.
  - Population Bomb: 10타
  - 가변 타수 기술은 호출할 때 타수를 지정할 수 있다.
  - Dragon Darts는 더블 대상 분할을 표현하지 않고 2타로 계산한다.
- 판정 모듈은 1타 확률을 공격 관점과 방어 관점 구간으로 매핑한다.
  - 공격 관점: 중난수 이하 / 고난수 1타 / 확정 1타
  - 방어 관점: 중난수 이상 / 저난수 1타 / 확정 버팀
- 구간 경계값은 판정·스윕 호출의 선택 인자다. 생략하면 기본값(고난수 75%, 저난수 18.75%)을 쓰고, 단건 판정과 스윕이 같은 값을 공유한다.

### 결정 4. 스피드 엔진: 앱이 직접 구현한다

- 최종 스피드는 앱 코드로 계산한다. 대상은 스카프, 순풍, 날씨 연계 특성, 랭크, 마비다. 4096 기준 보정 체인과 반올림 규칙은 게임과 같게 한다.
- 행동 순서 비교(선공/동속/후공)와 추월 최소 SP 역산도 이 모듈이 맡는다. 기술 우선도는 스냅샷 값을 별도 정보로 돌려준다.
- 엔진의 비공개 스피드 함수는 쓰지 않는다. 트릭룸은 다루지 않는다(PRD 비목표).
- PRD F4의 보정 외에 퀵풋(상태이상이면 ×1.5, 마비 반감 없음), 서핑테일(일렉트릭필드 ×2), 검은철구(×0.5)도 반영한다.
- 앱이 다루지 않는 스피드 보정 특성·도구(고대활성 등)가 세트에 있으면 틀린 값을 내지 않고 입력 오류로 거부한다.
  행동 순서만 바꾸는 특성·도구(시간벌기, 퀵드로, 선제공격손톱 등)는 순서 비교에서만 거부한다.

### 결정 5. 게임 데이터 원천: `@pkmn/mods`·`@pkmn/dex` 0.10.13을 정확히 고정하고, 빌드 시 추출한다

- 레귤레이션 데이터의 기계용 진실원은 Showdown champions 계열 모드다.
  이를 패키징한 `@pkmn/mods`·`@pkmn/dex` 0.10.13을 정확한 버전으로 고정해 개발자 명령(빌드 시)으로만 읽는다.
  런타임 번들에는 넣지 않는다.
- 현재 레귤레이션은 champions 모드, 이전 레귤레이션은 레귤레이션별 모드(championsregmb 등)에서 추출한다.
- 합법 판정 규칙:
  - 종: 비표준 표시가 없음 + 외형 전용 폼이 아님 + (배틀 전용 폼이 아님 또는 메가 폼). 메가 여부는 폼 이름으로 판정한다. 메가 플래그로 판정하면 메가냐오닉스 2종이 빠진다.
  - 도구: 상속까지 해석한 뒤 비표준 표시가 없음
  - 커뮤니티 티어 정보는 쓰지 않는다.
- 추출기의 입력은 "상속이 해석된 종·기술·도구·특성·학습 기술 조회 인터페이스"다. 패키지 원천은 그 구현 중 하나이고, 후속 원천(Showdown 커밋)도 같은 인터페이스로 넣는다.
- 종별 특성 목록, 학습 기술, 기술 수치(위력·타입·분류·우선도·타수·대상)의 원천도 이 모드다.
  계산 엔진의 내장 데이터는 합법 판정과 수치에 쓰지 않는다.
- 이 단위는 원천을 그대로 쓰되, 개발자가 공식 게임 값과 다르다고 확인한 항목은 결정 6의 보정표로 덮는다.
- 패키지 배포가 레귤레이션 전환보다 늦으면, 같은 추출기에 Showdown 저장소 특정 커밋의 데이터를 넣는 경로를 붙인다.
  이 경로는 이 단위에서 구현하지 않는다. M-D 전환 시점에 패키지가 없으면 우선 구현한다.

### 결정 6. 스냅샷 구조: 레귤레이션 목록 + 레귤레이션별 정적 JSON 묶음 + 보정표, 저장소에 커밋

- **레귤레이션 목록(인덱스):** 사용 가능한 레귤레이션, 기본 레귤레이션, 레귤레이션마다 추출할 원천 모드의 대응을 담는다. 새 레귤레이션은 데이터 추가와 목록 갱신만으로 들어온다.
  "지정하지 않으면 기본 레귤레이션"은 데이터 접근층이 해석한다(대전 형식 기본값은 코어, 결정 1).
- **레귤레이션별 묶음:** 레귤레이션마다 디렉터리 하나를 둔다.
  - 게임 데이터: 종·메가·도구·기술(수치 포함)·특성·성격·종별 특성·종별 학습 기술
  - 매니페스트: 스키마 버전, 규칙값(능력치당 SP 최대, SP 합계 상한, 레벨, 기간), 원천 개정 식별자, 원천 기준 시각

  생성물은 저장소에 커밋한다.
- **원천 개정 식별자와 시각:**
  - 매니페스트의 원천 식별자는 두 원천을 모두 담는다.
    - 게임 데이터: "패키지명@버전 + lockfile 무결성 해시". 정적 대조로 확인한 Showdown 커밋은 참고값으로만 적는다.
    - 한국어: PokeAPI 커밋 + 파일별 해시(결정 7)
  - 원천 기준 시각은 원천 버전과 함께 저장소의 고정 설정에 기록해 둔 값(패키지 배포 시각, 커밋 시각)이다.
    생성할 때 네트워크로 조회하지 않고, 현재 시각도 쓰지 않는다. 그래서 같은 원천이면 생성물이 바이트 단위로 같다(PRD F6의 "원천 기준 시각").
- **이전 스냅샷 동결:** 원천 버전을 올려도 이미 커밋된 이전 레귤레이션 스냅샷은 다시 만들지 않고 동결한다. 각 매니페스트가 자기 원천 버전을 보존한다.
  재현성 검증은 현재 고정된 원천으로 만드는 스냅샷에만 적용한다.
- **식별자:** 항목 식별자는 Showdown id(소문자 영숫자)다. 레귤레이션이 바뀌어도 변하지 않고, 이름은 표시용이다.
  계산 엔진과 표기가 다른 항목(예: Aegislash)은 별칭표로 잇는다.
- **로드:** 앱은 선택된 레귤레이션의 묶음만 지연 로드한다.
- **수치:** 계산은 선택한 스냅샷의 수치를 쓴다(결정 2의 주입).
  이 단위의 M-B 수치는 현재 원천이 M-C 수치를 물려받은 값이다. 원천 당시 그대로임이 확인된 것은 종·메가·도구 로스터뿐이다(Serebii 신규 목록 대조). M-B의 종별 특성·학습 기술은 레귤레이션별 모드에 오버라이드가 없으면 M-C 값을 물려받는다. 생성 시 오버라이드 존재 여부를 리포트에 적는다.
- **보정표:** 원천이나 엔진이 공식 게임 값과 다르다고 개발자가 확인한 항목을 담는다.
  - 대상 필드: 종족값, 타입, 특성 목록, 학습 기술, 기술 수치, 허용 여부
  - 항목마다 출처와 확인일을 단다.
  - 우선순위: 보정 > 원천 > 엔진
  - 추출 단계에서 적용하고, 적용 내역을 리포트에 남긴다.
  - 원천 기준값으로 쓴 골든 테스트에는 "원천 기준"이라는 출처를 적는다.
- **생성 리포트:** 생성 명령은 다음을 함께 낸다.
  - 직전 레귤레이션 대비 추가·제거 리포트(종·메가·도구)
  - 레귤레이션 간 수치 차이 경고
  - 엔진 내장 수치와의 차이 목록
  - 보정 적용 내역

### 결정 7. 한국어 명칭과 라이선스 고지: PokeAPI CSV(커밋 고정) + 메가 조립 규칙 + 공식 대조표 + 출처를 단 보정표

- 한국어 원천은 PokeAPI 저장소의 CSV다. 커밋 `e5b79b2e…`(2026-11-02)로 고정하고 파일별 해시를 기록한다.
  내려받은 원본은 커밋하지 않는 캐시에 두고, 생성된 한국어 매핑만 스냅샷에 넣는다.
- 조인 키: PokeAPI identifier에서 영숫자만 남긴 값 = Showdown id.
  예외(폼 약어, Leek/stick, 중복 identifier)는 별칭표로 처리한다.
- 메가 이름 규칙: PokeAPI 폼 한국어명이 있으면 그대로 쓰고, 없으면 "메가" + 종 한국어명 + X/Y/Z를 공백 없이 조립한다.
  공식 도감 대조표([mega-ko-official.tsv](./mega-ko-official.tsv))와의 전수 일치를 테스트로 강제한다.
  대조표는 이름 82개라는 사실 정보로 보고, 출처를 표기해 저장소에 테스트 기준값으로 둔다. 앱 번들에는 넣지 않는다.
- 같은 한국어 이름을 가진 폼(메가냐오닉스 수컷·암컷)의 구분 라벨은 한국어 보정표에서 준다.
- 남는 결손(특성 3개, 일부 폼 접미)은 출처를 단 한국어 보정표로 채운다.
  - 보정표는 원천보다 우선한다.
  - PokeAPI 고정 커밋을 올렸을 때 보정 항목에 원천 값이 새로 생기면 리포트를 낸다. 같으면 보정 제거를 권고하고, 다르면 경고한다.
  - 보정도 없는 항목은 영문 대체로 두고, 대체 목록 산출물에 반드시 올린다.
- 생성 명령은 번들되는 코드·데이터 전체의 라이선스·출처 목록을 산출물로 만든다(엔진 MIT, Showdown·@pkmn 파생 데이터 MIT, PokeAPI BSD-3, 상표 문구).
  이 고지는 저장소 고지 파일과 확인 페이지에 표기한다.

## 선택지

### 결정 1 (기술 스택)

#### 선택지 1-A: Vite + React + TypeScript SPA (채택)

- 장점: 정적 빌드가 기본이라 오프라인·정적 배포 요구에 맞는다. 형제 프로젝트 poke-sherpa와 스택이 같아(`package.json` 확인: vite, react, vitest, @playwright/test) 데이터 스크립트·테스트 패턴을 옮기기 쉽다. 다음 단위의 표 UI 상호작용을 무리 없이 만든다.
- 단점: 서버 기능(기능 3의 AI 호출, 데이터 수집 배치)은 별도 계층이 필요하다.

#### 선택지 1-B: Next.js 등 서버 포함 프레임워크

- 장점: 기능 3의 서버 기능을 같은 저장소에 둘 수 있다.
- 단점: 정적 export는 가능하다. 다만 서버 런타임을 전제한 규약·라우팅·의존성이 이 단위(브라우저 단독 계산)에는 필요 없다.

#### 선택지 1-C: 프레임워크 없는 TypeScript + 최소 DOM

- 장점: 의존성이 가장 적다.
- 단점: 다음 단위의 표·하이라이트 UI에서 상태 관리를 직접 짜야 하고, 확인 페이지 구현도 느리다.

### 결정 2 (계산 엔진 경계)

#### 선택지 2-A: 얇은 래퍼. 대미지 공식만 엔진에 맡기고 수치는 항상 주입한다 (채택)

- 장점: 실측한 엔진 결함을 모두 앱 경계에서 막는다(메가 오해석 8쌍, 조용한 무시, 특성 1슬롯, 깨진 기술 11개, 몇 타 판정 실패, 스피드 999 상한). 가장 큰 구현 부담인 대미지 공식은 엔진에 남긴다. 비공개 경로에 의존하지 않고, 성능 여유도 크다(33칸 스윕 0.39ms).
- 단점: 입력 검증, 메가 해석, 수치 주입, 1타 확률, 스피드를 앱이 직접 유지해야 한다. 엔진 버전을 올릴 때 래퍼 가정을 다시 검증해야 한다.

#### 선택지 2-B: 엔진 기능을 최대한 쓴다 (내장 수치·몇 타 판정·폼 해석·스피드 함수 포함)

- 장점: 앱 코드가 가장 적고 엔진 수정이 자동으로 들어온다.
- 단점: 실측한 결함이 그대로 앱 버그가 된다.
  - 메가한카리아스Z가 일반 메가로 계산된다.
  - 앵커샷 같은 기술이 대미지 0으로 나온다.
  - 회복 도구가 있으면 판정이 빈다.
  - 스피드가 999에서 잘린다.

#### 선택지 2-C: 대미지 공식까지 자체 구현

- 장점: 외부 의존이 없고 모든 동작을 통제한다.
- 단점: 특성·도구·필드 상호작용이 방대해 엔진만큼의 회귀 테스트가 필요하다. PRD 비목표와 충돌한다.

### 결정 3 (판정 모델)

#### 선택지 3-A: 대미지 분포에서 1타 확률을 직접 계산하고 앱이 구간을 매핑 (채택)

- 장점: 사용자 기준(1타 여부와 확률 구간)과 정확히 맞는다. 엔진 판정이 회복·지속 대미지를 섞다가 비는 문제를 피한다. 실측 사례에서 엔진 n=1 확률과 일치했다.
- 단점: 연속기 분포 합성을 직접 검증해야 한다.

#### 선택지 3-B: 엔진의 몇 타 판정(n과 확률)을 그대로 쓰고 n=1만 사용

- 장점: 코드가 적다.
- 단점: 방어측이 회복 도구를 지니면 판정이 비는 실측 결함이 있다. 무엇을 섞어 계산하는지 앱이 통제하지 못한다.

#### 선택지 3-C: poke-sherpa의 비율 기반 판정(n = ⌈100 / 최대%⌉, 최소% ≥ 100/n이면 확정) 이식

- 장점: 이미 테스트된 코드가 있다.
- 단점: 확정/난수만 구분하고 1타 확률(16분의 k)을 내지 못한다. 그래서 사용자 구간(75%, 18.75%)을 판정할 수 없고, 연속기와 첫 타 감소 특성도 다루지 못한다.

#### 연속기 타수 규칙의 대안

- 엔진 기본 타수(채택): 엔진·커뮤니티 계산기와 같은 값이라 비교·검증하기 쉽다. 가변 타수는 지정할 수 있다.
- 최대 타수(5타): 공격 관점에서 낙관적이어서, 1타 판정을 과대평가한다.
- 기댓값 타수: 확률 가중 합성이 필요해 복잡하다. 실전 계산기들과 값이 달라 대조하기 어렵다.

### 결정 4 (스피드 엔진)

#### 선택지 4-A: 앱이 직접 구현 (채택)

- 장점: 공식이 단순하고 엔진 데이터와 무관하다. 엔진 비공개 함수와 42,672개 조합을 대조해, 상한 버그 외에는 100% 일치했다. 역산·비교를 같은 모듈에서 일관되게 다룬다.
- 단점: 새 스피드 보정 요소가 생기면 앱이 직접 추가해야 한다.

#### 선택지 4-B: 엔진의 비공개 스피드 함수를 직접 가져와 쓴다

- 장점: 엔진이 지원하는 보정을 그대로 얻는다.
- 단점: gen 0에 999 상한이 잘못 걸린다. 실전 조합에서도 발생한다(예: 실능 230, 랭크 +1, 스카프, 순풍 = 1035 → 999). 공개 API가 아니라 버전업 때 깨질 수 있다. 역산·비교는 어차피 앱이 구현해야 한다.

### 결정 5 (게임 데이터 원천)

#### 선택지 5-A: `@pkmn/mods`·`@pkmn/dex` 정확한 버전 고정 + 빌드 시 추출 (채택)

- 장점: 이미 JS로 빌드돼 있어, 상속(9세대 base → champions → 레귤레이션별 모드) 해석을 패키지가 해 준다. lockfile로 재현성이 완전하다. 0.10.13은 Showdown 2026-11-02 커밋과 데이터가 같다. 특성·학습 기술·기술 수치까지 완전한 목록을 준다.
- 단점: 레귤레이션 전환 반영이 늦을 수 있다(M-C 때 약 7주).

#### 선택지 5-B: Showdown 저장소 특정 커밋의 데이터를 받아 추출

- 장점: 레귤레이션 시작 당일 반영된다. 커밋으로 고정할 수 있다.
- 단점: 외부 코드를 빌드 시 실행해야 하는데, 이번 실측에서 실행을 검증하지 못했다. 두 가지 방식이 있다.
  - 모드 파일만 받아 JS로 바꾼 뒤 고정된 `@pkmn/dex`에 넣기: 9세대 base와 상속 해석은 패키지가 맡는다.
    다만 고정된 패키지의 9세대 base가 그 Showdown 커밋보다 오래됐을 수 있다. 모드 안의 스크립트 코드를 실행해야 하는 부담도 남는다.
  - 저장소를 커밋 고정으로 받아 Showdown 자체 빌드·Dex로 읽기: 상속은 Showdown이 해석하지만, 외부 빌드·실행 부담이 크다.

  어느 쪽이든 Showdown 내부 구조가 바뀌면 깨질 수 있다.

#### 선택지 5-C: 계산 엔진 내장 데이터를 로스터·수치 원천으로 사용

- 장점: 추가 의존성이 없다.
- 단점: 레귤레이션을 하나만 담고, 특성이 1슬롯이며, learnset이 없고, 깨진 기술 11개가 있다. PRD F6을 충족하지 못한다.

### 결정 6 (스냅샷 구조)

#### 선택지 6-A: 레귤레이션 목록 + 레귤레이션별 정적 JSON 묶음 커밋 + 지연 로드 + 보정표 (채택)

- 장점:
  - 오프라인·정적 배포를 만족한다.
  - 레귤레이션을 추가해도 초기 로드가 커지지 않고, 코드 수정 없이 데이터만 넣으면 된다.
  - 커밋된 생성물이라 diff 리뷰와 재현 확인이 쉽다.
  - 레귤레이션별 종·메가·도구 로스터를 원천 당시 그대로 보존하고, 이전 스냅샷을 동결한다.
- 단점: 생성물이 저장소 크기를 늘린다. 이 단위에서 이전 레귤레이션의 수치와 종별 특성·학습 기술은 원천 당시 값이 아닐 수 있다.

#### 선택지 6-B: 모든 레귤레이션을 한 데이터셋에 넣고 항목마다 허용 레귤레이션 플래그를 붙인다

- 장점: 중복이 적다.
- 단점: 레귤레이션 간 학습 기술·특성·규칙값 차이를 표현하기 복잡하다. 새 레귤레이션을 넣을 때 기존 레귤레이션 데이터도 함께 다시 써야 해서 동결할 수 없다. 항상 전체를 로드한다.

#### 선택지 6-C: 런타임에 원천(API 등)에서 받아 온다

- 장점: 저장소가 가볍다.
- 단점: 오프라인 요구(PRD 비기능)를 어기고 재현성이 없다.

### 결정 7 (한국어 원천)

#### 선택지 7-A: PokeAPI CSV 커밋 고정 + 메가 조립 규칙 + 공식 대조표 + 보정표 (채택)

- 장점: 기술·도구·성격·기본 종 결손이 0이고, 신규 메가스톤도 들어 있다. BSD-3라 재배포할 수 있다. 메가 82개는 규칙과 대조표로 전수 검증된다. 수동 입력은 특성 3개와 폼 일부로 작다.
- 단점: 폼 별칭표를 관리해야 한다. 원천이 나중에 값을 채우면 보정표와 충돌할 수 있다(생성 리포트로 완화한다). 라이선스 고지가 필요하다.

#### 선택지 7-B: 포켓몬코리아 공식 도감 스크래핑

- 장점: 공식 표기라 권위가 가장 높다.
- 단점: 기술·도구 DB가 없다. 이용 조건이 불명확하고 버전을 고정할 수 없다. 그래서 메가 대조용 테스트 기준값으로만 쓴다.

#### 선택지 7-C: 나무위키 등 커뮤니티 위키

- 장점: 신규 항목 반영이 빠르다.
- 단점: CC BY-NC-SA 조건이 번들 재배포와 맞지 않는다. 비정형이고 버전을 고정할 수 없다.

#### 선택지 7-D: 전부 수동 테이블

- 장점: 완전히 통제할 수 있다.
- 단점: 약 1,290개 항목을 입력·검수해야 하고, 레귤레이션마다 유지 비용이 크다.

## 선택 근거

- **결정 1:** PRD는 브라우저 단독, 정적 배포, 개발용 확인 페이지를 요구한다. 1-A가 추가 설정 없이 이를 만족하고, 형제 프로젝트의 스크립트·테스트 자산을 옮길 수 있다.
  - 1-B는 기능 3의 서버 규약을 미리 끌어온다.
  - 1-C는 다음 단위 UI 비용을 키운다.

  계산 코어를 스냅샷 인자를 받는 동기 함수로 둔 이유는 두 가지다. 테스트가 단순해지고, 다음 단위가 같은 코어를 일괄 계산에 그대로 쓸 수 있다.
- **결정 2:** 실측한 엔진 결함은 전부 "엔진이 대신 판단하거나 엔진이 들고 있는 데이터"에서 나왔다(검증, 폼 해석, 특성 슬롯, 깨진 기술 데이터, 몇 타 판정, 스피드).
  - 대미지 공식은 무보정 단타 1건에서 손계산과 일치했다. 수치를 덮어쓴 결과도 기대값과 일치했다.
  - 그래서 공식만 맡기고 데이터와 판단은 앱이 갖는 2-A가 정확도와 유지 비용의 균형점이다.
  - 2-B는 확인된 버그를 그대로 안고, 2-C는 PRD 비목표다.
  - 엔진이 챔피언스 고유 규칙(바뀐 상태이상, 기술 사용 조건)을 대미지 공식에 반영했는지는 확인하지 못했다. 이 위험은 결과에 남기고, 보정이 걸린 독립 손계산을 추가해 검증한다.
- **결정 3:** 사용자가 정한 판정 기준(1타 여부와 75%·18.75% 구간)은 엔진의 n타 개념과 다르고, 엔진 판정은 회복 도구에서 비는 결함도 있다. 분포에서 직접 계산하면 정의를 앱이 소유하고, 실측상 결과도 같다.
  - 3-C는 확률을 내지 못해 사용자 구간을 표현할 수 없다.
  - 연속기 타수는 엔진 기본값을 따른다. 커뮤니티 계산기와 비교할 수 있게 하고, 결과에 타수를 보여 해석을 열어 두기 위해서다.
- **결정 4:** 공식이 단순하고 전수 대조로 검증됐다. 엔진 함수에는 실전 범위의 상한 버그가 있다. 역산·비교는 어느 쪽이든 앱이 구현해야 하므로 4-A가 일관적이다.
- **결정 5:** PRD는 공식 레귤레이션 기준, 종별 특성·학습 기술, 이전 레귤레이션 보존을 요구한다. 이를 모두 담은 원천은 champions 계열 모드뿐이고, 5-A는 그 모드를 검증된 패키지로 재현 가능하게 쓴다.
  - 전환 시 실측 지연은 M-C 때 약 7주였다. 그래도 5-B는 실행 검증을 하지 못한 경로라 지금 채택하지 않는다. 같은 추출기에 원천만 바꿔 넣을 수 있도록 구조만 열어 두고, M-D 전환 때 패키지가 없으면 우선 구현한다.
  - 5-C는 PRD를 충족하지 못한다.
- **결정 6:** 오프라인, 재현성, 레귤레이션 선택, 원천 기록 요구를 6-A가 직접 만족한다.
  - 수치를 항상 스냅샷에서 주입하므로, 엔진 데이터가 늦거나 틀려도 계산은 원천과 보정표를 따른다.
  - 규칙값(SP 상한 등)을 매니페스트에 두는 이유: PRD가 이를 레귤레이션별 값으로 관리하라고 했고, 다음 레귤레이션에서 바뀌어도 코드를 고치지 않기 위해서다.
  - 원천 기준 시각을 원천에서 정하는 이유: 생성 시점 기록과 재현성(같은 원천이면 같은 결과) 요구를 동시에 만족하기 위해서다.
- **결정 7:** 결손이 가장 적고 재배포할 수 있는 원천은 PokeAPI다. 메가 표기는 규칙과 공식 대조표로 82/82 검증된다.
  - 남는 결손은 출처를 단 보정표로 추적하므로, sherpa에서 생긴 "대체값과 진짜 한국어를 구별할 수 없는" 문제가 생기지 않는다.
  - 대조표는 이용 조건이 불명확한 공식 사이트에서 왔으므로 번들하지 않는다.

## 결과

### 긍정적 영향

- 계산 도구의 결함(깨진 기술 데이터 포함)이 앱 경계에서 막혀, 다음 단위의 표·하이라이트·추천이 같은 정확한 판정 위에 선다.
- 판정 정의(1타 확률, 구간, 경계)를 앱이 소유한다. 사용자 기준이 바뀌면 경계값 인자나 판정 모듈만 바꾸면 된다.
- 레귤레이션 데이터가 원천 버전·규칙값과 함께 보존되고 diff 리포트가 나온다. 원천 패키지가 제때 배포되면 M-D 전환은 "생성 → 리포트 대조 → 커밋"이 된다.
- 한국어 결손과 보정 적용 내역이 산출물로 드러나 누락 없이 추적된다.
- 성능 여유(33칸 스윕 0.39ms, 300세트 약 4ms, Node 기준)가 커서 다음 단위의 일괄 계산을 별도 최적화 없이 시작할 수 있다.

### 부정적 영향 / 트레이드오프

- 입력 검증, 메가 해석, 수치 주입, 1타 확률 합성, 스피드를 앱이 유지해야 한다. 엔진을 올릴 때마다 래퍼 가정을 다시 검증해야 한다.
- 엔진이 챔피언스 고유 규칙을 대미지 공식에 반영했는지는 아직 일부만 검증했다(무보정 단타 1건 + 보정 추가 1건 예정).
- 기술 플래그, 부가효과, 종 체중, 도구·특성 효과는 엔진 데이터에 의존한다. 차이는 생성 리포트로 드러나지만, 엔진 데이터에 있는데 효과가 구현되지 않은 경우는 탐지하지 못한다.
- 원천 패키지가 레귤레이션 전환보다 늦으면, Showdown 커밋 경로(후속 작업)를 구현하기 전까지 새 레귤레이션 반영이 늦어진다.
- 계산 엔진 npm도 늦을 수 있다(M-C 9일, M-B 약 3개월). 엔진에 없는 신규 종·도구·특성·기술은 수치 주입으로도 계산할 수 없다. 이런 항목은 매니페스트에 "엔진 미지원"으로 기록되고 계산이 거부된다.
- 이 단위의 M-B 수치는 원천 당시 값이 아니다(M-C 수치를 물려받음). 허용 범위만 원천 당시 그대로다.
- 생성된 스냅샷 JSON이 저장소에 커밋되어 저장소가 커진다.
- 엔진은 Dragon Darts의 더블 대상 분할을 표현하지 못한다. 2타로 계산하고 결과에 타수를 표시한다.
- 성능 수치는 Node(Apple M4 Pro) 기준이다. PRD 기준인 브라우저 측정은 구현 중에 한다.

## 검증

- [ ] PRD 수용 기준 중 자동화할 수 있는 항목은 자동 테스트와 UI 스모크로 통과한다. 문서 기록 항목(경계 SP 사전 기록, 측정 기록, 생성 명령 문서)은 notes.md와 README로 확인한다. 아래는 이 ADR의 결정이 의도대로 동작하는지 따로 확인하는 항목이다.
- [ ] 결정 1:
  - 정적 빌드 결과물에서 확인 페이지가 동작하고, 계산·조회 중 외부 요청이 0건이다.
  - 계산 코어가 스냅샷을 인자로 받아 브라우저 없이(단위 테스트에서) 동작한다.
  - 세트와 스냅샷의 레귤레이션이 다르면 입력 오류가 난다.
  - 앱 실능치와 엔진 내부 실능치가 전 합법 종 × SP 0·32 × 성격 보정 3종에서 일치한다.
- [ ] 결정 2:
  - 메가 82쌍 전체가 "스톤 × 원종" 표로 해석된다.
  - 메가 방어측은 메가 폼 특성으로 계산된다(예: 메가마폭시는 부유로 땅 기술에 면역이다).
  - 깨진 기술 11개가 스냅샷 수치로 대미지가 나온다.
  - 범위기 대상 수 1 + 도우미 조합이 싱글 + 도우미와 같다.
  - 단단한발톱(메가갑주무사)과 예리함(메가앱솔Z)이 접촉·베기 기술에 각각 반영된다.
  - 엔진 미지원 항목은 테스트용 합성 스냅샷으로 매니페스트 기록과 계산 거부를 확인한다.
- [ ] 결정 3:
  - 1타 확률이 독립 계수(HP 이상 개수 ÷ 16)와 일치한다.
  - 연속기는 2타 기술의 16 × 16 전수 계수와 일치하고, 엔진 n=1 확률과도 일치한다.
  - 멀티스케일 + 연속기에서 첫 타만 반감된 분포로 1타 확률이 나온다.
  - 구간 매핑이 PRD 확률 사례표대로 나온다.
  - 경계값 인자를 바꾸면 단건과 스윕이 함께 바뀐다.
  - 연속기 결과에 타별 배열과 타수가 담긴다.
- [ ] 결정 4: PRD 스피드 기준값이 통과한다. 자체 공식이 엔진 함수와 상한 이외 범위에서 일치하는지 표본 대조 테스트를 둔다.
- [ ] 대미지 독립 출처:
  - 대도각참 기습 → 메가마폭시 162~192가 손계산과 일치한다.
  - 보정이 걸린 독립 손계산(예: 범위기 + 도우미)을 1건 더 둔다.
- [ ] 결정 5:
  - M-B → M-C 리포트가 `@pkmn/*` 0.10.13 기준 종 35/0, 도구 18/0, 메가 6으로 나온다.
  - Future 메가와 배틀·외형 전용 폼이 빠지고, Smogon 밴 종은 들어 있다.
- [ ] 결정 6:
  - 같은 원천으로 두 번 생성한 결과가 바이트 단위로 같고, 생성 중 네트워크 조회가 없다(PokeAPI 캐시가 있을 때).
  - 수치를 하나 바꾼 합성 이전 스냅샷으로 레귤레이션 간 수치 차이 경고가 나온다.
  - 엔진과의 차이 목록에 기술 플래그·종 체중 대조가 들어 있다.
  - 레귤레이션 목록만 바꿔 기본 레귤레이션이 바뀐다.
  - 규칙값이 매니페스트에서 읽힌다.
