# ADR: 스피드 탭 개편

> 작성 고도: ADR은 "어떤 구조를 왜 골랐나"의 근거 저널이다. 코드 스니펫·전체 설계문서를 본문에
> 넣지 않는다(과대 ADR) — 상세 구현은 코드·별도 설계문서로 내린다. 사람은 중립 역할어로만
> 지칭하고 개인 호칭·별명은 넣지 않는다. 참고: `harness/templates/examples/README.md`.

> 범위: PRD "ADR 필요 여부" 6항목을 결정 1~6으로 다룬다. 결정 1(화면 배치)은 디자인 결정 레인 시안(`./design-options.html`) 중 사용자가 고른 대안 C로 정했다(2026-11-15).
> 상위 ADR과의 관계: `../sp-sweep-table/adr.md`·`../damage-tabs-row-revamp/adr.md`의 스피드 탭 조항(스피드 카드·랭크 행·스카프 행, "스피드 탭은 항목 층을 쓰지 않고 지금 모델 그대로")을 이 ADR이 대체한다. 공격·방어 탭 조항은 도구 표시 위치(결정 4) 외에는 그대로 유효하다.
> 권고로 적었던 항목(결정 2 최소 S 규칙·예산 초과 표시, 결정 3 날씨 특성 기준, 결정 5 메가스톤·대체 표지)은 사용자가 2026-11-15에 확정했다. 결정 5 메가스톤은 권고(종별)와 달리 공통 아이콘 하나로 정해졌다. 문서 상태는 사전 승인 전이라 proposed다.

## 컨텍스트

- **PRD 요구**
  - 스피드 탭 본문은 세로 스피드 차트 하나다. 카드 리스트·배분 선택 메뉴·직접 추가 폼·핀·결과 배지가 없어진다(R1·R12).
  - 래더 상대마다 점유율 1위 배분 묶음 하나가 기본 배지이고, 조건 배지(랭크업·스카프·순풍·날씨/필드)는 그 기본 배지에만 붙는다(R3·R7).
  - 내 쪽은 기준선 하나다. 날씨·필드는 넣지 않고 내 도구·특성·내 순풍만 반영한다. 내 세트가 거부되면 기준선·상태·요약·최소 S를 내지 않는다(R4).
  - 배지 상세에 추월에 필요한 내 최소 S(무보정·상승)가 있고, 다른 배분을 차트에 추가·삭제할 수 있다(R6·R15).
  - 조건 종류별 필터가 "상대 순풍" 토글을 대체한다(R8). 구애스카프 기준 기본값이 10%에서 5%로 바뀐다(R7).
  - 전 탭에서 도구 아이콘이 포켓몬 이미지 오른쪽 아래에 겹친다. 변형 줄 표지의 접근 이름·줄 높이는 유지한다(R13). 대상 도구 전부가 오프라인 아이콘을 가진다(R14).
  - 차트는 실수치 내림차순 목록으로 읽히고 화살표·Home/End로 이동한다(비기능 접근성).
  - 성능 예산(첫 표시 ≤ 500ms, 완료 ≤ 3초, Long Task ≤ 100ms), 깜박임 없음(AC25), 계산 일관성(앱 공식만)을 지킨다.
- **현재 코드/데이터 제약**(조사 2026-11-15, notes "코드 제약")
  - 스피드는 `src/core/speed.ts`의 앱 공식으로만 낸다(INV-261105-app-speed-no-engine). 이 모듈은 한 세트의 최종 스피드, 두 세트 순서 비교, 수치 목표에 대한 최소 SP, 한 세트의 스피드 지원 여부 확인을 이미 공개한다.
  - 날씨는 조건의 양쪽 공통 입력이다. 순서 비교는 주어진 두 세트 중 하나라도 구름보기·에어록이면 날씨를 지운다. 한 세트 단독 계산은 자기 특성만 본다.
  - 날씨·필드 ×2 특성 표(특성 id → 판정 술어 함수의 Record)와 계산 거부·순서 거부 목록은 `speed.ts` 안에만 있다(비공개). 날씨 무효 특성 목록(구름보기·에어록)만 이미 공개돼 있다(`core/index.ts`에서 export).
  - 지금 스피드 목표 문구는 코어의 최소 SP 함수가 아니라 cards 층 `target.ts`의 공용 목표 규칙("현재 판정보다 한 단계 위, 어느 변형도 닿지 않으면 현재 유지")을 행 스윕 칸에 적용해 낸다. 스피드 판정 순서는 후공 < 동속 < 선공이라, 후공이면 목표가 동속 이상이고 이미 선공이면 "현재 유지"다. 예산 초과는 칸의 필요 SP(need)로 낸다. 코어의 최소 SP 함수는 제품 경로에서 부르지 않는다(개발용 패널만).
  - 지금 스피드 탭은 공격·방어와 같은 계획(`src/cards/plan.ts`의 스피드 카드 빌더) → 행 작업(`src/cards/rowTask.ts`, 내 SP 0~32 스윕) → 실행기(`src/app/executor.ts`, 시간 조각) 경로를 탄다. 행에는 이미 내·상대 실수치가 있다.
  - 랭크 수단은 `src/cards/rank.ts`·`rankMeans.ts`의 능동 수단 규칙(INV-261113-rank-active-means-only)을 따른다. 스카프 규칙은 스피드 카드 빌더 안에 묻혀 있다. 기준값은 `src/cards/types.ts`의 표시 기준 기본값이다.
  - 앱 상태(`src/app/state.ts`)의 직접 추가 배분·핀은 탭 필드를 갖지만 "모든 추가 배분은 고정" 단일 모델이고 계산 세대를 올린다. 순풍은 내·상대 두 값이다.
  - 도구 아이콘은 반감열매·화력 도구 40개뿐이고(`src/assets/item-icons`), 판 고정 manifest와 라이선스 고지가 있다. 없는 도구는 텍스트 배지로 대체된다(`src/ui/images.ts`).
  - 포켓몬 이미지는 단독 이미지 요소이고, e2e가 "이름 칸 바로 아래 자식" 구조를 전제한다(`e2e/product-images.spec.ts`).
- **사용자 경험 제약**
  - 스피드는 한 줄로 늘어선 값이라 순서와 내 위치를 한 화면에 보여야 한다(PRD 배경).
  - SP 슬라이더를 움직이는 동안 배지가 튀지 않아야 한다.
  - 도구 겹침은 게임 박스·파티 화면처럼 보여야 하고, 공격·방어 탭 카드의 클릭·높이를 바꾸지 않아야 한다.
- **검증 제약**
  - 조건 배지 생성 규칙과 최소 S는 화면 없이 단위 테스트로 재현할 수 있어야 한다.
  - 기존 스피드 카드 테스트의 대체는 AC23 매핑으로 남긴다. 기존 목표 문구 결과는 카드를 지우기 전에 기대값 표로 고정한다(AC7b).

## 결정

### 결정 1. 스피드 탭 화면 배치: 실수치 사다리 + 따라오는 기준선 띠(시안 대안 C, 사용자 선택 2026-11-15). 비례 축 없이 실수치마다 같은 높이 한 줄을 두고, 요약을 품은 기준선 띠가 차트 안에서 위·아래 끝에 붙어 따라오며, 상세는 그 줄 바로 아래에 펼친다

- **축과 줄(PRD R2).**
  - 연속 비례 축을 두지 않는다. 표시 중인 배지의 실수치마다 같은 높이의 줄 하나를 위가 빠른 순서로 쌓는다. 배지가 없는 실수치는 줄이 없다(내 실수치 줄은 예외, 아래 기준선 띠).
  - 실수치 차이는 화면 간격 대신 줄마다 "윗줄과 차이" 숫자(예: −22)로 적는다. 맨 윗줄은 비운다. 기준선 띠 바로 아랫줄의 숫자는 곧 내가 그 줄보다 빠른 차이다.
  - 줄은 세 칸이다: 실수치 라벨(줄마다 한 번) · 윗줄과 차이 · 배지 칸. 배지는 배지 칸 안에서 R2의 같은 줄 순서로 가로로 놓이고, 넘치면 같은 줄 안에서 줄을 바꾼다. 줄 높이는 최소 높이가 같고, 줄바꿈이 생긴 줄만 그만큼 높아진다.
  - 그래서 실수치가 1만 달라도 이웃 줄이 겹치지 않는다(R2 최소 줄 간격, AC2). "아슬아슬 / 크게 차이"는 차이 숫자로만 읽는다(트레이드오프).
  - 축 범위: 줄은 표시 중인 배지와 내 실수치만 만든다. 어떤 배지도 잘리지 않고, R2의 내 S0 무보정 ~ S32 상승 도달 범위는 띠로 그리지 않으므로(R2) 따로 줄을 만들지 않는다. 연속 축이 없어 결정 2의 "축 범위 입력"은 배치에 쓰지 않는다(결정 2에서 뺐다).
  - 내 SP를 바꾸면 기준선 띠가 다른 줄로 옮겨 가고, 내 실수치에 배지가 없으면 띠 줄이 새로 끼거나 빠져 그 아래 줄이 한 줄 높이만큼 밀릴 수 있다. 배지가 다른 실수치 줄로 옮겨 가는 일은 없다(배지 목록이 내 SP와 무관, 결정 2). AC25의 판정은 "배지가 자기 실수치 줄에 있는가"로 한다.
- **기준선 띠와 요약(PRD R4·R5).**
  - 기준선 띠는 내 실수치 줄 자체다. 띠 안에 "나 · 내 배분 표기(내 순풍이 켜져 있으면 '순풍') · 내 실수치" 표지, 그 실수치의 동속 배지들, 오른쪽 끝에 요약 "추월 n · 동속 n · 추월당함 n"이 한 흐름으로 놓인다. 동속 배지와 라벨·요약이 같은 흐름이라 서로 가리지 않는다(R5). 동속 배지에는 "동속" 표지가 보인다.
  - 띠는 차트 프레임 안에서 위·아래 양쪽 끝에 붙는(sticky) 불투명 줄이다. 스크롤하면 띠가 위 끝이나 아래 끝에 붙어 늘 보이므로 "내 위치로" 버튼이나 자동 스크롤을 두지 않는다(R2 "기준선이 자동으로 화면 안"을 띠가 늘 만족). 요약이 띠 안에 있어 스크롤 중에도 보인다(R2·R5 요약 위치 = 기준선 띠 안). 400px에서는 요약이 띠 안에서 다음 줄로 넘어갈 수 있다.
  - 처음 열면 스크롤 위치는 맨 위다. 기준선이 아래쪽에 있으면 띠는 아래 끝에 붙은 채 보인다(AC24).
  - 띠가 끝에 붙어 있는 동안 다른 줄은 그 뒤로 지나간다. AC2의 겹침 검사는 띠가 제자리에 있는 스크롤 위치에서 하고, 띠가 붙은 상태에서는 키보드로 포커스한 배지가 띠에 가리지 않도록 차트 프레임의 위·아래 스크롤 여백을 띠 높이만큼 둔다.
  - 띠 안 동속 배지의 상세를 열 때 띠가 끝에 붙어 있으면, 띠와 그 상세가 제자리에 보이도록 차트 프레임을 스크롤한다.
- **차트 프레임(PRD R2 고정 요소).** 차트는 자체 내부 스크롤 프레임이다. 최대 높이는 보이는 화면 높이에서 프레임 위 고정 요소(탭 머리·차트 머리)를 뺀 값이고, 데스크톱·400px이 같은 구조다. 프레임 안에서 고정되는 것은 기준선 띠뿐이다. 실수치 라벨은 줄마다 붙어 함께 스크롤된다.
- **배지(PRD R3).** 이미지(도구 겹침, 결정 4) · 이름 텍스트 · 배분 표기 · 조건 태그 · 표지("메가"·"도구 무효"·"동속"·"추가"·"프리셋 n") 순이다. 상태(추월·동속·추월당함)는 배경색과 위치로, 목록 밖 타겟은 다른 배경색으로 구분한다.
  - 이름 텍스트: 줄 폭에 여유가 있는 데스크톱 폭에서는 배지 안에 상대 이름 텍스트를 둔다. 400px 같은 좁은 폭에서는 빼고 이미지·배분 표기만 둔다. 어느 폭이든 이름은 접근 이름·툴팁에 있다. 전환 폭 경계값은 구현 설계에서 정한다.
  - 시안의 "아이콘 없는 도구는 첫 글자" 표시는 시안용 자리 표시다. 실제 대체 표지는 결정 5를 따른다.
- **상세(PRD R6).**
  - 형태: 팝오버·아래쪽 시트를 두지 않는다. 그 배지가 있는 줄 바로 아래에 줄 폭 전체로 펼쳐지는 인라인 상세다. 데스크톱은 배지 칸 시작선에 맞춰 들여 쓰고, 400px은 들여쓰기 없이 같은 구조다. 한 번에 하나만 열린다.
  - 열기: 호버는 250ms 지연 뒤, 포커스·탭·클릭은 즉시 연다. 키보드 화살표로 포커스를 옮겨도 R6대로 새 배지의 상세로 바뀐다. 상세가 다른 줄로 옮겨 갈 때는 포커스한 배지의 화면 위치가 유지되도록 프레임 스크롤을 맞춘다.
  - 닫기: 다른 배지로 바뀔 때, Esc, 바깥 클릭·탭, 상세의 닫기(×) 버튼. 마우스가 배지를 떠나는 것만으로는 닫히지 않는다(아래 줄이 밀렸다 돌아오는 흔들림 방지). 펼친 상세는 아래 줄만 민다. 해당 줄과 그 위 줄은 움직이지 않는다.
  - 내용 순서: 머리(큰 이미지 + 도구 겹침, 상대 이름(메가 폼), 배분 표기·조건·실수치, 상태 표지, 닫기) → 배분 점유율(임의 추가 배지는 "직접 입력", 목록 밖 타겟은 "목록 밖 타겟 · 프리셋 n") → 조건(조건 점유율, 날씨·필드 배지는 "파트너 날씨 가정"도 적음) → 도구(겹쳐 보인 도구 이름, 무딘손이면 "도구 효과 없음") → 최소 S 한 줄("추월: 최소 S20 / S12+", 예산 초과 표지는 결정 2)과 "성격 무보정 / 상승 · 내 도구·특성(·순풍) 기준" 보조 문구 → "다른 배분 추가" 또는 "이 배지 지우기".
  - "다른 배분 추가"(R15): 래더 상대 배지(기본·조건·추가) 상세에만 있는 접힘 버튼이다. 상세를 열 때마다 접힌 상태로 시작한다. 펼치면 그 상대의 배분 묶음 목록(배분 표기·점유율·실수치, 이미 차트에 있으면 "차트에 있음"으로 비활성, 아니면 "+ 추가")과 직접 입력 줄(SP 0~32 숫자 입력, 성격 상승·무보정·하락 선택, "추가" 버튼, 중복이면 "이미 있음" 정중한 알림 문구)이 상세 안에 나온다. 추가한 배지의 상세에는 대신 "이 배지 지우기"가 있다. 목록 밖 타겟 상세에는 둘 다 없다.
- **차트 머리(조건 필터·내 순풍, PRD R8·R11).** 차트 프레임 바로 위 한 줄이 스피드 탭 툴바다. "조건 배지" 라벨 뒤에 랭크업·스카프·순풍·날씨/필드 토글 칩 4개, 구분선, "내 순풍" 토글 칩을 둔다. 이 줄은 프레임 밖이라 스크롤과 무관하게 보인다. 전 탭 공통 툴바(상위 N·선택 필터·통계 설정)는 그대로 그 위에 있다. 400px에서는 칩이 줄을 바꾼다.
- **순서 비교 불가 영역(PRD R9).** 차트 프레임 스크롤 내용의 맨 끝, 가장 느린 줄 아래에 점선 구분과 함께 "순서 비교 불가 · 스피드 축에 놓지 않음" 머리를 두고, 상대마다 이미지(도구 겹침) · 이유("계산 불가"·"행동 순서 변경") · "이름 · 원인(특성·도구)" 텍스트를 나열한다. 원인이 화면 텍스트로 보이므로 상세·포커스가 없다. 차트 키보드 이동 대상이 아니고, 차트 목록과 별개의 목록이다. 해당 상대가 없으면 영역을 그리지 않는다.
- **빈 상태(PRD R11, AC15).** 표시할 배지가 하나도 없으면 프레임 안에 기준선 띠(내 실수치·배분 표기, 요약은 모두 0)를 두고 그 바로 아래에 "표시할 상대가 없습니다. 상위 N·포켓몬 선택 필터를 확인해 주세요." 안내 줄을 둔다. 순서 비교 불가 상대가 있으면 그 영역은 그대로 그 아래에 보인다.
- **내 세트 계산 불가(PRD R4, AC5b).** 내 세트가 거부되면 기준선 띠를 그리지 않는다(동속·요약도 없음). 차트 머리 줄 바로 아래, 프레임 밖에 "내 스피드 계산 불가" 또는 "내 행동 순서 변경"과 원인 이름을 적은 안내 줄을 둔다. 줄과 배지는 그대로 놓이고 상태 배경 없이 중립으로 보이며, 상세의 최소 S 자리에 같은 안내가 들어간다.
- **결정 2·6이 넘긴 제약의 반영.** 배치는 결정 2의 배지 모델(배지 목록·기준선·순서 비교 불가 목록·내 세트 거부)만 그린다. 줄 구성(실수치 줄 목록, 윗줄 차이, 기준선 띠 줄 위치와 동속 병합)은 결정 6의 순수 계산이 내고, 화면은 그 순서대로 흐름 배치한다. 연속 축이 없어 따로 계산할 위치 값이 없다.

### 결정 2. 차트 데이터 모델과 계산 경로: 행 스윕을 걷어내고, 배지(상대·묶음·조건 → 실수치) 단위 모델을 cards 층의 동기 순수 계산으로 둔다

- **데이터 계약(배지 모델).** 차트의 입력은 "배지 목록 + 기준선 + 순서 비교 불가 목록"(내 세트 거부면 기준선 대신 거부 종류·원인)이다.
  - 배지 = 상대(래더/목록 밖 타겟) × 배분 묶음(SP, 성격 부호) × 조건(없음/랭크 값/스카프·스카프 아닌 도구/순풍/날씨·필드 하나) → 실수치·계산에 쓴 도구·점유율 근거.
  - 배지 목록은 내 SP·성격에 의존하지 않는다. 내 세트에서 쓰는 것은 특성뿐이다(날씨 무효 판정).
  - 기준선과 상태(추월·동속·추월당함)·요약은 배지 목록과 내 세트로부터 따로 낸다.
- **계산 위치.** 배지 모델은 cards 층의 순수 함수가 동기로 만든다. 실행기의 행 작업·시간 조각·캐시를 쓰지 않는다. 스피드 탭은 실행기의 탭 목록에서 빠지고, 공격·방어 탭만 실행기를 탄다.
- **실수치.** 배지마다 그 배지 세트(조건을 반영한 상대 세트)의 최종 스피드를 앱 공식의 한 세트 단독 계산으로 낸다. 화면이나 배지 모델이 배수를 따로 곱하지 않는다(PRD R7, INV-261105-app-speed-no-engine).
- **상대 단독 날씨와 무효 판정 주체.**
  - 날씨 배지는 상대 세트(특성을 그 날씨 특성으로 둔 세트)에만 날씨·필드를 넣어 단독 계산한다. 단독 계산은 자기 특성만 보므로 상대 쪽 무효는 생기지 않는다.
  - 무효 판정은 배지 생성 규칙(결정 3)이 내 특성으로 한다. 내 특성이 구름보기·에어록이면 날씨 배지를 만들지 않는다. 무효 특성 목록은 코어가 이미 공개한 것을 쓴다.
  - 기준선은 날씨·필드 없음으로 계산한다. 그래서 공통 날씨 입력을 상대에게만 거는 새 코어 입력이 필요 없다.
  - 대미지 판정의 날씨 경로(`fieldAbilities.ts`의 공격측 유도, `plan.ts`의 대미지 조건)와 방어 탭 "확실히 빠름" 규칙은 건드리지 않는다(INV-261115-attacker-field-only).
- **최소 S.** 상세를 연 배지에 대해, 코어의 "수치 목표에 대한 최소 SP"를 내 세트(무보정·상승 두 성격), 내 순풍, 날씨 없음 조건으로 부른다. 목표는 그 배지 실수치다. 엄격히 큰 경우만 추월이다.
  - 이 규칙은 기존 목표 문구 규칙(한 단계 위)과 다르다. 기존 규칙은 후공일 때 동속을 목표로 잡을 수 있고, 이미 선공이면 "현재 유지"를 낸다. 그래서 AC7b의 기존 결과 고정 표는 "추월(선공) 목표"인 사례끼리만 비교한다. 기존 규칙이 동속을 목표로 잡은 사례와 "현재 유지" 사례는 표에 "규칙 변경으로 결과 다름"으로 따로 적고 일치 판정에서 뺀다(사용자 확정 2026-11-15. PRD R12 문구는 이 규칙에 맞게 정정됐다).
  - 코어 결과 세 종류의 표시: 가능(ok) = "S＜SP＞", 불가(impossible) = "불가", 예산 초과(over-budget) = 0~32 안에서 닿으므로 불가가 아니라 "S＜SP＞"을 내고 "잔여 예산 ＜잔여＞ 초과" 표지를 덧붙인다(사용자 확정 2026-11-15). 무보정·상승 각각 따로 판정한다. AC7b 사례 표에 예산 초과 사례를 하나 넣는다.
  - 결과는 배지 모델에 미리 넣지 않고 상세 표시 때 계산한다(배지 수 × 2회라 즉시 계산도 가능하지만, 모델을 내 SP와 무관하게 유지하려는 선택).
- **거부 처리.**
  - 상대: 배지 세트마다 코어의 스피드 지원 확인을 부른다. 거부 종류(계산 불가 / 행동 순서 변경)와 원인(특성·도구)을 코어가 구분해 돌려주도록 확인 경로를 넓힌다. 거부 목록은 `speed.ts` 한 곳에만 둔다. 기본 배지가 거부되면 그 상대는 "순서 비교 불가"로, 조건 배지만 거부되면 그 조건 배지만 빠진다(R9).
  - 내 세트: 같은 확인을 내 세트에 먼저 부른다. 거부면 기준선·상태·요약·최소 S를 내지 않고 "내 세트 거부(종류·원인)"를 모델 결과로 낸다. 배지 목록은 그대로 만든다(R4).
- **순풍 조건과 필터의 관계.**
  - 상대 순풍은 계산 입력이 아니라 조건 배지 종류 하나다. 순풍 배지는 상대 쪽 순풍을 켠 단독 계산으로 늘 만든다.
  - 조건 필터 4종은 표시 선택이다. 배지 모델 출력을 거를 뿐 다시 계산하지 않는다. 앱 상태의 "상대 순풍" 값은 없앤다.
  - 내 순풍은 기준선·최소 S의 계산 입력으로 남는다. 공격·방어 탭은 이미 순풍 없음으로 계산하므로 내 순풍은 실행기 세대 입력에서 빠진다.
- **축 범위 입력은 두지 않는다.** 초안은 연속 축을 전제로 내 S0 하락 ~ S32 상승 실수치를 모델에 함께 내려 했다. 결정 1(사다리 배치)은 실수치 줄만 쌓고 도달 범위를 그리지 않으므로 이 입력이 필요 없어 뺐다. PRD R2의 "어떤 배지도 잘리지 않음"은 줄 구성이 만족한다.
- **하위 — 걷어낼 스피드 탭 상태.**
  - 스피드 탭 카드 계획·행 작업·조립 분기, 결과 패널의 스피드 분기, 스피드 탭의 배분 선택·직접 추가·핀 UI를 지운다.
  - 상태의 직접 추가 배분·핀은 탭 필드를 가진 채 남는다(공격·방어용). 스피드 탭 값을 만드는 경로는 없어지고, 남은 값이 있어도 무시된다(R12 "오류 없음").
  - 상대 순풍 상태와 그 액션을 지운다.
- **하위 — R15 추가 배분 상태의 위치.** 앱 상태에 스피드 차트 전용 "추가 배분" 목록을 새로 둔다.
  - 항목 = (래더 상대 id, S SP, 성격 부호), 메모리에만 둔다. 계산 세대를 올리지 않고 배지 모델의 입력으로만 쓴다.
  - "목록 묶음 / 직접 입력" 구분과 "이미 있음" 중복 판정은 상태에 저장하지 않고 배지 모델 기준으로 정한다. 단계 분담 등 세부는 구현 설계에서 정한다.
- **조건 필터 상태.** 앱 상태에 4개 켜짐 값으로 두고 탭 이동에도 유지한다. 새로고침하면 기본값(랭크업·스카프·날씨/필드 켜짐, 순풍 꺼짐)이다. 계산 세대를 올리지 않는다.

### 결정 3. 조건 배지 생성 규칙: cards 층 스피드 차트 모듈 한 곳에 두고, 랭크 수단·스카프 규칙은 기존 함수를 공유하며, 날씨 특성 기준은 툴바에 새 값으로 노출한다(사용자 확정 2026-11-15)

- **위치.** 기본 배지 선정(1위 묶음, 동률이면 실수치 높은 쪽), 랭크업·스카프·순풍·날씨/필드 배지 자격, "기본 배지와 실수치가 같으면 만들지 않음", 목록 밖 타겟 규칙을 cards 층 스피드 차트 모듈 한 곳에 둔다. 화면은 결과만 그린다.
- **랭크업.**
  - 래더 상대는 기존 래더 수단 함수(능동 수단, 수단 기준 이상)를, 목록 밖 타겟은 기존 세트 수단 함수를 쓴다. 효과는 기존 수단 적용 함수로 얻는다.
  - S 랭크가 오르는 경우만 남기고, S 랭크 값이 같은 수단은 배지 하나로 합친다. 합친 배지는 수단 목록·수단별 점유율을 근거로 갖는다.
  - 수단 주인은 상대만이다. 내 랭크업은 이번 단위 비목표다. 탭별 수단 주인 표의 스피드 탭 항목은 이 규칙에 맞게 상대만으로 바꾼다.
  - 순풍은 수단이 아니라는 기존 규칙과 동시채용 하한·첫 턴 전용 기술 규칙은 그대로다. 기술 판정이 없는 스피드 차트에는 기술 거름이 걸리지 않는다(INV-261113-rank-active-means-only).
- **스카프.**
  - 스카프 규칙("메가 제외, 기준 이상이면 스카프, 대표 도구가 스카프면 스카프 아닌 최다 도구")을 스피드 카드 빌더에서 꺼내 이 모듈의 함수로 옮긴다. 붙는 자리는 "첫 묶음"에서 "1위 묶음 기본 배지"로 바뀐다.
  - 기준값은 툴바의 기존 "구애스카프" 기준을 그대로 쓴다. 기본값 변경(10%→5%)은 cards 층 표시 기준 기본값 한 곳에서만 한다. 툴바·새로고침 초기값은 그 값을 따른다. 이 기준은 스피드 탭만 쓰므로 공격·방어 탭에 영향이 없다.
- **날씨/필드.**
  - 날씨·필드 ×2 특성과 그 조건(비·쾌청·모래바람·설경·일렉트릭필드)의 표는 코어가 데이터로 공개하고, 이 모듈이 그 표를 읽는다. 특성 목록을 cards 층에 다시 적지 않는다.
  - 지금 표는 술어 함수의 Record라 그대로 공개해서는 "특성 → 조건" 표로 읽을 수 없다. 코어의 표를 "특성 id → 날씨 값 또는 필드 값" 데이터 표로 바꾸고, 기존 판정 술어는 그 표에서 만든다. 계산 결과는 바뀌지 않는다(기존 스피드 단위 테스트로 확인). 코어 변경은 거부 종류 반환에 더해 이 표 형태 변경·공개가 하나 는다.
  - 래더 상대는 특성 분포에서 해당 특성 점유율이 기준 이상이면 배지를 만든다. 목록 밖 타겟은 지정 특성이 해당하면 만든다. 내 특성이 날씨 무효면 날씨 배지만 만들지 않는다(서핑테일은 남는다).
  - **기준값: 툴바 통계 설정에 "날씨 특성" 기준을 새로 두고 기본값 10%로 한다(사용자 확정 2026-11-15).** 툴바는 이미 조건 종류마다 기준 하나를 둔다(SP 배분·랭크업 기술·구애스카프·반감열매·화력 도구).
- **순풍.** 표시 중인 상대의 기본 배지마다 하나를 만든다. 가정 세트 도구가 스카프면 스카프 × 순풍이 함께 반영된 값이다(조건은 하나).
- **도구 근거.** 각 배지는 "계산에 쓴 지닌 도구"와 "도구 효과 무효 여부(무딘손)"를 함께 낸다. 결정 4의 겹침 표시와 상세 안내가 이것을 쓴다.

### 결정 4. 도구 겹침 공용 표시 요소: "포켓몬 이미지 + 도구 겹침" 공용 컴포넌트 하나를 전 탭이 쓰고, 기존 변형 표지 요소는 위치만 옮겨 그 성질을 보존하며, e2e는 직계 자식 셀렉터만 자손 셀렉터로 바꾼다

- **구조.** 포켓몬 이미지 크기와 같은 고정 크기 상자 하나 안에 기존 포켓몬 이미지 요소와 도구 겹침 요소를 둔다. 겹침 요소는 상자 기준 오른쪽 아래에 절대 배치하고, 너비는 이미지 너비 비율(PRD R13 범위)로 정한다. 상자 크기가 이미지와 같으므로 줄 높이가 바뀌지 않는다.
- **입력.** 공용 컴포넌트는 종 id, 크기, 겹칠 도구(없으면 겹침 없음), 겹침의 역할을 받는다. 겹칠 도구는 화면이 정하지 않는다. 그 줄·배지를 만든 계산(공격·방어 계획의 변형 줄 도구·메가스톤, 결정 2·3의 배지 도구)이 정해 넘긴다(R13 "계산이 가정한 도구만").
- **변형 줄 표지 보존.** 공격·방어 탭 반감열매·화력 도구 변형 줄의 겹침 요소는 지금의 변형 표지 요소를 그대로 옮긴 것이다.
  - 접근 이름 "OO 지닌 경우", 도구 이름은 툴팁·읽기 이름에만 두고 점유율은 적지 않는다.
  - 기존 식별 속성(표지 testid, 도구 id 속성, 아이콘 id 속성)을 유지한다.
  - 이름 옆 자리에서는 지운다.
- **메가스톤 겹침은 다른 역할로 구분.** 공격·방어 기본 줄의 메가스톤 겹침은 변형 표지가 아니다. 변형 표지 testid를 쓰지 않고 별도 역할 속성을 단다. 기존 e2e의 "기본 줄에는 변형 표지 없음" 검사가 메가 상대에서도 유효하게 남는다. 접근 이름은 메가 폼 이름이 이미 담고 있으므로 장식으로 두고, 툴팁에만 도구 이름을 둔다. 스피드 차트 배지에서는 배지 접근 이름이 도구를 담는다(결정 6).
- **클릭.** 상자와 겹침은 이름 칸 버튼 안에 있고 자체 상호작용이 없다. 그래서 겹침을 클릭해도 이미지 클릭과 같다(R13).
- **e2e 호환.**
  - 포켓몬 이미지 요소의 testid·종 id 속성·클래스는 유지한다.
  - 이미지가 상자 안으로 한 단계 내려가므로 "이름 칸 직계 자식" 셀렉터는 "이름 칸 안 이미지"로 바꾼다. 다크 테마 받침 검사도 같다.
  - 이 셀렉터 변경을 AC23 매핑에 "구조 변경, 기능 동일"로 적는다.

### 결정 5. 도구 아이콘 자산 확장: 대상 집합은 스냅숏에서 계산하는 단위 검사가 권위이고, 받기 목록은 기존 판 고정 생성 경로를 넓히며, 메가스톤은 자체 제작 공통 메가스톤 표지 하나, 대체 표지는 자체 제작 공통 "도구" 표지 하나다(사용자 확정 2026-11-15)

- **대상 집합 산출과 대조.**
  - cards 층에 R14 합집합(기존 40개, 래더 전 종 가정 세트 도구, 스카프·"스카프 아닌 최다 도구" 후보, 프리셋 3종 도구, 래더 메가 종 메가스톤)을 계산하는 순수 함수를 둔다. 메가스톤 id는 집합에 남되 아래 공통 메가스톤 표지로 덮이는 것으로 판정한다(받기 대상이 아니다). 래더는 번들된 모든 메타 선택(월·매치 방식)이고, 상위 N 상한과 무관하다. 가정 세트·스카프 규칙은 앱이 쓰는 같은 함수를 부른다.
  - 단위 검사가 이 집합의 메가스톤 밖 모든 id에 manifest 항목과 PNG가 있음을, 메가스톤 id는 모두 메가스톤 판정(도구 데이터의 메가스톤 여부)으로 공통 표지에 대응함을 확인한다(AC19). 새 월 데이터가 아이콘 없는 도구를 들이면 이 검사가 실패한다.
  - 생성 스크립트(`scripts/data/lib/images.mjs`의 도구 id 목록)는 지금처럼 정적 목록이다. 검사 실패 때 목록을 넓히고 `gen:images`를 다시 돌린다.
- **출처·판 고정.** 기존과 같은 Bulbagarden Archives "Champions Bag sprites"에서 받는다. MediaWiki imageinfo로 판(올린 시각·sha1)을 manifest에 고정하고, 받은 바이트를 대조한다. README 범위 설명을 갱신한다.
- **라이선스.** 같은 출처라 기존 고지 문구를 유지하되 대상 범위(도구 종류·개수)를 갱신한다. 제3자 고지 산출물이 그 변경을 반영하는지 기존 라이선스 검사로 확인한다.
- **메가스톤: 모든 메가스톤에 공통 메가스톤 아이콘 하나를 쓴다(사용자 확정 2026-11-15, PRD R14 5번).**
  - 그림은 출처에서 받지 않고 자체 제작한다(외부 자산 없는 공통 메가스톤 표지: 둥근 보석 모양, 게임 고유 문양은 베끼지 않음). 출처에 "공통 메가스톤" 스프라이트가 있는지 불확실하고, 대표 메가스톤 한 종의 그림을 쓰면 다른 종 배지에서 툴팁 이름과 그림이 어긋나기 때문이다.
  - 아이콘 상자와 같은 크기·받침을 갖고, 도구 대체 표지(가방 모양)와 모양으로 구분된다. 이미지 요청을 하지 않으므로 오프라인에서도 보인다(AC19).
  - 툴팁·접근 이름(배지 접근 이름의 지닌 도구, 상세의 도구 칸)은 그 배지 계산에 쓴 종별 메가스톤 이름(예: 팬텀나이트)을 그대로 쓴다. 그림만 공통이다. 결정 4의 메가스톤 겹침 별도 역할은 그대로다.
  - 메가스톤은 자체 제작이라 제3자 라이선스 고지 항목이 늘지 않는다.
- **대체 표지 한 가지.**
  - 자체 제작 공통 "도구" 표지(가방 모양, 외부 자산 없음)를 쓴다. 아이콘 상자와 같은 크기·받침을 갖는다.
  - 접근 이름·툴팁에는 도구 이름이 그대로 있다. 이미지 요청을 하지 않으므로 깨진 이미지가 생기지 않는다.
  - 지금의 텍스트 배지 대체는 이것으로 바꾼다.
  - 모양의 세부(가방 실루엣·색)는 공통 메가스톤 표지와 함께 구현 때 정하고 UI 검증(라이트·다크 대비)으로 확인한다. 결정 1 시안은 이 모양을 다루지 않았다.

### 결정 6. 차트 접근성 구조: 의미 구조는 DOM 한 벌(실수치 내림차순 목록)이고 화면은 그 순서대로 흐름 배치한다. 키보드 이동은 순수 탐색 함수로 분리한다

- **의미 구조.**
  - 차트 DOM은 실수치 내림차순의 바깥 목록이다. 각 항목은 실수치 줄 하나이고, 줄 라벨(실수치)과 그 줄 배지들의 안쪽 목록을 갖는다. 안쪽 순서는 R2의 같은 줄 순서다.
  - 기준선은 바깥 목록 안의 구분 항목으로, 실수치 순서의 제자리에 놓인다. 포커스를 받지 않는다. 결정 1의 기준선 띠는 동속 줄과 한 항목이다. 그 항목 안에서 구분 텍스트가 먼저, 동속 배지 목록이 다음에 오므로 읽기 순서는 "구분 → 동속 배지"로 같다.
  - 구분 항목의 읽기 이름은 "내 스피드 N. N과 같으면 동속, 그보다 아래는 추월"이다. 동속 줄이 DOM상 구분 항목 뒤에 오므로 "이 아래는 추월"만 두면 동속 배지를 추월로 읽을 수 있어서다(R5 "동속은 추월 아님"). 배지 접근 이름에도 상태 이름이 들어가 이중으로 막는다.
  - 시각 배치는 결정 1의 사다리라 DOM 순서대로 흐름 배치하고, 위치 값으로 순서를 바꾸지 않는다. 기준선 띠의 고정(sticky)도 DOM 순서를 바꾸지 않는다. 그래서 스크린 리더 읽기 순서와 화면 순서가 늘 같다.
- **배지.** 배지는 버튼이다.
  - 접근 이름에 상대 이름(메가 폼 포함)·배분 표기·조건·실수치·상태·지닌 도구·"추가"/"프리셋 n"을 담는다.
  - 상세와는 확장 상태·제어 관계로 잇는다. 상태 표지는 텍스트로도 있다(색만으로 구분하지 않음).
- **키보드.**
  - 차트는 로빙 탭 인덱스로 탭 순서에서 한 자리만 차지한다.
  - 위아래(이웃 줄의 같은 순번, 없으면 그 줄 마지막)·좌우(같은 줄 이웃)·Home/End(가장 빠른·느린 배지) 이동은 "줄 구조 + 현재 위치 + 키 → 다음 위치" 순수 함수가 정한다. 기준선 항목은 이동 대상 목록에 없다.
  - 추가·삭제 뒤 포커스 대상도 같은 순수 함수 계열이 정한다(세부 규칙은 구현 설계).
- **알림 영역.** 요약("추월 n · 동속 n · 추월당함 n")을 정중한 상태 알림 영역 하나에 둔다. SP 드래그 중에는 갱신하지 않고, 값이 확정(슬라이더 놓기·입력 확정)된 뒤에 갱신한다. 배분 추가·삭제와 필터 변경 뒤에도 갱신한다.
- **층 경계.**
  - 데이터 계약 = 결정 2 배지 모델.
  - 응용 로직 = 결정 3 생성 규칙, 상태·요약, 줄 구성 계산(결정 1의 실수치 줄 목록·윗줄 차이·기준선 띠 줄 위치와 동속 병합), 키보드 탐색 함수. 모두 화면 없이 단위 테스트한다.
  - UI 렌더링 = 목록 DOM·스타일·포커스 적용·상세 표시.

## 선택지

### 선택지 — 결정 1 (화면 배치)

시안 원본: `./design-options.html`. 세 대안은 같은 데이터(내 실수치 138, 상위 30 일부·프리셋 1개, 기본 필터)로 그렸다.

#### 선택지 A: 단일 열 압축 차트 + 팝오버

- 정보 우선순위: 고정 머리(요약·조건 필터) > 기준선 띠 > 배지(이미지·배분 표기) > 상세. 배지 안 이름 텍스트 없음.
- 어포던스: 실수치 1 차이 ≈ 1.1px 비례, 24 넘는 간격은 "빈 구간" 빗금 띠로 압축, 줄 사이 최소 간격 보장. 호버(250ms 지연)·포커스·탭으로 배지 오른쪽 팝오버(공간 없으면 아래), 팝오버는 기준선 반대쪽으로 자란다. 기준선이 화면 밖이면 "내 위치로" 버튼.
- 장점: 간격이 차이 크기를 대략 보여 준다. 폭을 배지에 다 써 같은 줄 줄바꿈이 적다.
- 단점: 팝오버가 이웃 배지를 가린다. 기준선 반대쪽으로 열어도 기준선 옆 줄이나 차트 끝에서는 동속 줄 배지를 가릴 수 있다. 기준선이 스크롤과 함께 사라져 버튼 조작에 의존한다. 비례와 압축 규칙이 섞여 간격 해석이 일정하지 않다. 400px에서 팝오버가 폭 전체로 바뀌어 형태가 두 가지다.

#### 선택지 B: 2단 차트 + 고정 상세 패널

- 정보 우선순위: 차트와 상세·요약을 동시에 본다. 상세가 오른쪽 고정 패널이라 배지를 옮겨 가며 비교해도 사라지지 않는다.
- 어포던스: 완전 비례 축(1 차이 ≈ 0.9px), 차트만 내부 스크롤. "내 순풍"·SP를 바꾸면 기준선으로 자동 스크롤, 직접 스크롤해 벗어나면 "내 위치로". 순서 비교 불가는 패널 아래. 400px에서는 패널이 처음엔 닫힌 아래쪽 시트(화면 절반 이하)가 된다.
- 장점: 간격이 그대로 차이 크기다. 상세가 차트를 가리지 않고 비교가 쉽다(데스크톱).
- 단점: 비례 축이라 차트가 길어진다. 차트 폭이 줄어 같은 실수치 줄이 빨리 줄바꿈된다. 상세 형태가 데스크톱 패널·모바일 시트 두 벌이다. 자동 스크롤이 사용자의 스크롤 위치를 빼앗는다. 시트가 400px 화면 절반을 덮는다.

#### 선택지 C: 실수치 사다리 + 따라오는 기준선 띠 (채택, 사용자 선택 2026-11-15)

- 정보 우선순위: 순서 > 간격. 실수치마다 같은 높이 한 줄, 간격은 "윗줄과 차이" 숫자로 대신한다. 줄 폭 여유로 배지 안에 이름 텍스트를 둔다(400px은 뺌).
- 어포던스: 기준선 띠 = 내 줄(동속 배지 포함)이며 요약을 품고 차트 프레임 위·아래 끝에 붙어 늘 보인다. 배지를 가리키거나 누르면 그 줄 바로 아래에 상세가 펼쳐진다. 팝오버·시트가 없어 400px도 같은 구조다.
- 장점: 기준선·요약이 늘 보여 "내 위치로"·자동 스크롤이 필요 없다. 이웃 줄이 1 차이여도 겹치지 않는다. 상세가 아무것도 가리지 않는다. 데스크톱·400px이 한 구조라 구현·e2e가 한 벌이다. 화면 순서가 DOM 순서와 같아 결정 6과 바로 맞는다.
- 단점: 비례가 없어 "아슬아슬 / 크게 차이"를 숫자로만 읽는다. 호버로 펼치면 아래 줄이 밀린다(지연과 "떠나도 닫지 않음"으로 완화). 내 실수치에 배지가 없으면 SP 변경 때 띠 줄이 끼거나 빠져 아래 줄이 한 줄 밀린다. 동속 배지가 많으면 띠가 높아져 프레임을 더 차지한다.

### 선택지 — 결정 2 (데이터 모델과 계산 경로)

#### 선택지 A: 행 스윕 모델 유지, 표시만 차트로

- 장점: 계획·행 작업·실행기·캐시·acceptance 테스트를 그대로 둔다. 행에 이미 내·상대 실수치가 있다.
- 단점:
  - 카드 단위가 "상대 × 5% 이상 전 묶음"이고 조건이 카드 안 행이다. 1위 묶음·조건 배지·추가 배지 규칙을 맞추려면 계획을 크게 고쳐야 한다.
  - 내 SP 0~32 스윕은 차트에 쓰지 않는 계산이다.
  - 실행기 시간 조각 때문에 배지가 순차로 채워져, 표시 중 위치 변동(AC25) 방지에 갱신 중 처리가 필요하다.
  - 상대 순풍이 계산 입력이라 필터를 바꿀 때마다 세대가 오른다.
  - 날씨를 상대에게만 거는 입력은 순서 비교 경로가 양쪽 세트로 무효를 판정해서 맞지 않는다.

#### 선택지 B: 배지 단위 모델, cards 층 동기 순수 계산 (채택)

- 장점:
  - PRD 모델(배지 = 상대·묶음·조건)과 1:1이다.
  - 배지 목록이 내 SP와 무관해 슬라이더 중 배지가 움직이지 않는다(AC25를 구조로 만족).
  - 계산량이 작다. 상위 30 × (기본 + 조건 몇 개)의 단독 스피드 계산이라 시간 조각이 필요 없다.
  - 단독 계산으로 상대 단독 날씨가 자연스럽게 표현된다.
  - 필터가 재계산 없는 표시 선택이 된다.
- 단점:
  - 스피드 탭 계획·행 작업·조립 경로와 그 테스트를 지운다(AC23 매핑 비용).
  - 실행기의 탭 목록이 바뀐다.
  - 동기 계산이 예산을 넘으면 분할로 바꿔야 한다(측정으로 확인).

#### 선택지 C: 배지 단위 모델을 실행기 작업으로 비동기 계산

- 장점: 공격·방어와 같은 실행 경로·진행률을 공유한다.
- 단점: 작은 계산에 시간 조각·세대·캐시 기계를 얹는다. 순차 채움 때문에 깜박임 방지 처리가 다시 필요하다.

#### 하위 — R15 추가 배분 상태

- **기존 직접 추가 배분 재사용(탭 = 스피드):** 상태 필드가 늘지 않는다. 대신 "추가는 곧 고정" 모델·세대 증가·계획의 사용자 묶음 검증이 함께 따라오고, 성격 부호를 담지 않아 스피드 배분(SP, 성격)을 표현하지 못한다.
- **스피드 차트 전용 새 목록 (채택):** 격리(R15·AC16)와 성격 부호 표현이 자연스럽고, 세대를 올리지 않는다. 상태 필드 하나와 액션 둘이 는다.

### 선택지 — 결정 3 (생성 규칙의 위치와 임계값)

#### 위치 A: cards 층 스피드 차트 모듈 한 곳 + 기존 수단·스카프 함수 공유 (채택)

- 장점: 단위 테스트 한 곳에서 R7 전체를 재현한다. 랭크 수단 불변식 코드 경로를 그대로 탄다.
- 단점: 스카프 규칙을 스피드 카드 빌더에서 옮기는 이동 비용이 있다.

#### 위치 B: 화면 컴포넌트에서 조건 배지 조합

- 장점: 초기 구현이 빠르다.
- 단점: 화면 없는 재현(비기능 검증 가능성)을 깬다. 배수를 화면이 곱할 유혹이 생긴다(R7 위반 위험).

#### 날씨 기준 A: 랭크업 기술 기준값 재사용

- 장점: 새 설정이 없다. PRD 열린 질문 3의 기본값과 같은 10%다.
- 단점: 툴바 라벨 "랭크업 기술"이 날씨 특성까지 바꾼다는 사실이 보이지 않는다. 두 개념이 묶인다.

#### 날씨 기준 B: 고정 상수 10%, 노출 안 함

- 장점: UI 변경이 없다.
- 단점: 다른 조건 종류는 모두 툴바로 조절하는데 날씨만 못 바꾼다. 일관성이 떨어진다.

#### 날씨 기준 C: 툴바에 "날씨 특성" 기준 신설, 기본 10% (채택, 사용자 확정 2026-11-15)

- 장점: 조건 종류마다 기준 하나라는 기존 툴바 패턴과 같다. 개념이 분리된다.
- 단점: 툴바 필드·상태 검증·e2e가 하나씩 는다.

### 선택지 — 결정 4 (도구 겹침 공용 요소)

#### 선택지 A: 이미지 상자 공용 컴포넌트 + 기존 표지 이동, e2e 셀렉터를 자손으로 (채택)

- 장점: 카드 간단행·상세, 차트 배지, 순서 비교 불가 영역이 같은 요소를 쓴다. 겹침 위치·크기·대비를 한 곳에서 지킨다. 기존 식별 속성·접근 이름이 보존된다.
- 단점: 이미지가 한 단계 내려가 직계 자식 셀렉터 몇 개를 바꿔야 한다(AC23 매핑).

#### 선택지 B: 래퍼 없이 이름 칸 안에서 겹침을 이미지 형제로 절대 배치

- 장점: 이미지 직계 자식 구조와 셀렉터가 그대로다.
- 단점: 위치 기준이 이름 칸 레이아웃에 묶인다. 카드·배지·불가 영역마다 따로 맞춰야 해서 공용 단위가 되지 않는다. 레이아웃이 바뀌면 겹침이 어긋난다.

#### 선택지 C: 도구를 합성한 단일 이미지(캔버스·사전 합성)

- 장점: DOM 구조가 그대로다.
- 단점: 툴팁·접근 이름·식별 속성을 둘 요소가 없다. 종 × 도구 조합이 폭발한다. 오프라인 자산이 커진다.

### 선택지 — 결정 5 (아이콘 자산)

#### 집합 산출 A: 스냅숏 계산 단위 검사 + 정적 받기 목록 (채택)

- 장점: 기존 패턴(정적 목록 + 동기화 검사)과 같다. 데이터가 늘면 검사가 알려 준다. 스크립트가 cards 로직을 중복하지 않는다.
- 단점: 검사 실패 때 목록 갱신과 생성 재실행이 수동이다.

#### 집합 산출 B: 생성 스크립트가 직접 집합 계산

- 장점: 목록 수동 갱신이 없다.
- 단점: 스크립트(mjs)가 가정 세트·스카프 규칙을 다시 구현하거나 TS 계획 로직에 의존해야 한다. 규칙이 두 곳에 생긴다.

#### 메가스톤 A: 종별 아이콘 (기각)

- 장점: 게임 화면과 같다. 계산에 실제 쓴 도구와 그림이 일치한다.
- 단점: 래더 메가 종 수만큼 자산·고지 항목이 늘고, 새 메가 종이 들어올 때마다 받기 목록을 넓혀야 한다. 출처에 없는 메가스톤은 결국 대체 표지로 섞여 표시가 일정하지 않다.

#### 메가스톤 B: 공통 메가스톤 아이콘 하나 (채택, 사용자 확정 2026-11-15)

- 장점: 그림 하나라 자산이 단순하고 데이터 갱신에 영향을 받지 않는다. 메가 배지가 한눈에 같은 표시로 보인다.
- 단점: 그림이 종별 메가스톤을 구분하지 않는다(이름은 툴팁·읽기 이름으로만). 출처에 공통 스프라이트가 있는지 불확실하다 → 자체 제작 표지로 해결한다(결정 5 본문).

#### 대체 표지 A: 자체 제작 공통 "도구" 표지 (채택, 사용자 확정 2026-11-15)

- 장점: 라이선스가 필요 없다. 언어와 무관하다. 크기·받침이 실제 아이콘과 같아 배치가 흔들리지 않는다.
- 단점: 도구마다 구분되지 않는다(이름은 툴팁·읽기 이름으로만).

#### 대체 표지 B: 도구 이름 첫 글자 텍스트

- 장점: 약간의 구분 정보가 있다.
- 단점: 한국어 첫 글자는 겹침 크기(이미지의 0.35~0.45배)에서 읽기 어렵다. 겹치는 글자(예: "구")가 많아 오인을 부른다.

### 선택지 — 결정 6 (접근성 구조)

#### 선택지 A: DOM 한 벌(내림차순 목록) + 흐름 배치 + 순수 탐색 함수 (채택)

- 장점: 읽기 순서와 화면 순서가 구조적으로 같다. 중복 구조가 없어 어긋날 수 없다. 탐색 규칙을 단위 테스트한다.
- 단점: 시각 배치가 DOM 순서를 바꾸지 못한다. 결정 1(C)은 흐름 배치라 이 제약이 부담이 되지 않는다.

#### 선택지 B: 시각 차트(SVG 등)는 숨기고 별도 숨김 목록을 접근성용으로

- 장점: 시각 배치 자유도가 크다.
- 단점: 두 구조가 어긋날 위험이 있다. 포커스 링이 화면 배지와 따로 논다. 상세 연결이 이중이 된다.

#### 선택지 C: 격자 역할(행 = 실수치 줄, 칸 = 배지)

- 장점: 화살표 이동 의미가 내장된다.
- 단점: PRD가 요구한 "목록" 읽기와 다르다. 포커스 불가 기준선 줄을 격자 안에 두기 어색하다. 열 수가 줄마다 달라 격자 의미가 약하다.

## 선택 근거

- **결정 1**
  - 사용자가 시안 세 개 중 C를 골랐다(2026-11-15, 세부 수정 요구 없음).
  - PRD의 핵심 질문은 "어디까지 추월하는가, S를 몇 더 주면 다음 상대를 넘는가"다. 이것은 순서와 차이 숫자로 답할 수 있고, 차이를 화면 간격으로 보이는 것은 부차적이다. C는 순서를 우선하고 차이를 숫자로 적어 이 질문에 바로 답한다.
  - 기준선과 요약이 늘 보여야 한다는 R2·R5·AC24를 C는 고정 띠 하나로 구조적으로 만족한다. A·B는 "내 위치로" 버튼이나 자동 스크롤이라는 보조 장치가 필요하다.
  - 1~2 차이 이웃 줄 겹침 금지(R2·AC2)를 C는 같은 높이 줄로 바로 만족한다. A·B는 비례와 최소 간격이 충돌하는 지점을 따로 처리해야 한다.
  - 상세가 아무것도 가리지 않고 데스크톱·400px이 같은 구조라, 화면 형태 두 벌(A의 팝오버 변형, B의 패널·시트)을 만들고 검증하는 비용이 없다. DOM 순서 = 화면 순서라 결정 6의 한 벌 구조와 그대로 맞는다.
  - A 기각: 팝오버가 이웃·동속 줄 배지를 가릴 수 있고, 기준선이 스크롤로 사라지며, 비례와 압축이 섞여 간격 해석이 일정하지 않다.
  - B 기각: 완전 비례라 차트가 길어지고 폭이 좁아 줄바꿈이 잦다. 상세가 두 벌이고, 400px 시트가 화면 절반을 덮으며, 자동 스크롤이 사용자 스크롤을 빼앗는다.
- **결정 2**
  - PRD가 카드 단위·조건 범위·필터·추가 배분을 모두 배지 단위로 다시 정의했다. 행 스윕(A)을 지키면 표시와 계산 단위가 어긋나 계획을 사실상 다시 쓰게 되면서 쓰지 않는 스윕만 남는다.
  - 배지 목록이 내 SP와 무관하다는 성질이 깜박임 없음과 성능을 함께 해결해 B를 택했다. C는 그 성질을 비동기 기계로 다시 잃어 기각했다.
  - 상대 단독 날씨는 코어의 단독 계산과 공개된 무효 특성 목록으로 충분하다. 공통 날씨 입력을 한쪽에만 거는 새 코어 입력을 만들지 않는다. 앱 공식(INV-261105)과 대미지 날씨 규칙(INV-261115)을 건드리지 않는 가장 좁은 경로다.
  - 거부 목록을 코어 한 곳에 두려고, cards 층이 id 목록을 복제하지 않고 코어가 거부 종류를 돌려주게 한다.
  - 추가 배분을 새 목록으로 둔 이유: 기존 직접 추가는 "추가 = 고정 + 세대 증가" 모델이고 성격 부호가 없다. 스피드 차트 요구(성격 포함, 세대 무관, 공격·방어와 격리)와 맞지 않는다.
- **결정 3**
  - R7 전체를 화면 없이 재현하라는 검증 요구 때문에 생성 규칙은 cards 층 한 곳이어야 한다.
  - 랭크 수단·스카프는 이미 검증된 규칙이라 다시 쓰지 않고 공유한다.
  - 날씨 기준은 툴바의 "조건 종류마다 기준 하나" 패턴을 따르는 C로 정했다(사용자 확정 2026-11-15). A는 라벨과 의미가 어긋나고, B는 일관성이 깨진다. 툴바가 한 칸 늘어나는 비용은 감수한다.
- **결정 4**
  - R13이 "같은 표시 단위를 전 탭이 공유"를 요구하고 위치·크기·대비 수치 기준을 둔다. 한 곳에서 지키는 A가 유일하게 공용 단위가 된다.
  - 셀렉터 변경은 기능 동등한 구조 변경이라 매핑으로 처리할 수 있다. B·C는 공용성이나 접근 이름을 잃어 기각했다.
  - 메가스톤을 별도 역할로 둔 것은 기존 "기본 줄에는 변형 표지 없음" 계약과 접근 이름 "OO 지닌 경우"의 의미(변형 줄 전용)를 지키기 위해서다.
- **결정 5**
  - 집합은 데이터와 함께 변하므로 데이터에서 계산해 검사하는 것이 AC19의 판정과 같다. 규칙 중복을 피하려 계산은 cards 층에 두고 스크립트는 받기만 한다.
  - 메가스톤은 권고였던 종별(A) 대신 사용자가 공통 아이콘 하나(B)를 골랐다(2026-11-15). A는 사용자 선택에서 빠졌고, 메가 종 수만큼 자산·고지·받기 목록이 늘어 자산 관리가 복잡해진다. B는 그림 하나로 단순하다.
  - 공통 그림을 출처에서 찾지 않고 자체 제작하는 이유: 출처의 공통 스프라이트 존재가 불확실하고, 대표 메가스톤 한 종을 공통 그림으로 쓰면 다른 종 배지에서 그림과 툴팁 이름이 어긋난다. 자체 제작이면 라이선스 항목도 늘지 않는다. 종별 구분은 툴팁·접근 이름의 종별 메가스톤 이름으로 지킨다.
  - 대체 표지는 라이선스·가독성 면에서 A가 낫다(사용자 확정 2026-11-15).
- **결정 6**
  - PRD가 읽기 구조(목록)·이동 규칙·알림을 구체로 요구했다. 시각과 의미를 두 벌로 두면 어긋남을 테스트로 다 막기 어렵다. 한 벌의 DOM을 그 순서대로 흐름 배치하는 A가 구조적으로 안전하다.
  - B 기각: 시각 구조와 숨김 목록 두 벌이 어긋날 수 있고 포커스 링과 상세 연결이 이중이 된다.
  - C 기각: PRD가 요구한 읽기 구조는 목록이고, 줄마다 열 수가 달라 격자 의미가 약하며, 포커스 불가 기준선을 격자 안에 두기 어색하다.
  - 탐색을 순수 함수로 빼면 줄 순서·빈 줄·기준선 건너뛰기 규칙을 화면 없이 검증할 수 있다.

## 결과

### 긍정적 영향

- 스피드 탭이 실행기·행 스윕에서 빠져 계산량이 줄고, SP 슬라이더 중 배지 위치가 구조적으로 고정된다.
- 조건 배지·최소 S·거부 처리가 전부 화면 없는 단위 테스트로 재현된다.
- 앱 공식·대미지 날씨 규칙·랭크 수단 규칙이 바뀌지 않는다. 코어에는 거부 종류 반환과 날씨 특성 표의 데이터 형태 변경·공개만 더한다.
- 전 탭 도구 표시가 공용 요소 하나로 모여 위치·크기·대비를 한 곳에서 지킨다.
- 아이콘 대상 집합이 데이터 갱신에 따라 자동으로 검사된다.

### 부정적 영향 / 트레이드오프

- 스피드 탭 계획·행 작업·조립·결과 패널 분기와 그 단위·e2e 테스트를 지우거나 바꾼다. 범위가 크다(notes 코드 제약 18·19의 목록, AC23 매핑).
- 실행기의 탭 집합이 공격·방어로 줄어 실행기 테스트·진행률 표시 가정이 바뀐다.
- 내 순풍이 세대 입력에서 빠지고 상대 순풍 상태가 없어진다. 순풍 토글 기반 e2e(`e2e/product-berry.spec.ts` 등)를 다시 쓴다.
- 스카프 기준 기본값 5%로 10%를 전제한 테스트가 바뀐다.
- 도구 겹침 구조 변경으로 이미지 직계 자식 셀렉터 e2e를 바꾼다.
- 추가 도구(가정 세트·스카프 후보·프리셋 도구)로 오프라인 자산과 고지 항목이 는다. 메가스톤은 자체 제작 공통 표지 하나라 자산·고지가 늘지 않는 대신, 그림으로는 종별 메가스톤을 구분하지 못한다.
- 스피드 차트가 비례 축이 아니라 실수치 차이를 숫자로만 읽는다. 펼친 상세와 기준선 띠 줄의 끼고 빠짐이 아래 줄을 밀 수 있다.
- 동기 배지 계산이 상위 30·조건 전부 켬에서 예산을 넘으면 분할이 필요하다(측정 전 미확인).
- 방어 탭 "확실히 빠름"과 스피드 차트는 날씨 가정이 다르다(공격측 유도 vs 파트너 날씨 가정). 의도된 차이지만 사용자가 두 값을 비교하면 다르게 보일 수 있다.

## 검증

- [ ] **계산 일관성**: 배지·기준선 실수치가 코어 단독 계산 결과와 같고, 스카프×순풍·+1×스카프·날씨×스카프·홀수 반올림·무딘손 경계를 단위 테스트로 고정한다(AC12).
- [ ] **상대 단독 날씨**: 날씨 배지가 상대에게만 날씨를 넣은 값이고, 기준선이 날씨 없음이며, 내 구름보기·에어록이면 날씨 배지가 없고 서핑테일은 남음을 단위 테스트로 확인한다(AC6·AC9·AC10).
- [ ] **최소 S**: 엄격 추월·동속 제외·불가·예산 초과 사례와, AC7b 기대값 표 중 추월 목표 사례의 일치를 단위 테스트로 확인한다. "규칙 변경으로 결과 다름" 사례는 새 결과를 따로 기대값으로 고정한다.
- [ ] **거부**: 상대 기본·조건 거부와 내 세트 거부(종류·원인)가 모델 결과로 나오는지 단위 테스트로, 화면 안내는 e2e로 확인한다(AC5b·AC13).
- [ ] **생성 규칙**: R7 전 항목을 cards 층 스피드 차트 모듈 단위 테스트로 재현한다(AC9). 스카프 기준 기본값 5%는 새로고침 e2e로 확인한다(AC11).
- [ ] **상태 격리**: 스피드 추가 배분·조건 필터가 세대를 올리지 않고, 공격·방어 직접 추가·핀과 서로 영향이 없음을 리듀서 단위 테스트와 e2e로 확인한다(AC16·AC26).
- [ ] **깜박임·성능**: SP 연속 변경 중 배지 좌표 프레임 기록(AC25)과, 상위 30·조건 전부 켬 기준 처음 열기·SP 놓기 각 10회 측정(AC21)을 notes에 기록한다. 통과 조건: 첫 표시 중앙값 ≤ 500ms, 전체 완료 중앙값 ≤ 3초, 계산 구간 최대 Long Task ≤ 100ms, 자기 실수치 줄이 아닌 줄에 배지가 놓인 프레임 0개.
