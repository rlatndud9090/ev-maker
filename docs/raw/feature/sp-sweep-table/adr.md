# ADR: SP 구간 판정 표 화면(메타 카드 리스트)

## 컨텍스트

- PRD 요구: 내 포켓몬 하나를 설정하면 공격·방어·스피드 탭마다 메타 포켓몬과의 판정을 사용률 순 카드로 보인다. 카드 = 상대 × 판정 관여 능력치 묶음 × 분류이고, 판정 행마다 현재 판정·경계 SP·예산 밖 필요 SP를 보인다. 방어 탭 극단 사전 필터, 변화 없음 제외 요약, 통계 기반 랭크 변화 행, 스카프 행, 목록 밖 커스텀 프리셋, 순풍 토글, 표시 기준 설정이 있다. 같은 입력이면 화면 없이 같은 카드 목록이 재현돼야 하고, 화면은 판정을 직접 계산하지 않는다.
- 현재 코드/데이터 제약
  - 계산 코어(`src/core`)는 스냅샷을 인자로 받는 동기 순수 함수다. `validateSet`이 SP 합계 상한 초과를 `SP_TOTAL_EXCEEDED`로 거부하고, 스윕은 예산 밖 칸을 판정하지 않는다. 그래서 PRD의 예산 밖 칸 판정과 극단 필터(H32·B32, 예산 무시)를 지금 코어로는 계산할 수 없다.
  - `sweepDamage`의 허용 능력치는 공격측 A/C, 방어측 H/B/D로 고정이다. 바디프레스(내 B 참조)를 공격측으로 스윕할 수 없다.
  - 스냅샷 기술 항목에는 참조 능력치 정보가 없다. 엔진은 방어 쪽 참조를 기술 데이터 필드(`overrideDefensiveStat`, 사이코쇼크)로, 공격 쪽 참조를 기술 이름 분기(속임수·바디프레스)로 정한다(notes 실측).
  - 엔진과 코어는 위협·오기 같은 랭크 변화를 스스로 적용하지 않는다(notes 실측). 랭크는 세트의 `boosts`로만 들어간다.
  - 메타 계약(`src/meta`)은 보존 배분(종당 최대 30)과 관측 배분 가정, 목록 밖 종의 커스텀 출처 가정 경로를 이미 준다.
  - 화면은 `src/main.tsx`가 개발 확인 페이지를 그대로 렌더하는 구조다. 라우팅·상태 라이브러리가 없고, 런타임 의존성은 `@smogon/calc`·react·react-dom이다.
- 사용자 경험 제약: PRD 비기능 반응성 정의(세 탭 × 처음 열기·주 능력치 SP ±4 놓기, 첫 카드·전체 완료 10회 중앙값 ≤ 500ms·≤ 3초, 10회 모두 최대 Long Task ≤ 100ms)를 따른다. 폭 400px·1280px 반응형, 키보드 조작.
- 검증 제약: 정적 빌드·오프라인 e2e(외부 요청 0건)가 유지돼야 하고, 기존 dev 확인 페이지 스펙과 `window.__perf` 성능 훅이 계속 돌아야 한다.

## 결정

### 결정 1. 화면 배치와 카드 구성

사용자가 세 단계로 나눠 고른 배치를 채택한다(비교: [전체 레이아웃](./design-layout.html) · [설정 영역](./design-settings.html) · [상대 목록](./design-opponents.html); 첫 통합 비교 [design-options.html](./design-options.html)은 세 단계 분할 전 이력).

- **전체 레이아웃 (layout A): 좌 고정 사이드바 + 우 결과.**
  - 넓은 화면: 작업 영역(설정 사이드바 + 결과 열)은 뷰포트 높이(100dvh)에 맞춰 첫 화면을 채운다. 문서 세로 스크롤은 그 아래 페이지 푸터(데이터 출처·라이선스, 경계선으로 구분)에 닿을 때만 생긴다(사용자 피드백 2026-11-10). 왼쪽 설정 사이드바는 자체 스크롤이다. 오른쪽 결과 상단의 탭(공격/방어/스피드)·툴바(상위 N·포켓몬 선택·내 순풍/상대 순풍·표시 기준·메타 출처와 매치 방식/월)·추가 패널은 스크롤 박스 밖에 있어 항상 보이고(sticky 불필요), 그 아래 상대 목록은 남은 높이를 채우는 자체 스크롤 박스다(사용자 피드백 2026-11-10). 박스 안에서는 진행 줄이 위에 붙고, 카드 목록이 스크롤된다(변화 없음 요약은 화면에 두지 않는다 — 사용자 피드백 2026-11-10)(라이선스 고지는 박스 밖 페이지 푸터). 박스는 테두리·배경·안쪽 여백·가장자리 스크롤 그림자로 구분한다. 넓은 모니터에서 줄이 너무 길어지지 않게 작업 영역·페이지 푸터 폭은 최대 76rem으로 제한하고 가운데 정렬한다(사용자 피드백 2026-11-10).
  - 좁은 화면(400px): 설정(접기 가능, 접으면 내 포켓몬 요약 한 줄) → 탭·툴바(탭 줄만 sticky) → 상대 목록 스크롤 박스 순으로 위아래로 쌓인다. 상대 목록은 뷰포트 높이에 맞춘 자체 스크롤 박스(사용자 피드백 2026-11-10)로, 높이는 화면 높이에서 탭 줄을 뺀 값(최소 60dvh)이다. 페이지 스크롤과 공존하며 박스 끝에 닿으면 페이지 스크롤로 이어진다.
- **내 포켓몬 설정 영역 (settings C): SP 슬라이더 중심.**
  - 패널의 대부분을 능력치 6줄의 SP 슬라이더(+/− 미세 조정, 숫자 직접 입력, 잔여 예산, 큰 실능치 숫자, 성격 ↑↓ 표시)에 준다. 종·특성·도구는 위쪽에 2열 칩으로 압축하고, 칩을 누르면 그 자리에서 편집한다. 기술은 '기술' 라벨 하나 아래 4칸을 1열로 쌓고(칸별 접근 이름 "기술 1~4"는 유지), 칸마다 해석된 기술의 타입 아이콘과 타입색 테두리·연한 타입색 배경을 준다(비었거나 해석되지 않으면 기본 스타일, 사용자 피드백 2026-11-10). 종 칸은 라벨 없이 검색 입력만 보이고(접근성 이름 유지), 메가는 별도 체크박스 없이 메가 폼 이름으로 고르며 그때 도구 칸은 메가스톤으로 잠긴다. 도구 수동 후보에서 메가스톤은 뺀다(사용자 피드백 2026-11-10). 성격은 콤보박스 없이 H를 뺀 능력치 줄의 숫자 입력 옆 상승(+)·하락(−) 토글로 고른다. +·−는 각각 한 줄에만 켜지고 같은 줄에 함께 켤 수 없다. −는 고르지 않아도 되며, 그때는 덜 쓰이는 능력치로 자동 지정한다(+A↔−C, 그 밖은 내 기술이 특수만이면 −A 아니면 −C, 기술이 바뀌면 다시 정함). 자동 −는 흐린 점선으로 보이고 눌러서 직접 지정할 수 있다(사용자 피드백 2026-11-10).
  - 규칙 위반은 원인 칸 옆에 한국어로 보인다. 내 랭크 변화 수단(예: 칼춤)은 기술 칩에 표시하고 "공격 탭 +2 행 추가"를 짧게 알린다.
  - 슬라이더를 끄는 동안에는 재계산 없이 즉시 갱신한다. 드래그 중인 능력치의 행은 이미 계산된 0~32 칸에서 현재 칸·판정·경계 증감을 다시 읽고, 모든 행은 n·예산 밖 표시를 다시 계산한다. 다른 능력치 고정값이 바뀌어 낡은 행은 "갱신 대기"로 두고(칸·경계는 갱신하지 않음) 놓을 때 결정 3의 실행기로 재계산한다(아래 슬라이더 드래그 계약). 슬라이더 위 경계 눈금 표시는 이 단위에서 하지 않는다.
- **상대 포켓몬 목록 영역 (opponents D 변형): 압축 목록 + 아래로 펼치는 아코디언 상세.**
  - 목록은 카드당 한 줄로 포켓몬·결과 배지·배분 라벨과, 대표 판정 행 하나(기술 라벨)·"외 k행"만 보인다(사용자 결정: 접힌 줄은 항목당 대표 1줄). 간단행은 표처럼 열을 맞춘다: 포켓몬 | SP 배분 라벨 | 기술 라벨 | 결과 배지 | "외 k행"(오른쪽 끝). 모든 카드가 같은 열 폭을 쓰고, 좁은 화면(44rem 이하)에서는 [포켓몬·결과·외 k행] / [배분·기술] 2줄로 바뀐다(사용자 피드백 2026-11-10·11). 최소 필요 목표 문구는 간단행에서 뺐고 펼친 상세 행에만 있다(사용자 피드백 2026-11-11, 이전: 기술 라벨과 결과 배지 사이 "최소 필요 문구" 열, 좁은 화면 3줄째).
  - 판정 기준 입력(사용자 피드백 2026-11-11, 같은 날 2차 개정): 목록 위 툴바에 "고난수 기준" n 하나를 둔다. 공격 탭 라벨 "고난수 1타 기준 [n]/16 (xx.x%)", 방어 탭 라벨 "고난수 견딤 기준 [n]/16 (xx.x%)"(같은 값, 입력 옆 보조 문구 공격 "16번 중 n번 이상 1타 = 고난수1타"·방어 "16번 중 n번 이상 버팀 = 저난수1타" — 단위·백분율과 함께 입력의 접근 가능한 설명), 스피드 탭 없음. n은 1~15 정수만 리듀서에 반영하고(그 밖 입력은 반영하지 않고 칸 옆 안내), 백분율은 반영된 값이다. 기본 14. 값은 앱 상태 `rollSteps`에 두고 카드 모델 입력 `rollSteps`로 계산 전체에 넘긴다(결정 2·3). 2차 개정 이전: 공격 "고난수 기준"·방어 "저난수 기준" 두 값(`thresholds`, 기본 14/16·2/16).
  - 카드 줄 표기(사용자 피드백 2026-11-10, 이전: "#2 42.25% · 포켓몬 · A32↑ · 56.3% · 보존 80% · ◎ 상대 칼춤 A+2 아이언헤드 H12까지 줄여도 확정 버팀(−4)"):
    - 사용률 순위·사용률은 간단행·상세 모두에서 뺀다. 정렬은 그대로 사용률 순이고, 순위는 카드 DOM `data-rank`로만 싣는다(테스트용). 목록 밖 포켓몬 추가 목록에 순위·사용률을 붙이는 것은 다음 단위.
    - 배분 라벨: 묶음 관련 SP와 점유율을 한 라벨로 묶는다("A32↑ 56.3%", 점유율은 작은 회색 글씨). 보존률은 화면에서 뺀다(모델에는 남김). 소수 배분은 "소수 배분", 커스텀은 "프리셋 n"이 같은 자리에 작게 붙는다.
    - 판정 기호(◎△×)는 간단행에서 뺀다. 결과 배지가 대신한다. 결과 배지가 없는 스피드 탭은 같은 자리에 행동 순서 배지("선공"·"동속"·"후공")를 둔다. 상세 행의 기호·텍스트 라벨은 그대로이고, 상세 판정 줄의 현재 판정은 목표 문구와 같은 5단 단계명으로 쓴다. 상세의 0~32 띠 칸·범례·현재 판정 칩은 결과 배지와 같은 5색(확정1타 빨강 … 확정견딤 초록, 스피드는 선공 초록·동속 노랑·후공 빨강)이고 기호는 그 탭 관점 좋음 → 나쁨 ◎○△▽×(스피드 ◎△×)다(사용자 피드백 2026-11-11 2차, 이전: 탭 관점 좋음/중간/나쁨 3색·◎△×).
    - 기술 라벨: [타입 아이콘][랭크][기술명] 순서의 한 라벨이고 내 기술 칸처럼 타입색 테두리·연한 타입색 배경이다(`TypeIcon` 재사용). 랭크가 그 기술 사용자(공격·스피드 탭은 나, 방어 탭은 상대)의 공격 능력치(행 `refs.offense`, 사용자 쪽일 때만) 랭크면 부호만("+2 아이언헤드"), 그 밖의 랭크는 같은 라벨 안에 작은 회색 "내 B+2"·"상대 S−1"로 붙인다. 이전 근거 태그("상대 칼춤 A+2")는 이 라벨로 대체했고, 수단 이름·점유율은 상세 행 근거에 남는다. 스카프 행은 라벨 앞에 "구애스카프"류 작은 태그를 유지한다.
    - 목표 문구: "~까지 줄여도"·"~부터" 경계 문구 대신 행 `target`(결정 2)을 성격 보정 2종으로 "<판정>: 최소 A32 / A15+"(무보정 최소 / 상승 최소, 상승 대상 능력치 약자 뒤 '+')로 보인다. 방어 탭은 H와 B/D를 함께 "확정견딤: 최소 H4 B12 / H2 B8+", 스피드 탭 "선공: 최소 S20 / S12+". 한쪽이 0~32에서 불가면 그쪽은 "무보정 불가"·"상승 불가". n이 있으면 선택지마다 "(다른 능력치에서 n 필요)"를 붙인다(사용자 피드백 2026-11-11 2차, 이전: "<판정>: 최소 <능력치><SP> 필요" 하나). 목표 문구는 펼친 상세 행에만 있다(2026-11-11부터 간단행에는 없음).
  - 결과 배지(사용자 피드백 2026-11-10): 물리/특수 분류 라벨을 빼고(묶음의 B/D 표기로 충분) 그 자리에 대표 행 현재 칸의 1타 확률 배지를 둔다. 단계는 코어 5단 판정 `rollTier`(결정 2, 탭 뷰의 `rollSteps`)가 정하고 화면은 문구·색으로 포맷만 한다. 문구는 단계명 + 확률: "고난수1타 93.8%"·"중난수1타 50.0%"·"저난수1타 6.3%"(확률은 작은 글씨, 소수 첫째 자리 반올림, 0.1%~99.9% 고정), "확정1타"·"확정견딤"은 확률 없이, 무효 칸 "무효"(회색)다. 색 5종: 확정1타 빨강·고난수 주황·중난수 노랑·저난수 연두·확정견딤 초록, 공격·방어 같은 문구·색(사용자 피드백 2026-11-11 2차, 이전 1차: "난수1타: 12.8%"와 탭마다 다른 4단 색, 그 이전: 4단 단계 이름). 텍스트 라벨이 항상 함께 있고 배지 면 위 글자 대비는 4.5:1 이상이다. 계산 불가·갱신 중 카드와 스피드 탭(1타 확률 없음)에는 배지가 없다. 카드 DOM의 `data-category` 계약 속성은 남긴다.
  - 대표 행 규칙: 경계까지 SP 차이가 가장 작은 행이다. 동률이면 기본 행 → 랭크 행 → 스카프 행, 그다음 내 세트 기술 슬롯 순(방어 탭은 상대 기술 사용률 순, 같은 기술은 H 행 → B 행)이다. 경계 있는 행이 없으면(전부 계산 불가 또는 갱신 대기) 대표 대신 "계산 불가" 또는 "갱신 중"과 이유를 보인다. 목록 밖 커스텀 카드에서 행이 모두 변화 없음이면 그 고정 판정을 결과 배지로 보인다(0~32 칸이 없는 고정 판정 행뿐이면 "항상 …" 문구, 사용자 피드백 2026-11-10 — 이전: "변화 없음 — 고정 판정 요약"). 분류 가변 기술(셸암즈류) 안내는 행이 아니라 카드 머리 문구라 대표 행·k와 무관하다. k = 표시되는 행(기본·랭크·스카프·계산 불가 행) 수 − 1이고(0 이하이면 "외 k행" 생략) 변화 없음 행은 세지 않는다. 대표 선택과 k는 조립 단계가 정한다. "소수 배분"·"출처: 사용자 지정"·"계산 불가"는 같은 줄의 표시로 구분한다.
  - 항목을 클릭(탭)하면 오른쪽 패널이 아니라 그 항목 바로 아래로 상세가 펼쳐진다. 상세에는 모든 판정 행(방어 탭은 H 행·B 행 쌍), 랭크 행·스카프 행, 행마다 0~32 띠(현재값 마커·예산 밖 빗금·텍스트 판정 라벨)가 항상 펼쳐져 있다. 여러 항목을 동시에 펼칠 수 있다. 카드 안에서 뺀 변화 없음 행 수("변화 없음 k행")는 모델이 세지만 화면에 보이지 않는다(사용자 피드백 2026-11-10).
  - 키보드: 항목은 버튼으로 포커스·Enter/Space로 펼치고, 펼침 상태를 보조 기술에 알린다. 판정 구분은 색·텍스트를 함께 쓴다(간단행은 결과 배지 텍스트, 상세 띠는 기호도 함께).
  - 좁은 화면에서도 같은 아코디언이고 0~32 띠는 자체 가로 스크롤을 허용한다.
- **배치 보완(에이전트 결정, 사전 승인 때 확인)**
  - 목록 밖 타겟 추가 진입점은 툴바의 포켓몬 선택 옆 "목록 밖 포켓몬 추가" 버튼이다. 누르면 툴바 바로 아래에 인라인 패널이 펼쳐진다: 종 검색(한국어) → 그 타겟의 기술 칩 선택(최소 1, 최대 4) → [취소]/[추가]. 기술을 하나도 고르지 않으면 [추가]가 비활성이고, 기술을 자동으로 채우지 않는다(목록 밖 종에 통계 값을 쓰지 않는 메타 불변식 유지). (2026-11-09 빌드 중 개정, 사용자 확인)
  - 커스텀 카드의 프리셋 SP·성격·도구·특성 편집과 타겟 기술 목록 편집은 그 카드의 아코디언 상세 안에서 한다. 기술 목록은 타겟 단위이고 최소 1개를 남겨야 한다(마지막 기술은 지울 수 없다).
  - 탭 단위 "내 세트 계산 불가" 안내와 계산 진행 표시는 툴바 바로 아래(목록 위)에 둔다.
- **슬라이더 드래그 계약(결정 3과 함께)**
  - 드래그 중 값은 슬라이더의 표시 국소 상태다. 리듀서에 반영하지 않고 계산 세대도 올리지 않는다. 놓을 때 리듀서에 반영하고 세대를 올린다. 키보드·숫자 입력은 값이 확정될 때 반영한다.
  - 슬라이더는 잔여 예산까지 클램프한다(그 능력치 최대 = min(32, 현재 값 + 잔여 예산)). 숫자 입력은 클램프하지 않으며, 합계를 넘기면 코어가 거부해 그 탭들이 "내 세트 오류"가 되고 원인 칸 옆에 안내가 보인다. (2026-11-09 빌드 중 개정, 사용자 확인)
  - 드래그 중에는 변화 없음 요약(극단 필터·내 SP 무관 항목)이 드래그 능력치에 의존해 낡더라도 따로 표시하지 않는다. 놓으면 재계산한다.
  - 조립 단계가 표시용 현재 SP로 산술·조회만 한다(판정 재계산 없음). 드래그 중인 능력치의 행은 현재 칸·판정·경계 증감이, 모든 행은 n·예산 밖 여부가 즉시 갱신된다.
  - 드래그 중인 능력치에 판정이 의존하는 다른 능력치의 행(예: 방어 탭에서 H를 끄는 동안의 B 행)은 "갱신 대기"로 표시하고 칸·경계는 갱신하지 않으며, 놓은 뒤 재계산 결과로 바꾼다.

### 결정 2. 카드 모델 계층: 화면과 분리된 순수 도메인 모듈 `src/cards/`, 코어는 "예산 무시 평가"와 "기술 참조 능력치"로 확장한다

#### 위치와 공개 계약

- `src/cards/`는 React·브라우저 API를 import하지 않는 순수 모듈이다. 코어(`src/core`)와 메타(`src/meta`) 공개 API만 쓴다.
- **입력(카드 모델 입력):** 게임 데이터 스냅샷, 메타 뷰, 내 세트(코어 세트 계약), 탭, 조건(내 순풍·상대 순풍), 고난수 기준(`rollSteps` = n, 1~15 정수, 코어 `normalizeRollSteps`로 검증 — 2026-11-11 2차 개정, 이전 1차는 `thresholds` 두 값. 제품 기본 `DEFAULT_ROLL_STEPS` 14를 앱 상태가 명시 전달하고, 코어 3단 구간 기본 `DEFAULT_THRESHOLDS` 0.75·0.1875는 dev 화면·코어 골든 기준으로 그대로 둔다), 표시 기준(묶음 점유율 기준·분류당 카드 상한·랭크 기준·스카프 기준), 필터(상위 N·선택 종), 목록 밖 타겟(로스터 id, 필수 기술 목록 1~4개, 탭·분류·프리셋별 편집값).
- **공개 함수(시그니처 수준)**
  - 계획: (입력, 탭) → 탭 계획. 상대 순서, 묶음, 카드 골격, 카드별 행 작업 목록을 만든다. 코어 판정을 부르지 않아 싸다.
  - 행 작업 계산: (탭 계획, 행 작업, 선택적 캐시) → 행 결과. 행 작업은 양 끝 칸 판정(현재 성격 0·최대 + 변형 범위 끝 무보정 0·상승 최대), 극단 필터 판정 1쌍, 스윕 1회, 성격 변형 스윕 1회(variant), 방어 쌍 최소 조합(pair, 성격 변형마다) 중 하나다(결정 3의 단계). 행 결과는 예산을 무시한 판정과, 그 판정이 의존한 내 능력치 목록을 담는다. 대미지 칸 범주는 모두 코어 5단 판정(`rollTier(p, rollSteps)`)이다.
  - 성격 변형(사용자 피드백 2026-11-11 2차): 스윕 행마다 내 성격 변형 2종 `natures = { stat, neutral, plus }`(실제 성격 id)을 계획이 정한다. stat은 공격·스피드 탭 스윕 능력치, 방어 탭 그 필터의 B/D(H 행·B/D 행·필터 공통). neutral = stat 보정 없는 성격(현재 성격이 그러면 현재 그대로, 아니면 무보정 성격), plus = stat 상승 성격(현재 성격이 그러면 현재 그대로, 아니면 하락을 관여 능력치 밖에 두는 성격 — 현재 하락이 관여 밖이면 유지, 아니면 C → A → B → D → S 순 첫 관여 밖 능력치). 하락 보정은 쓰지 않는다. 현재 성격과 같은 변형은 따로 계산하지 않고 현재 스윕을 쓴다.
  - pair 작업(사용자 피드백 2026-11-10, 2026-11-11 2차 개정): 방어 탭 극단 필터 하나(= 같은 상대 기술·같은 랭크 조건의 H 행·B/D 행 쌍) × 성격 변형(무보정·상승)마다, 5단 방어 순위(확정1타 → 고난수1타 → 중난수1타 → 저난수1타 → 확정견딤)의 각 단계 이상을 내는 (H, B/D) 중 H+B/D 합이 최소이고 동률이면 H가 큰 점을 찾는다. 판정은 예산 무시 대미지 판정의 5단 범주로만 내고, 판정이 두 SP에 대해 단조라는 가정 아래 H 0 → 32로 계단 경계를 따라가며 각 H의 최소 B/D를 줄여 간다(평가 메모 공유, 쌍당 실측 2~64회, 33×33 전수 탐색과 같은 결과를 테스트로 고정). 결과는 `PairPoint[]`이고 캐시 키는 극단 필터 규칙(내 H·B/D SP 제외, 관여 능력치만, 내 세트 성격 = 그 변형) + 작업 종류 'pair'다.
  - 목표(`RowView.target`, 조립 단계, 2026-11-11 2차 개정): 목표 순위 = 현재 판정(현재 성격·SP)의 5단 순위(코어 `tierRank`) + 1, 두 변형 모두 0~32에서 닿지 않거나 이미 최상위면 현재 순위(keep). 변형(무보정·상승)마다 그 순위 이상을 내는 최소 SP를 따로 내고(`neutral`·`plus`, 닿지 않으면 null = "불가"), 건너뛴 칸은 그 칸의 실제 판정을 쓴다. `label`은 두 선택지 실제 판정 중 낮은 쪽이다. 공격·스피드 탭은 그 행의 변형별 33칸에서, 방어 탭은 변형별 pair 결과에서 고른다. n = (목표 SP 합 − 현재 그 능력치 SP 합) − 잔여 예산(0보다 클 때만, 선택지마다). 변화 있는 ok/stale 행에만 붙고, 필요한 변형 스윕(방어 탭은 두 pair)이 끝난 뒤에만 붙는다.
  - 조립: (탭 계획, 지금까지 끝난 행 결과, 표시용 현재 SP) → 탭 뷰. 앞에서부터 일부만 끝났어도 조립할 수 있다(점진 표시). 예산 밖 여부·n·현재 칸·경계 증감·"갱신 대기"는 여기서 산술로만 정한다.
  - 일괄: (입력, 탭) → 탭 뷰. 계획 → 모든 행 작업 → 조립을 한 번에 돈다. 테스트와 재현성의 기준이다.
- **탭 뷰(출력)**
  - 탭 상태: 정상 / 내 세트 오류(이유).
  - 표시 카드 목록(정렬 완료). 카드마다 카드 상태(정상 / 상대 세트 계산 불가), 분류 가변 기술 안내(셸암즈류 — 카드 머리 문구), 상대(id·한국어 이름·순위·사용률 또는 "출처: 사용자 지정"), 분류, 묶음(관련 능력치 SP·성격 보정, 묶음 점유율, 보존률, 소수 배분 여부), 행 목록, 접힌 줄 대표 행·k, 카드 안 변화 없음 k행, 계산 불가 이유가 있다.
  - 행: 종류(기본 / 랭크 변화 / 구애스카프 / 스카프 아님), 기술, 스윕하는 내 능력치, 근거 라벨(수단·점유율), 33칸, 현재 칸, 경계 목록, 목표(`target`: 판정·한 단계 위/유지·최소 SP 능력치 목록·n — 사용자 피드백 2026-11-10), 계산 불가 이유, 갱신 대기 여부, 변화 없음 여부(목록 밖 커스텀 카드에서만 남는 행).
    - 칸: SP, 판정 범주, 예산 밖 여부, 필요 SP n, 표시용 요약(1타 확률·대미지 % 범위 또는 양측 스피드)이 있다. 난수 배열은 담지 않는다.
    - 경계: SP, 이전·이후 범주, 현재 대비 증감, 필요 SP n.
  - 변화 없음 요약: 행 N개·카드 M장, 항목별 고정 판정. 극단 필터 기술·"내 SP 무관" 항목은 1건 = 행 1개, 카드 M은 표시 행이 하나도 남지 않은 래더 카드 수(처음부터 행이 없던 카드 포함). 이 요약과 카드의 변화 없음 k행은 모델 출력으로 계산하되 화면에는 표시하지 않는다(사용자 피드백 2026-11-10).
  - 탭 안내: 내 기술 중 분류 가변 기술(셸암즈류)과 공격 탭에서 대미지가 내 HP로 정해지는 기술(목숨걸기)의 "계산하지 않음" 안내.
  - 진행: 끝난 행 작업 수 / 전체.
  - 출처: 매치 방식·월·컷.
- **정렬:** 목록 밖 커스텀 카드가 맨 앞(추가한 순서, 그 안에서 분류 → 프리셋 번호)이고, 그다음 래더 카드다. 래더 카드는 상대 사용률 내림차순 → 사용률 동률이면 종 id 순 → 분류(물리 → 특수) → 묶음 점유율 내림차순 → 동률이면 대표 배분 키 순이다. 목록 밖 커스텀 카드는 상위 N·포켓몬 선택 필터와 무관하게 보인다(에이전트 결정).
- 코어 오류(`CoreError`·`CoreInputError`)는 카드 모델이 잡아 이유(코드·필드·메시지)로 바꿔 담는다. 화면은 예외를 다루지 않는다. 내 세트가 거부되면 그 탭이 "내 세트 오류"가 되고, 상대 세트·기술이 거부되면 그 카드·행만 계산 불가가 된다.
- 화면은 판정·경계·점유율·n을 계산하지 않고 탭 뷰를 그대로 그린다.

#### 관여 능력치와 카드 분류

- 코어에 **기술 참조 능력치 조회**를 추가한다. (스냅샷, 기술 id) → 공격 능력치가 누구의 어느 능력치인지(자신 / 대상), 방어 능력치, 분류 가변 여부를 돌려준다.
  - 엔진이 실제로 쓰는 판별을 그대로 따른다. 방어 쪽은 엔진 기술 데이터의 `overrideDefensiveStat` 필드다. 공격 쪽은 엔진이 필드가 아니라 기술 이름(속임수 → 대상, 바디프레스 → 자기 B)으로 분기하므로, 코어도 같은 이름 목록을 상수로 두고 테스트로 엔진과 맞춘다(검증 참고).
  - 분류가 능력치에 따라 바뀌는 기술(셸암즈)은 "분류 가변"으로 돌려준다. 카드 모델은 이 단위에서 그 기술을 카드·행에 넣지 않고 그 포켓몬 항목의 안내 문구로만 남긴다(내 기술이면 탭 안내, 상대 기술이면 그 상대 카드 머리의 안내, 변화 없음 요약·외 k행 미집계. 방어 탭 상대 상위 5기 자리는 다음 순위로 채우지 않는다). 실측으로 현재 메타 사용자는 없다. (2026-11-09 빌드 중 개정, 사용자 확인)
  - 대미지가 사용자 HP로 정해지는 기술(목숨걸기, 참조 능력치 `attackerStats`에 hp)은 공격 탭의 내 기술이면 셸암즈와 같은 방식으로 카드·행을 만들지 않고 탭 안내로만 남긴다. 내 H로 스윕하는 공격 탭이 아니라 공격 능력치로 스윕하면 33칸이 모두 같아 "항상 …"으로 잘못 요약되기 때문이다. 상대 목숨걸기(방어 탭)는 상대 H를 묶음 키에 넣어 그대로 계산한다(코어 계약 무변경). (2026-11-09 1차 구현 뒤 개정, 사용자 결정)
- 메모(2026-11-09 빌드 중 개정, 사용자 확인): 참조 능력치는 기술 단위로 정의한다. 섭동·속성 테스트가 특성 때문에 생기는 숨은 능력치 의존(예: 상대 방어·특방을 비교하는 특성)을 찾으면, 카드 모델의 관여 능력치 규칙(`src/cards/relevance.ts`)에 특성 규칙을 더한다.
- 카드 분류는 상대가 쓰는 쪽이 아니라 **방어 능력치**로 정한다. 공격 탭은 상대 방어 능력치, 방어 탭은 내 방어 능력치가 B면 물리, D면 특수다. 그래서 사이코쇼크는 공격 탭 물리 카드(상대 H·B)에 들어간다. 기술 분류와 참조가 다르면 행에 참조 능력치를 표기한다.
- **스윕 능력치(행)**
  - 공격 탭은 기술이 참조하는 내 공격 능력치다(보통 A/C, 바디프레스는 B).
  - 공격 능력치를 대상에서 가져오는 기술(내 속임수)은 내 SP와 무관하다. 행을 만들지 않고 변화 없음 요약에 "내 SP 무관"으로 넣는다. 고정 판정은 묶음 대표의 상대 A로 계산한다.
  - 방어 탭은 H와 기술이 참조하는 내 방어 능력치다. 상대 속임수는 내 A도 참조하지만 행은 H·B만 두고 내 A는 현재 값으로 고정한다.
  - 스피드 탭은 내 S다.

#### 묶음 규칙

- **묶음 키:** 카드 안 기술들이 참조하는 상대 능력치의 (SP, 성격 보정 +/0/−) 조합. 여러 기술이면 합집합이다.
  - 공격 탭: H + 상대 방어 능력치. 행이 없는 기술(속임수)은 키에 보태지 않는다.
  - 방어 탭: 상대 공격 능력치(A/C, 상대 바디프레스면 B). 상대 능력치를 참조하지 않는 상대 속임수는 키에 보태지 않는다. 키가 비면 "배분 무관" 묶음 하나다.
  - 스피드 탭: S.
- 원천은 메타 항목의 보존 배분이다. 묶음 점유율은 키가 같은 보존 배분 점유율의 합이고, 보존률은 그 종의 보존 누적 점유율이다.
- 기준 이상 묶음을 점유율 내림차순(동률은 대표 배분 키 순)으로 분류당 상한까지 낸다. 없으면 최대 묶음 1장을 "소수 배분"으로 낸다.
- 묶음 대표 세트는 묶음 안 점유율 최대 보존 배분의 관측 배분 가정이다. 키 밖 능력치는 판정에 관여하지 않는다. 예외로 스피드 의존 기술(자이로볼·일렉트릭볼)은 대표의 S로 계산하고 키에 S를 넣지 않는다(알려진 단순화, 에이전트 결정).
- 방어 탭 상대 기술 후보는 기술 분포에서 변화기를 뺀 점유율 상위 5개다. 그중 계산할 수 없는 기술(배울 수 없음·엔진 미지원 등)은 순위를 채우지 않고 계산 불가 행으로 남긴다. 판정 행은 아래 "가장 센 기술 하나" 규칙으로 고른 기술만이다(사용자 피드백 2026-11-11, 이전: 상위 5 공격기 모두 행).

#### 판정 규칙

- **카드·조건당 가장 센 기술 하나 + 선공기(사용자 피드백 2026-11-11, 이전: 공격 탭 내 공격기 각각·방어 탭 상대 상위 5 공격기 각각이 행).** 계획은 카드마다 조건 묶음(`CardSpec.conditions`: 기본 상태 하나 + 랭크 수단 행 조건마다 하나, 커스텀 프리셋 카드도 같음)과 그 후보(공격 탭 = 스윕 행·내 SP 무관 고정 판정, 방어 탭 = 극단 필터 = H행·B/D행 쌍)를 기존 순서(내 기술 슬롯 / 상대 사용률)로 싣는다. 후보는 분류를 가로지른 그 포켓몬의 기술 전부다(사용자 피드백 2026-11-11 — "내가 가진 4개 기술 중 가장 센 기술", 이전 구현은 카드 분류 안 기술끼리만 비교해 같은 상대·같은 조건에서 분류마다 기술이 하나씩 남았다): 카드 분류 밖 기술은 행 없는 비교 전용 후보(`MoveCandidate.target = 'probe'`, `TabPlan.probes`의 `ProbeSpec` = 그 카드 대표 세트·같은 조건 세트)로 넣고, 그 후보가 고르면 이 카드에는 판정 행이 없다(선공기 제외). 비교 전용 후보만 있는 조건은 두지 않는다. 후보마다 현재 세트(계획 시점 SP·성격) 단건 판정(행 작업 `probe`, 고정 판정은 그 결과 자체)을 1단계에서 먼저 하고, 1타 확률 → 최대 대미지 비율 → 순서로 가장 센 후보 하나를 고른다. 무효는 고르지 않고, 코어가 거부한 후보는 고르지 않되 그 행만 계산 불가로 보인다. 우선도 > 0(스냅샷 `move.priority`)인 후보는 가장 센 기술이 아니어도 남기고(`RowView.keptAsPriority`, 간단행 기술 라벨 옆·상세 행 제목 옆 "선공" 태그), 무효면 남기지 않는다. 고른 후보에만 양 끝·스윕·변형·극단·쌍 작업이 생기고, 고르지 않은 후보는 표시·변화 없음 요약·외 k행·진행 수 어디에도 없다. 그 뒤 노출·극단 필터 규칙은 남은 행에 그대로라, 남은 행이 모두 변화 없음이면 래더 카드는 목록에서 빠진다. 다른 분류 기술이 골라져 남은 행이 하나도 없으면 커스텀 카드도 빠진다(그 타겟의 다른 분류 카드가 보인다). 고르기는 판정 비교·집계이고 1타 확률 → 범주 변환을 하지 않는다(판정의 단일 출처 유지). 스피드 탭은 기술 강도와 무관해 조건 묶음이 없다. SP·성격 변경은 새 세대 = 새 계획이라 다시 고른다(드래그 중 표시용 SP는 다시 고르지 않는다 — 놓으면 재계획).
- **극단 사전 필터(방어 탭):** 기술 × 묶음마다 단건 판정 두 번을 한다. 낮은 극단 = 내 H와 참조 방어 능력치를 둘 다 0·무보정 성격, 높은 극단 = 둘 다 32·그 방어 능력치 상승 성격이다(다른 능력치는 현재 값, 예산 무시 평가, 사용자 피드백 2026-11-11 2차 — 이전: 두 극단 모두 현재 성격). 두 5단 판정이 같으면 그 기술을 빼고 변화 없음 요약에 기술 1건 = 행 1개로 넣는다. 랭크 변화 행에도 같은 필터를 따로 적용한다.
- **변화 없음:** 행의 성격 변형(무보정·상승) 33칸씩(예산 밖 포함)과 변형 범위 끝 2칸(무보정 0·상승 최대)의 5단 범주가 모두 같으면 행을 뺀다(사용자 피드백 2026-11-11 2차, 이전: 현재 성격 33칸만). 현재 성격 칸은 비교에 넣지 않는다 — 확정 결정이 무보정·상승 성격 × SP만 보고 하락 보정은 고려하지 않으며, 방어 극단 필터(무보정 H0·B/D0 / 상승 H32·B/D32)와 같은 규칙이다(현재 성격이 무보정·상승이면 그 변형 칸이 곧 현재 칸이다). 스피드 탭도 같다(S 변형). 모든 행이 빠진 카드는 목록에서 뺀다. 집계 규칙은 PRD 그대로다.
  - 예외: 목록 밖 커스텀 카드는 사용자가 직접 고른 타겟이라 제외 대상이 아니다. 탭·분류마다 프리셋 3장을 항상 내고, 33칸이 같은 행(방어 탭 극단 필터에 걸리는 기술 포함)은 빼지 않고 "변화 없음 여부"를 단 행으로 카드 안에 남긴다. 탭의 변화 없음 요약에는 세지 않는다.
- **예산 밖:** n = 칸 SP − (SP 합계 상한 − 그 능력치를 뺀 나머지 SP 합). PRD 정의식(칸 SP − 현재 SP − 잔여 예산)과 같은 값이며 n > 0인 칸·경계에만 붙는다. 조립 단계에서 표시용 현재 SP로 계산한다.
- **경계:** 범주가 직전 칸과 다른 SP다(코어 경계 정의와 같고, 예산 밖 칸 사이도 포함). 현재 판정 요약은 현재 칸에서 위·아래로 가장 가까운 경계와 증감이다.

#### 랭크 변화 행

- 카드 모델이 수단을 적용한 랭크를 세트의 `boosts`에 넣어 코어에 넘긴다. 랭크가 실능치·스피드에 미치는 계산(천진 등)은 엔진과 앱 스피드가 한다.
- **수단과 반응:** 초기 목록과 규칙은 카드 모델의 데이터 상수와 단위 테스트로 관리한다(기준은 Showdown 동작, 초기 목록과 근거 실태는 notes). 수단마다 종류(특성/기술), id, 효과 대상(사용자 자신 / 상대), 능력치별 랭크 변화를 둔다.
  - 대표 예: 상대 하락 — 위협(A−1), 막말내뱉기(A−1·C−1), 얼어붙은바람(S−1). 자기 상승 — 칼춤(A+2), 명상(C+1·D+1), 용의춤(A+1·S+1), 껍질깨기(A·C·S +2, B·D −1), 가속(S+1).
  - 반응은 받는 쪽의 계산 특성(메가면 메가 폼 특성)·도구로 차단 → 변환(심술꾸러기) → 반응(오기·승기는 상대가 낮춘 하락이 실제로 적용될 때 수단 하나당 한 번, 주눅, 하양허브) → −6~+6 자르기 순으로 적용한다. 자기 기술의 자기 하락은 오기·승기를 부르지 않는다.
- **제외 원칙**
  - 확률 부가효과(문포스 30% 등)
  - 엔진이 스스로 적용하는 랭크 변화: 메테오빔·일렉트로빔의 특공 +1, 연속 타격 중 랭크 변화(엔진 `checkMultihitBoost`)와 그 안의 하양허브 소비. 카드 모델이 하양허브를 이미 소비한 행에서 그 기술이 연속기면 이중 처리를 피하려고 그 행을 계산 불가로 둔다.
  - 조건부 도구, 같은 수단의 반복 사용, 수단 조합(행 하나 = 수단 하나 1회), 순풍(별도 토글)
  - 목록에 없는 수단·반응 특성은 효과가 없다(점유율이 높아도 행이 생기지 않는다).
- **점유율:** 상대는 메타 항목 분포(특성·기술)에서 그 id의 점유율이 랭크 기준 이상일 때 행을 낸다. 메가 항목의 특성 분포는 메가 폼 기준이다(선행 계약). 내 세트는 기술 목록·계산 특성(메가면 메가 폼 특성)에 있으면 "내 세트"로 표시하고 점유율은 없다. 목록 밖 타겟은 통계가 없으므로 사용자가 지정한 그 타겟의 기술 목록·계산 특성에 있는 수단을 점유율 기준 없이 상대 수단으로 적용하고 "사용자 지정"으로 표시한다.
- **적용 탭 규칙(표 대신 규칙):** 반응까지 적용한 뒤 랭크가 바뀐 능력치가 그 카드 판정의 참조 능력치에 하나라도 들면, 그 카드의 기본 행마다 랭크 행을 하나 더한다.
  - 참조 능력치: 공격 탭은 내 공격·상대 방어 능력치, 방어 탭은 상대 공격·내 방어 능력치, 스피드 탭은 양쪽 S다.
  - 예: 상대 위협 → 공격 탭 물리. 상대 칼춤 → 방어 탭 물리. 상대 명상 → 방어 탭 특수와 공격 탭 특수(상대 D). 내 칼춤 → 공격 탭 물리 전 카드. 내 얼어붙은바람 → 스피드 탭 전 카드(상대 S−1).

#### 스카프 행과 목록 밖 프리셋

- **스카프 행:** 스피드 탭에서 상대 도구 분포의 구애스카프 점유율이 스카프 기준 이상이면, 그 종의 점유율 최대 S 묶음 카드에 "구애스카프" 행을 더한다. 대표 도구가 구애스카프면 "스카프 아닌 최다 도구"("도구 없음" 포함) 행을 더한다. 메가 항목은 대상이 아니다(메가스톤 고정, 강제로 스카프를 씌우면 코어가 거부).
- **목록 밖 프리셋:** (로스터 id, 탭, 분류, 프리셋 번호, 타겟 기술 목록, 사용자 편집값) → 커스텀 출처 가정(근거 "출처 그대로")을 만든다. 메타 계약의 가정 해석 경로를 그대로 지난다.
  - 특성: 원종 첫 슬롯
  - 도구: 없음. 예외로 메가 폼이 타겟이면 원종 + 메가스톤 + 메가 지정이다(에이전트 결정).
  - 프리셋이 정하지 않은 SP: 0
  - 보정 없는 성격: 노력. 상승 성격은 고집(A+)·조심(C+)·장난꾸러기(B+)·신중(D+)·명랑(S+)이다.
  - 기술: 타겟 단위의 필수 목록(1~4개, 사용자 지정, 자동 채움 없음)을 모든 탭·프리셋 세트의 기술로 쓴다. 방어 탭은 그 목록의 공격기가 상대 기술이고(상위 5 규칙 대신), 카드는 그 기술들이 참조하는 내 방어 능력치 분류마다 프리셋 3장이다(공격기가 없으면 방어 탭 카드 없음). 랭크 수단 출처·스피드 비교의 세트 기술도 같은 목록이다. (2026-11-09 빌드 중 개정, 사용자 확인 — 기술 미선택 상태는 없앴다)
  - 메타 목록 안의 종은 목록 밖 타겟으로 받지 않는다.

#### 코어 계약 확장

- **예산 무시 평가 옵션:** 세트 검증·단건 대미지·스피드 비교에 선택 인자를 더한다. 켜면 SP 합계 상한 검사만 건너뛴다. 능력치별 0~32와 종·특성·도구·기술 합법성 검사는 그대로다. 기본은 꺼짐이라 기존 호출·테스트·확인 페이지 동작이 바뀌지 않는다.
- **스윕 예산 밖 칸 판정 옵션:** `sweepDamage`·`sweepSpeed`(공통 `sweep`) 모두에 더한다. 켜면 예산 밖 칸도 판정한다. 그 칸은 판정 칸에 "예산 밖" 표시를 달고, 경계는 예산 밖 칸까지 포함해 계산한다. 끄면(기본) 지금처럼 판정하지 않는 칸이다. 카드 모델은 판정만 쓰고 예산 밖 표시는 조립 단계에서 다시 계산한다.
- **단일 출처를 위한 추가 export(2026-11-09 빌드 중 개정, 사용자 확인):** 모두 추가만이고 기본 동작은 그대로다.
  - `judgeDamage`·`judgeSpeed`: 스윕 칸 판정과 같은 범주 규칙의 단건 판정. 카드 모델의 양 끝·극단·고정 판정이 범주 규칙을 다시 쓰지 않게 한다.
  - 5단 판정(사용자 피드백 2026-11-11 2차): `rollTier(ohkoChance, n)` = 확정1타(p=1) / 고난수1타(p ≥ n/16) / 중난수1타 / 저난수1타(0 < p ≤ (16−n)/16) / 확정견딤(p=0), 두 경계가 겹치는 n ≤ 8은 고난수 우선. `normalizeRollSteps`(1~15 정수 검증), `TIER_ORDER`(공격 확정견딤 → 확정1타, 방어 그 역순, 스피드 후공 → 선공)·`tierRank`·`nextBetterTier`. `judgeDamage`·`sweepDamage`는 옵션 `rollSteps`가 있으면 칸 범주를 5단 판정으로 내고, 없으면 기존 3단 구간 그대로다(dev 화면·코어 골든·코어 기존 테스트 불변). 제품 경로(카드 모델·앱)는 전부 `rollSteps`를 넘긴다.
  - (2026-11-11 1차, 제품 경로에서는 위 5단 판정으로 대체) `koLabel(side, ohkoChance, thresholds?)`: 1타 확률 → 카드 줄 결과 배지 라벨(공격: 확정1타 / 고난수 / 중저난수 / 확정견딤, 방어: 확정1타 / 중고난수 / 저난수 / 확정견딤). `attackBand`·`defenseBand`와 같은 임계값 정규화·검증을 쓰고 구간·스윕 범주는 바꾸지 않는다. 화면은 대표 행 현재 칸의 `ohkoChance`와 탭 뷰 `thresholds`로 불러 단계 → 색, 확률 → 문구 포맷만 한다(사용자 피드백 2026-11-10·11). `normalizeThresholds`도 export해 카드 계획이 입력 기준을 같은 규칙으로 검증한다(2026-11-11).
  - `checkSpeedSupport`: 세트 하나가 스피드 비교에 쓰일 수 있는지 검사한다. 스피드 오류가 측 구분 없는 field로만 나와 내 세트/상대 귀속을 정할 수 없어서다.
  - `engineMoveOverrides`: 엔진 기술 데이터의 참조 재정의 필드 조회. `@smogon/calc` import를 엔진 래퍼 한 곳에 가둔다.
  - 엔진 상수 `SPEED_DEPENDENT_MOVES`·`SPEED_DEPENDENT_ATTACKER_ABILITIES` export(관여 능력치 S 판정용, 결정 3).
  - 메타 `parseSpreadKey`: 보존 배분 키 해석을 관측 배분 가정과 묶음 규칙이 공유한다.
- **대미지 스윕 허용 능력치(하위 호환 합집합):** 공격측 A/C + B(바디프레스용), 방어측 H/B/D + A(대상 참조 공격용)다. 지금 허용하던 조합은 모두 그대로 허용한다(좁히지 않음). 판정 범주는 지금처럼 측(공격측 → 공격 관점, 방어측 → 방어 관점)으로 정한다. 기술이 참조하지 않는 능력치를 스윕하면 판정이 일정하게 나올 뿐이다. 그 밖의 능력치(공격측 H/D/S, 방어측 C/S)는 지금처럼 거부한다.
- **선행 계약과의 정합**
  - 코어 ADR 결정 2의 "SP 범위와 합계 검증"은 기본 동작으로 남는다. 확장은 명시적으로 켜는 가상 평가다. `minSpToOutspeed`가 이미 예산 초과 SP를 판정하는 선례다.
  - "엔진에는 스냅샷 수치만 주입" 불변식은 위력·타입·분류·타수·대상 수치에 관한 것이다. 참조 판별은 선행 ADR이 엔진 데이터 의존으로 남긴 기술 고유 효과 범주라 이 불변식을 어기지 않는다.
  - 앱 스피드 공식, 1타 확률 자체 분포 합성 경로는 바뀌지 않는다.
  - 목록 밖 종은 커스텀 출처 가정만 받는다(메타 불변식).
  - 이 확장은 선행 ADR 본문을 고치지 않고 이 ADR에 후속 결정으로 남긴다.

### 결정 3. 계산 전략과 반응성: 메인 스레드 시간 분할 실행기 + 양 끝 칸 선판정 순서 + 점진 표시 + 관여 능력치 키 메모 캐시, Web Worker는 보류

- **실측 근거(notes "ADR 근거 실측")**
  - 브라우저 33칸 스윕 중앙값은 1.30ms, Node는 0.77ms다. 비 약 1.7은 서로 다른 조합 한 쌍의 비교라 대략적인 환산이다.
  - 방어 탭(묶음 적용, 한카리아스 예시): 극단 필터가 기술×묶음 332건 중 304건(92%)을 빼 스윕 56회, Node 60~81ms다. 별도 상한 추정(묶음 없이 배분 상위 3, 세트 6종)은 필터 84~95%, 스윕 42~132회, 52~121ms다.
  - 공격 탭(4기술): 스윕 298회, Node 223ms이고 행의 96%가 변화 없음이다. 스피드 탭은 11ms다.
  - 브라우저로 환산하면 최악인 공격 탭이 약 0.38s, 내 랭크 수단 행이 붙으면 약 0.76s다. 탭 하나를 한 번에 동기 계산하면 100ms 막힘 기준을 넘는다.
  - 첫 "보이는" 카드: 변화 없음 카드가 사용률 상위에 연달아 나오면 첫 표시 카드가 뒤로 밀린다. 실측(공격 탭, 세트 5종) 첫 표시 카드 위치는 2~60번째, 33칸 전부 계산하면 Node 3.5~59ms, 양 끝 칸 선판정을 쓰면 0.9~4.8ms다. 모든 카드가 변화 없음이면 탭 전체를 계산해야 "보이는 카드 없음"이 정해진다.
- **계산 단계(행 작업 순서):** 탭마다 다음 순서로 돈다.
  - (사용자 피드백 2026-11-11) 1단계 맨 앞은 후보 단건 판정(probe)이다. 한 카드·조건의 후보 판정이 다 나와야 고른 후보의 양 끝·극단 필터가 1단계에 생긴다(실행기는 probe·고정 판정 결과 뒤 대기열을 다시 만든다). 첫 카드는 probe 뒤에 나온다.
  - 방어 탭은 1단계와 같은 우선순위로 고른 기술 × 묶음마다 극단 사전 필터(단건 판정 1쌍)를 먼저 돈다. 필터로 빠진 기술은 그 자리에서 변화 없음으로 최종 확정하며 3단계 확인 스윕 대상이 아니다(필터는 PRD의 독립 제외 규칙이다). 필터를 통과한 기술의 H 행·B(또는 D) 행은 아래 1~3단계를 다른 탭과 똑같이 따른다.
  1. 모든 행의 양 끝 칸(SP 0·32, 예산 무시) 단건 판정.
  2. 양 끝 판정이 다른 행의 33칸 스윕(사용률 순). 카드는 이 단계에서 확정 표시된다.
  3. 양 끝 판정이 같은 행의 33칸 확인 스윕(저우선순위, 다른 탭의 1·2단계 뒤). 결과가 "전 칸 같음"이면 변화 없음으로 확정하고, 아니면(단조성 위반) 그 행을 정렬 위치에 넣는다.
  4. (사용자 피드백 2026-11-11 2차) 성격 변형 스윕(variant). 양 끝이 나온 행마다 현재 성격과 다른 변형(무보정·상승)의 33칸 스윕이다. 현재 성격 스윕(2·3단계) 뒤에 둔다. 1단계 양 끝에 변형 범위 끝(무보정 0·상승 최대) 2칸을 함께 판정해, 그 2칸이 다르면 2단계(확정 표시)로 올린다(현재 성격 양 끝은 표시용이고 노출 판단에 쓰지 않는다). 범위 끝이 같은 래더 행은 변형 스윕이 끝날 때까지 잠정 제외(요약에도 넣지 않음)이고, 변형에서 바뀌면 표시한다. 변형 결과가 오류면 목표를 내지 않는다(오류를 "불가"로 보이지 않음).
  5. (방어 탭, 사용자 피드백 2026-11-10, 2026-11-11 2차 개정) 방어 쌍 최소 조합(pair) × 성격 변형 2종.
     (가장 센 기술 하나 뒤 실측 2026-11-11, 예시 세트·상위 30·동기·Node·캐시 없음: 공격 탭 probe 340·양 끝 85·스윕 85·변형 85건 합계 약 190~220ms, 방어 탭 probe 411·극단 131·양 끝 50·스윕 50·변형 50·pair 32건 약 220~270ms, 스피드 탭 약 20ms 그대로. 아래 괄호의 이전 실측은 기술마다 행일 때 값이다.) 극단 필터를 통과하고 그 쌍의 H 행·B/D 행의 현재·변형 스윕이 모두 끝났으며 둘 중 하나라도 변화가 있는 쌍만 대상이다. 그 필터의 마지막 행 스윕·변형 스윕이 끝나면 대기열을 다시 만들어 pair가 빠지지 않게 한다. 탭 `complete`·진행 수는 5단계까지 포함한다(`stage12Done`의 뜻은 그대로). 실측(예시 세트, 상위 30, 동기, Node, 캐시 없음): 공격 탭 양 끝 340·스윕 340·변형 340건 합계 약 590ms, 방어 탭 극단 411·양 끝 122·스윕 122·변형 122·pair 96건 합계 약 480ms(pair 최대 4.7ms), 스피드 탭 약 20ms.
  - 3단계 덕분에 최종 결과는 "33칸 전부 같음" 정의 그대로이고(예외: 방어 탭 극단 필터로 빠진 기술은 필터 정의 그대로 확정된다), 1단계는 순서만 바꾼다. 단조성 실측(904개 위반 0, 세트 5종에서 양 끝 선판정과 전 칸 계산의 표시 카드 수 일치)이 이 순서 최적화의 근거다.
  - 실측상 1단계는 행당 단건 판정 2회(0.04ms 수준)라, 첫 표시 카드와 "모두 변화 없음" 판정이 탭 크기와 거의 무관하게 빨라진다(공격 탭 1·2단계 Node 5~33ms).
- **실행기(앱 계층 `src/app/`)**
  - 카드 모델의 행 작업을 위 순서대로 돈다. 한 조각에서 약 12ms 일한 뒤 브라우저에 양보한다. 양보는 MessageChannel 왕복(매크로태스크)으로 한다. `scheduler.yield`는 쓰지 않는다: 그 이어달리기가 렌더·일반 작업보다 앞서 계산 중 프레임이 약 9fps(rAF 간격 100~117ms)로 떨어지는 것을 실측했고, MessageChannel로 바꾸면 약 60fps(17ms)가 된다(notes "반응성 측정", 2026-11-09 1차 구현 뒤 개정).
  - 작업 단위는 스윕 1회(최대 약 2ms) 또는 방어 쌍 최소 조합 1건(pair, 쌍당 평가 약 64회·설계 상한 약 200회로 스윕 33회보다 클 수 있다)이다. pair는 실측 33건 합계 약 70ms(건당 약 2ms)라 조각 약 12ms를 크게 넘기지 않는다.
- **우선순위:** 현재 탭의 1·2단계 → 나머지 두 탭의 1·2단계 → 현재 탭의 3·4·5단계 → 나머지 탭의 3·4·5단계다(4단계 추가 2026-11-10, 성격 변형 4단계·쌍 5단계로 재번호 2026-11-11 2차). 탭을 바꾸면 바로 보인다. 상세 행의 목표 문구는 변형 스윕(방어 탭은 두 쌍)이 끝난 행부터 채워진다.
- **점진 표시:** 조각이 끝날 때마다 조립 결과를 외부 저장소에 넣는다. 화면은 확정된 카드를 정렬 위치에 보이고 진행(끝난 수/전체)을 보인다. 3단계가 남아 있는 동안 변화 없음 요약은 "확인 중"을 함께 보인다.
- **취소:** 입력(내 세트·메타 선택·조건·고난수 기준·표시 기준·필터·목록 밖 타겟)이 리듀서에 반영되면 세대 번호를 올린다. 진행 중이던 조각은 결과를 버리고 새 계획으로 다시 시작한다. 캐시는 유지한다. 슬라이더 드래그 중에는 세대를 올리지 않는다(결정 1).
  - 세대 교체 중 표시: 새 세대의 첫 카드 사건(첫 확정 카드 또는 잠정 빈 상태) 전까지 이전 세대 탭 뷰를 흐리게 남기고 "갱신 중"을 보인다(superseded). 첫 카드 사건 때 새 뷰로 바꾼다. 빈 목록이 깜빡이지 않게 하려는 것이다. (2026-11-09 빌드 중 개정, 사용자 확인)
- **메모 캐시**
  - **값:** 예산 무시 판정만 담은 축약 칸(범주·1타 확률·% 범위·스피드)이다. 예산 밖 표시는 담지 않는다(조립 단계에서 계산). 난수 배열은 버려 메모리를 줄인다.
  - **키:** 정규화한 코어 호출 입력이다. 레귤레이션, 호출 종류, 평가 옵션 2개(예산 무시·예산 밖 판정), 측·능력치, 공격·방어 세트, 기술, 조건, 고난수 기준(탭 계획의 `rollSteps`, 대미지 판정만 — 스피드 판정은 넣지 않는다. 2026-11-11 2차 개정, 이전 1차: `thresholds` 중 그 판정이 읽는 하나), 양 끝·극단 필터는 성격 변형 id(`natures`)를 넣는다. 후보 단건 판정(probe)은 작업 종류 `probe`로, 덮어쓰는 능력치가 없어 관여 SP를 모두 넣는다(2026-11-11). 변형 스윕(variant)은 내 세트 성격을 그 변형으로 바꾼 세트의 sweep과 같은 키 공간이라, 사용자가 그 성격으로 바꾸면 캐시 적중한다. pair는 변형 성격 세트로 키를 만든다. 화면 기준을 바꾸면 대미지 판정 키가 달라져 재계산하고 스피드 판정은 캐시 적중한다. 되돌리면 같은 키로 캐시 적중한다.
  - **SP 정규화(관여 능력치 키):** 세트 SP 중 그 판정에 관여하지 않는 능력치는 키에서 뺀다. 관여 능력치는 기술 참조 조회로 정한 참조 능력치 + 방어측 H + 양쪽 S(스피드 의존 기술이거나 공격측이 스피드 의존 특성일 때만 — 코어 참조 조회의 `speedDependent`와 엔진 `SPEED_DEPENDENT_ATTACKER_ABILITIES`)다. 처음 초안은 S를 항상 넣었으나, 그러면 공격·방어 탭에서 내 S를 끄는 동안 모든 행이 갱신 대기가 되고 놓으면 캐시가 전부 빗나가 좁혔다(2026-11-09 빌드 중 개정, 사용자 확인). 누락은 아래 속성 테스트로 지킨다. 스윕 행은 스윕하는 능력치의 SP도 뺀다(결과가 그 값과 무관). 단건 판정(양 끝·극단 필터)은 덮어쓴 세트의 관여 능력치 SP를 그대로 키에 넣는다. 스피드 비교는 양쪽 S만 넣는다. 랭크·성격·도구·특성·상태는 항상 넣는다.
  - **효과:** 내 A를 바꾸면 A 스윕 행(스윕 SP 제외)과 A가 관여하지 않는 C 행·방어 행(상대 속임수 제외)이 적중하고, 양 끝 판정과 A가 관여하는 행만 다시 계산한다. 내 B를 바꾸면 방어 탭 H 행은 B가 관여하므로 다시 계산한다.
  - **상한:** 항목 수 상한(초기 5,000)을 넘으면 오래 쓰지 않은 것부터 버린다. 레귤레이션이 바뀌면 비운다.
  - 캐시 없이 일괄 계산한 결과와 캐시를 거친 결과가 같아야 한다(재현성 테스트). 관여 능력치 규칙은 "뺀 능력치를 바꿔도 판정이 같다" 속성 테스트로 지킨다. 같은 관여 규칙이 결정 1 드래그 계약의 "갱신 대기" 판정에도 쓰인다(한 함수).
- **렌더 비용 제한:** 목록은 압축 줄이 기본이고, 0~32 띠는 상세를 펼친 카드만 그린다(결정 1).
- **달성 근거**
  - 첫 카드: 스냅샷·메타 로드(메타 파싱~대표 가정 0.7ms 실측) 뒤 1단계 + 첫 표시 카드의 스윕으로 Node 수 ms~수십 ms, 브라우저 환산으로도 500ms에 큰 여유가 있다. 모든 카드가 변화 없음이면 1단계가 끝난 시점(공격 탭 Node 수십 ms)에 "보이는 카드 없음 + 변화 없음 요약(확인 중)"을 보인다.
  - 전체: 1~3단계 합계는 33칸 전부 계산과 같은 양에 1단계(수십 ms)를 더한 것이다. 최악 약 0.8s 수준에 상대 랭크·스카프 행을 더해도 3초의 3배 이상 여유다.
  - 막힘: 조각 약 12ms + 스윕 1회 + 조각당 렌더로 100ms 미만이다.

## 선택지

### 결정 2 (카드 모델 계층)

#### 선택지 2-A: `src/cards/` 순수 도메인 모듈 + 계획/행 작업/조립 계약 (채택)

- 장점: PRD 재현성 요구(화면 없이 같은 카드 목록)를 일괄 함수로 바로 테스트한다. 행 작업 단위라 결정 3의 시간 분할·단계·캐시가 계약 위에서 자연스럽다. 조립이 산술 표시값을 맡아 슬라이더 드래그를 재계산 없이 따라간다. 화면이 판정을 계산하지 않는다는 경계가 import 방향으로 강제된다.
- 단점: 계획·작업·조립 세 단계라 단일 함수보다 계약이 넓다.

#### 선택지 2-B: React 컴포넌트·훅 안에서 코어를 직접 호출

- 장점: 파일이 적고 처음 구현이 빠르다.
- 단점: 묶음·필터·랭크 규칙이 화면 코드에 흩어져 화면 없는 재현성 테스트가 불가능하다. 점진 계산·캐시를 렌더 주기와 섞게 된다.

#### 선택지 2-C: 카드 모델을 단일 동기 함수(입력 → 탭 뷰) 하나로만 노출

- 장점: 계약이 가장 작다.
- 단점: 실측상 탭 하나가 브라우저 약 0.4~0.8s라 한 번에 부르면 막힘 기준을 넘는다. 점진 표시를 하려면 결국 내부를 쪼개야 한다.

#### 코어 계약 확장의 대안 (예산 밖 칸·극단 필터)

- **코어에 예산 무시 평가 옵션 + 스윕 예산 밖 판정 옵션 추가 (채택):** 판정 원천이 코어 하나로 남는다. 기본값이 꺼짐이라 기존 계약·테스트가 그대로다. 단점은 코어 공개 인자가 늘고 옵션 조합 테스트가 필요하다는 것이다.
- **카드 모델이 다른 능력치를 임시로 줄인 가상 세트로 계산:** 코어를 안 바꾼다. 그러나 "무관해 보이는" 능력치가 실제로 판정에 들어가는 경우가 실측·코드로 확인된다(속임수의 대상 A, 자이로볼·일렉트릭볼의 S, 셸암즈의 B/D). 줄일 능력치 선택도 임의라 결과가 조용히 틀릴 수 있다. H32·B32 극단 판정은 다른 능력치를 합 2 이하로 강제로 바꿔야 해 PRD의 "다른 능력치는 현재 값"을 지키지 못한다.
- **스윕만 예산 무시로 확장:** 칸 판정은 풀리지만 극단 필터는 두 능력치를 함께 바꾸는 단건 판정이다. 스윕은 한 능력치만 바꾸므로 이 판정을 표현하지 못하고, 단건 판정은 여전히 거부된다.

#### 참조 능력치 판별의 대안

- **엔진 판별을 그대로 따름(방어 쪽 필드 + 공격 쪽 이름 목록), 테스트로 엔진과 대조 (채택):** 엔진이 계산에 쓰는 판별과 같아 판별과 계산이 어긋나지 않는다. 스냅샷·메타를 다시 만들 필요가 없다. 엔진이 공격 쪽을 이름으로 분기하므로, 이름 목록 상수와 섭동 테스트가 엔진 버전업 때의 어긋남을 잡는다.
- **엔진 기술 데이터 필드만 읽음:** 공격 쪽은 엔진 계산이 필드를 읽지 않아(이름 분기) 필드만 믿으면 엔진과 어긋날 수 있다.
- **스냅샷 기술 항목에 참조 필드를 추가해 생성:** 데이터 계약으로는 깔끔하다. 그러나 `data.json` 해시가 바뀌어 최신 월 메타를 강제로 다시 만들어야 하고(메타 불변식), 엔진이 실제로 쓰는 값과 별개 원천이 생긴다.
- **능력치를 흔들어 보는 런타임 판별:** 원천이 필요 없지만 기술마다 판정을 여러 번 더 돌린다. 면역·고정 대미지에서 판별이 흐려진다. 대신 테스트 수단으로 쓴다.

#### 랭크 변화 적용의 대안

- **카드 모델이 수단·반응을 계산해 `boosts`로 넘김 (채택):** 엔진이 위협·반응을 적용하지 않는다는 실측과 맞는다. 규칙이 한 모듈의 데이터 상수와 테스트에 모인다.
- **엔진의 위협 처리(`abilityOn`)를 켬:** 위협과 그 반응만 다루고 기술 수단은 못 다룬다. 엔진 내부 동작에 기대게 된다(선행 ADR의 얇은 래퍼 원칙과 어긋남).

### 결정 3 (계산 전략)

#### 선택지 3-A: 메인 스레드 시간 분할 + 양 끝 칸 선판정 순서 + 점진 표시 + 메모 캐시 (채택)

- 장점: 실측상 최악 탭도 1초 안팎이라 분할만으로 막힘·전체 기준을 만족하고, 선판정 순서로 첫 표시 카드가 탭 크기와 무관하게 빨라진다. 최종 결과는 확인 스윕으로 정의 그대로다. 스냅샷을 한 번만 로드하고, 오류 객체와 동기 코어 계약을 그대로 쓴다.
- 단점: 메인 스레드 총 작업량은 줄지 않는다(분할·순서만). 확인 스윕 단계에서 드물게 카드가 뒤늦게 끼어들 수 있다(단조성 위반 시). 다음 단위(파티 6마리)처럼 작업량이 몇 배가 되면 다시 검토해야 한다.

#### 선택지 3-B: Web Worker 백그라운드 계산

- 장점: 메인 스레드 막힘이 원천적으로 없다.
- 단점
  - 워커가 게임 데이터(903KiB)와 메타(622KiB)를 따로 로드·파싱해야 한다.
  - 메시지 프로토콜·취소·오류 직렬화(코어 오류 클래스가 경계를 넘으면 프로토타입을 잃는다)가 필요하다.
  - e2e·성능 측정이 복잡해진다.
  - 이 단위의 실측 작업량에는 과하다. 파티 분석 단위의 예비안으로 남긴다.

#### 선택지 3-C: 동기 일괄 계산(분할 없음) + 캐시만

- 장점: 가장 단순하다.
- 단점: 최악 탭 약 0.4~0.8s 동안 입력이 멈춰 100ms 막힘 기준을 어긴다.

#### 선택지 3-D: 양 끝 칸이 같으면 확인 스윕 없이 변화 없음으로 확정

- 장점: 실측상 총 계산이 6~12배 줄어든다(공격 탭 Node 218ms → 33ms 등).
- 단점: 단조성 가정에 기대는 단축이다(실측 위반 0이지만 증명은 아님). PRD의 "전 칸이 같음" 정의를 그대로 계산하지 않는다. 3-A가 첫 표시 이득은 그대로 얻으므로 확인 스윕 생략은 보류하고, 작업량이 커지는 단위의 예비 수단으로 둔다.

#### 선택지 3-E: 사용률 순서 그대로 33칸 전부 계산

- 장점: 단계가 없어 가장 단순하다.
- 단점: 변화 없음 카드가 상위에 몰리면 첫 표시 카드까지 탭 상당 부분을 계산해야 한다(실측 최대 60번째 카드, 내 랭크 행이 붙는 최악은 탭 전체 약 0.76s 환산). 모든 카드가 변화 없음이면 "보이는 카드 없음"이 탭 전체 계산 뒤에야 정해진다.

#### 캐시 키 설계의 대안

- **정규화 입력 키, 관여 능력치 SP만 포함, 스윕 능력치 SP 제외 (채택):** SP 하나를 바꿀 때 그 능력치가 관여하는 판정만 다시 계산한다. 관여 규칙은 속성 테스트로 지킨다.
- **세트 SP 전체를 키로(스윕 능력치만 제외):** 단순하고 관여 규칙 위험이 없다. 그러나 내 A를 바꾸면 C 행·방어 행처럼 A와 무관한 판정까지 키가 달라져 다시 계산된다.
- **캐시 없음:** 매 변경마다 0.4~0.8s 재계산이 되어 입력 중 화면이 계속 다시 채워진다.

### 결정 4 (앱 진입과 상태)

#### 진입 선택지

- **해시 경로 `#/dev` + 지연 로드 (채택):** 정적 호스팅에서 서버 설정 없이 동작한다. 빌드 설정을 바꾸지 않고, 하위 경로 배포에서도 깨지지 않는다. 다음 단위 화면도 같은 방식으로 늘릴 수 있다.
- **쿼리 `?dev`:** 해시와 거의 같다. 다만 이후 화면 상태를 쿼리로 공유하게 되면 충돌하고, 서버 요청에 실린다.
- **별도 엔트리 HTML(`dev.html`, Vite 다중 페이지):** 번들이 완전히 분리된다. 그러나 빌드 입력 설정이 늘고, 성능 훅·공용 CSS 진입을 두 곳에서 관리해야 한다. 지연 로드로도 제품 번들 분리는 얻는다.
- **경로 라우팅(`/dev`):** 정적 호스팅에서 새로고침 시 404를 막으려면 서버 재작성 규칙이 필요해 기각한다.

#### 상태 선택지

- **루트 `useReducer` + 순수 리듀서 모듈 + 실행기 외부 저장소를 `useSyncExternalStore`로 구독 (채택):** 라이브러리 없이 상태 전이를 단위 테스트한다. 계산 진행은 렌더 주기와 분리된다.
- **여러 `useState`(현재 dev 페이지 방식):** 상태가 열 가지가 넘고 서로 묶여 바뀐다(메타 선택 → 필터 초기화 등). 전이 규칙이 컴포넌트에 흩어진다.
- **외부 스토어 라이브러리(zustand·redux 등):** 구독 최적화가 편하지만 의존성 추가 금지 기본값에 어긋나고, 이 규모에는 React 내장으로 충분하다.
- **Context만으로 전역 상태:** 값이 바뀔 때 하위 전체가 다시 렌더된다. 계산 결과처럼 자주 바뀌는 값에는 맞지 않는다.

## 선택 근거

- 카드 모델을 순수 모듈로 두면 PRD의 재현성·"화면은 표시만" 요구가 구조로 강제된다. 계획/행 작업/조립 계약은 실측된 계산량(브라우저 최악 약 0.4~0.8s)을 막힘 없이 나누고, 슬라이더 드래그를 재계산 없이 따라가는 데 필요한 최소 분해다.
- 예산 밖·극단 판정은 판정 원천을 코어 하나로 유지하는 확장이 가장 안전하다. 가상 세트 방식은 실측으로 확인된 숨은 능력치 의존(속임수·자이로볼·셸암즈) 때문에 조용히 틀릴 수 있다. 확장은 기본값이 꺼짐이고 허용 능력치는 합집합이라 선행 계약을 깨지 않는다.
- 참조 능력치는 엔진이 실제로 쓰는 판별(방어 쪽 필드, 공격 쪽 이름 분기)을 따라야 판별과 계산이 어긋나지 않는다. 데이터 재생성 연쇄(게임 데이터 해시 → 최신 월 메타 재생성)도 피한다.
- 계산량이 1초 안팎이라 Web Worker의 비용(데이터 이중 로드·직렬화·측정 복잡도)을 정당화하지 못한다. 시간 분할, 양 끝 선판정 순서, 관여 능력치 키 캐시로 기준과 조작감을 함께 얻고, 최종 결과는 PRD 정의 그대로 유지한다.
- 해시 경로와 React 내장 상태 도구로, 정적·오프라인 배포와 라이브러리 무추가를 유지하면서 제품·dev 화면을 공존시킨다.

## 결과

### 긍정적 영향

- 카드·행·판정·경계·변화 없음 요약을 Vitest만으로 검증할 수 있다(화면 없음).
- 코어의 판정 원천이 하나로 유지되고, 예산 밖·극단 판정과 바디프레스 스윕이 같은 경로로 계산된다.
- 슬라이더 드래그 중 드래그 능력치 행의 현재 칸·판정·경계 증감과 모든 행의 n·예산 밖이 즉시 갱신되고, 놓은 뒤에는 바뀐 능력치가 관여하는 판정만 다시 계산한다. 탭 전환은 백그라운드 선계산으로 바로 보인다.
- 첫 표시 카드가 변화 없음 카드의 분포와 거의 무관하게 빨리 나온다.
- 다음 단위(파티 분석)가 같은 카드 모델·실행기·해시 경로 위에 얹힌다.

### 부정적 영향 / 트레이드오프

- 코어 공개 계약이 넓어진다(평가 옵션 2개, 참조 조회 1개, 스윕 허용 능력치 합집합). 옵션 조합 테스트가 늘어난다.
- 참조 판별이 엔진 동작(방어 쪽 필드, 공격 쪽 이름 분기)에 의존한다. 엔진 버전을 올려 이름 분기 목록이나 필드가 바뀌면 조회가 엔진과 어긋날 수 있고, 대조·섭동 테스트가 깨지는 것으로만 드러난다.
- 관여 능력치 캐시 키는 "뺀 능력치는 판정에 무관"이라는 규칙에 기대고, 속성 테스트로만 지킨다.
- 랭크 수단·반응표는 앱이 직접 유지한다. 목록에 없는 수단은 행이 생기지 않는다(점유율이 높아도). 새 레귤레이션마다 notes 방식의 실태 점검이 필요하다.
- 메인 스레드 총 작업량은 그대로다(확인 스윕 포함). 작업량이 몇 배가 되는 단위에서는 3-D 또는 Web Worker를 다시 검토해야 한다.
- 알려진 단순화
  - 상대 속임수의 내 A는 현재 값 고정이다.
  - 내 속임수의 고정 판정은 묶음 대표의 상대 A 기준이다.
  - 스피드 의존 기술은 묶음 대표의 S로 계산한다.
  - 셸암즈(분류 가변 기술)는 계산하지 않고 그 포켓몬 항목의 안내 문구로만 보인다. 공격 탭의 내 목숨걸기도 탭 안내로만 보인다.
  - 드래그 중 변화 없음 요약은 낡아도 따로 표시하지 않는다(놓으면 재계산).
  - 미러아머는 반사 없이 차단만 한다.
  - 카드 모델이 하양허브를 소비한 행에서, 엔진의 연속 타격 중 랭크 변화와 하양허브 반응은 다루지 않고 그 행을 계산 불가로 둔다.
- dev 공용 모듈과 perf 훅 이동으로 import 경로가 바뀐다(동작 변화 없음).
- 메모: 테마 토큰은 사용자의 PokeQuiz(poke-battle-quiz) 팔레트를 기반으로 한다(raw `--mb-*` → 역할 토큰 2층, 라벤더 강조, 판정 색은 tier 파스텔 + 어두운 잉크, 다크는 `prefers-color-scheme`). 폰트 파일은 가져오지 않는다(사용자 피드백 2026-11-10).
