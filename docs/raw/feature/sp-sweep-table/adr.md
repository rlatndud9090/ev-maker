# ADR: SP 구간 판정 표 화면(메타 카드 리스트)

> 작성 고도: ADR은 "어떤 구조를 왜 골랐나"의 근거 저널이다. 코드 스니펫·전체 설계문서를 본문에
> 넣지 않는다(과대 ADR) — 상세 구현은 코드·별도 설계문서로 내린다. 사람은 중립 역할어로만
> 지칭하고 개인 호칭·별명은 넣지 않는다. 참고: `harness/templates/examples/README.md`.

## 컨텍스트

어떤 상황에서 이 결정이 필요했는가?

- PRD 요구: 내 포켓몬 하나를 설정하면 공격·방어·스피드 탭마다 메타 포켓몬과의 판정을 사용률 순 카드로 보인다. 카드 = 상대 × 판정 관여 능력치 묶음 × 분류이고, 판정 행마다 현재 판정·경계 SP·예산 밖 필요 SP를 보인다. 방어 탭 극단 사전 필터, 변화 없음 제외 요약, 통계 기반 랭크 변화 행, 스카프 행, 목록 밖 커스텀 프리셋, 순풍 토글, 표시 기준 설정이 있다. 같은 입력이면 화면 없이 같은 카드 목록이 재현돼야 하고, 화면은 판정을 직접 계산하지 않는다.
- 현재 코드/데이터 제약
  - 계산 코어(`src/core`)는 스냅샷을 인자로 받는 동기 순수 함수다. `validateSet`이 SP 합계 상한 초과를 `SP_TOTAL_EXCEEDED`로 거부하고, 스윕은 예산 밖 칸을 판정하지 않는다. 그래서 PRD의 예산 밖 칸 판정과 극단 필터(H32·B32, 예산 무시)를 지금 코어로는 계산할 수 없다.
  - `sweepDamage`의 허용 능력치는 공격측 A/C, 방어측 H/B/D로 고정이다. 바디프레스(내 B 참조)를 공격측으로 스윕할 수 없다.
  - 스냅샷 기술 항목에는 참조 능력치 정보가 없다. 엔진 기술 데이터에는 있다(m-c에서 바디프레스·속임수·사이코쇼크 셋, notes 실측).
  - 엔진과 코어는 위협·오기 같은 랭크 변화를 스스로 적용하지 않는다(notes 실측). 랭크는 세트의 `boosts`로만 들어간다.
  - 메타 계약(`src/meta`)은 보존 배분(종당 최대 30)과 관측 배분 가정, 목록 밖 종의 커스텀 출처 가정 경로를 이미 준다.
  - 화면은 `src/main.tsx`가 개발 확인 페이지를 그대로 렌더하는 구조다. 라우팅·상태 라이브러리가 없고 의존성은 react·react-dom뿐이다.
- 사용자 경험 제약: 탭을 열거나 설정을 바꾼 뒤 첫 카드 ≤ 500ms, 탭 전체 ≤ 3초, 계산 중 100ms 넘는 막힘 없음. 폭 400px·1280px 반응형, 키보드 조작.
- 검증 제약: 정적 빌드·오프라인 e2e(외부 요청 0건)가 유지돼야 하고, 기존 dev 확인 페이지 스펙과 `window.__perf` 성능 훅이 계속 돌아야 한다.

## 결정

### 결정 1. 화면 배치와 카드 구성

디자인 결정 레인에서 사용자 선택 후 작성(design-options.html).

### 결정 2. 카드 모델 계층: 화면과 분리된 순수 도메인 모듈 `src/cards/`, 코어는 "예산 무시 평가"와 "기술 참조 능력치"로 확장한다

#### 위치와 공개 계약

- `src/cards/`는 React·브라우저 API를 import하지 않는 순수 모듈이다. 코어(`src/core`)와 메타(`src/meta`) 공개 API만 쓴다.
- **입력(카드 모델 입력):** 게임 데이터 스냅샷, 메타 뷰, 내 세트(코어 세트 계약), 탭, 조건(내 순풍·상대 순풍), 표시 기준(묶음 점유율 기준·분류당 카드 상한·랭크 기준·스카프 기준), 필터(상위 N·선택 종), 목록 밖 타겟(로스터 id, 탭·분류·프리셋별 편집값, 방어 탭에서 고른 기술).
- **공개 함수(시그니처 수준)**
  - 계획: (입력, 탭) → 탭 계획. 상대 순서, 묶음, 카드 골격, 카드별 행 작업 목록을 만든다. 코어 판정을 부르지 않아 싸다.
  - 행 작업 계산: (탭 계획, 행 작업, 선택적 캐시) → 행 결과. 행 작업 하나는 스윕 1회이거나 극단 필터 판정 1쌍이다.
  - 조립: (탭 계획, 지금까지 끝난 행 결과) → 탭 뷰. 앞에서부터 일부만 끝났어도 조립할 수 있다(점진 표시).
  - 일괄: (입력, 탭) → 탭 뷰. 계획 → 모든 행 작업 → 조립을 한 번에 돈다. 테스트와 재현성의 기준이다.
- **탭 뷰(출력)**
  - 탭 상태: 정상 / 내 세트 오류(이유) / 목록 밖 방어 탭의 "기술을 선택하세요".
  - 표시 카드 목록(정렬 완료). 카드마다 상대(id·한국어 이름·순위·사용률 또는 "출처: 사용자 지정"), 분류, 묶음(관련 능력치 SP·성격 보정, 묶음 점유율, 보존률, 소수 배분 여부), 행 목록, 카드 안 변화 없음 k행, 계산 불가 이유가 있다.
  - 행: 종류(기본 / 랭크 변화 / 구애스카프 / 스카프 아님), 기술, 스윕하는 내 능력치, 근거 라벨(수단·점유율), 33칸, 현재 칸, 경계 목록, 계산 불가 이유.
    - 칸: SP, 판정 범주, 예산 밖 여부, 필요 SP n, 표시용 요약(1타 확률·대미지 % 범위 또는 양측 스피드)이 있다. 난수 배열은 담지 않는다.
    - 경계: SP, 이전·이후 범주, 현재 대비 증감, 필요 SP n.
  - 변화 없음 요약: 행 N개·카드 M장, 항목별 고정 판정.
  - 진행: 끝난 행 작업 수 / 전체.
  - 출처: 매치 방식·월·컷.
- 코어 오류(`CoreError`·`CoreInputError`)는 카드 모델이 잡아 이유(코드·필드·메시지)로 바꿔 담는다. 화면은 예외를 다루지 않는다. 내 세트가 거부되면 그 탭이 "내 세트 오류"가 되고, 상대 세트·기술이 거부되면 그 카드·행만 계산 불가가 된다.
- 화면은 판정·경계·점유율·n을 계산하지 않고 탭 뷰를 그대로 그린다.

#### 관여 능력치와 카드 분류

- 코어에 **기술 참조 능력치 조회**를 추가한다. (스냅샷, 기술 id) → 공격 능력치가 누구의 어느 능력치인지(자신 / 대상), 방어 능력치, 분류 가변 여부를 돌려준다.
  - 원천은 엔진 기술 데이터의 참조 재정의 필드다. 엔진이 실제 계산에 같은 값을 쓰므로 판별과 계산이 어긋나지 않는다.
  - 분류가 능력치에 따라 바뀌는 기술(셸암즈)은 "분류 가변"으로 돌려준다. 카드 모델은 이 단위에서 그 기술을 계산 불가 행("분류가 능력치에 따라 바뀌는 기술")으로 둔다. 실측으로 현재 메타 사용자는 없다.
- 카드 분류는 상대가 쓰는 쪽이 아니라 **방어 능력치**로 정한다. 공격 탭은 상대 방어 능력치, 방어 탭은 내 방어 능력치가 B면 물리, D면 특수다. 그래서 사이코쇼크는 공격 탭 물리 카드(상대 H·B)에 들어간다. 기술 분류와 참조가 다르면 행에 참조 능력치를 표기한다.
- **스윕 능력치(행)**
  - 공격 탭은 기술이 참조하는 내 공격 능력치다(보통 A/C, 바디프레스는 B).
  - 공격 능력치를 대상에서 가져오는 기술(내 속임수)은 내 SP와 무관하다. 행을 만들지 않고 변화 없음 요약에 "내 SP 무관"으로 넣는다(고정 판정은 묶음 대표로 계산).
  - 방어 탭은 H와 기술이 참조하는 내 방어 능력치다. 상대 속임수는 내 A도 참조하지만 행은 H·B만 두고 내 A는 현재 값으로 고정한다.
  - 스피드 탭은 내 S다.

#### 묶음 규칙

- **묶음 키:** 카드 안 기술들이 참조하는 상대 능력치의 (SP, 성격 보정 +/0/−) 조합. 여러 기술이면 합집합이다.
  - 공격 탭: H + 상대 방어 능력치. 행이 없는 기술(속임수)은 키에 보태지 않는다.
  - 방어 탭: 상대 공격 능력치(A/C, 상대 바디프레스면 B). 상대 능력치를 참조하지 않는 상대 속임수는 키에 보태지 않는다. 키가 비면 "배분 무관" 묶음 하나다.
  - 스피드 탭: S.
- 원천은 메타 항목의 보존 배분이다. 묶음 점유율은 키가 같은 보존 배분 점유율의 합이고, 보존률은 그 종의 보존 누적 점유율이다.
- 기준 이상 묶음을 점유율 내림차순(동률은 대표 배분 키 순)으로 분류당 상한까지 낸다. 없으면 최대 묶음 1장을 "소수 배분"으로 낸다.
- 묶음 대표 세트는 묶음 안 점유율 최대 보존 배분의 관측 배분 가정이다. 키 밖 능력치는 판정에 관여하지 않는다. 예외로 스피드 의존 기술(자이로볼·일렉트릭볼)은 대표의 S로 계산하고 키에 S를 넣지 않는다(알려진 단순화).
- 방어 탭 상대 기술은 기술 분포에서 변화기를 뺀 점유율 상위 5개다. 그중 계산할 수 없는 기술(배울 수 없음·엔진 미지원 등)은 순위를 채우지 않고 계산 불가 행으로 남긴다.

#### 판정 규칙

- **극단 사전 필터(방어 탭):** 기술 × 묶음마다 단건 판정 두 번을 한다. 내 H와 참조 방어 능력치를 둘 다 0으로 둔 판정과 둘 다 32로 둔 판정이다(다른 능력치·성격은 현재 값, 예산 무시 평가). 두 방어 구간이 같으면 그 기술을 빼고 변화 없음 요약에 기술 1건 = 행 1개로 넣는다. 랭크 변화 행에도 같은 필터를 따로 적용한다.
- **변화 없음:** 행의 33칸(예산 밖 포함) 범주가 모두 같으면 행을 뺀다. 모든 행이 빠진 카드는 목록에서 뺀다. 집계 규칙은 PRD 그대로다.
- **예산 밖:** n = 칸 SP − (SP 합계 상한 − 그 능력치를 뺀 나머지 SP 합). PRD 정의식(칸 SP − 현재 SP − 잔여 예산)과 같은 값이며 n > 0인 칸·경계에만 붙는다.
- **경계:** 범주가 직전 칸과 다른 SP다(코어 경계 정의와 같고, 예산 밖 칸 사이도 포함). 현재 판정 요약은 현재 칸에서 위·아래로 가장 가까운 경계와 증감이다.

#### 랭크 변화 행

- 카드 모델이 수단을 적용한 랭크를 세트의 `boosts`에 넣어 코어에 넘긴다. 랭크가 실능치·스피드에 미치는 계산(천진 등)은 엔진과 앱 스피드가 한다.
- **수단 목록:** 카드 모델의 데이터 상수다. 수단마다 종류(특성/기술), id, 효과 대상(사용자 자신 / 상대), 능력치별 랭크 변화를 둔다. 초기 목록은 다음과 같다.
  - 상대 하락
    - 위협(특성, A−1)
    - 막말내뱉기(A−1·C−1)
    - 애교부리기·깃털댄스(A−2)
    - 덤벼들기(A−1)
    - 바크아웃·매지컬플레임·소울크래시·벌레의저항(C−1)
    - 싫은소리(B−2)
    - 거짓울음·금속음(D−2)
    - 얼어붙은바람·일렉트릭네트·암석봉인·땅고르기·달려들기(S−1)
    - 겁나는얼굴(S−2)
  - 자기 상승
    - 칼춤(A+2), 나쁜음모(C+2), 철벽(B+2), 망각술(D+2), 고속이동(S+2)
    - 용의춤(A+1·S+1), 명상(C+1·D+1), 벌크업·똬리틀기(A+1·B+1), 나비춤(C+1·D+1·S+1)
    - 껍질깨기(A·C·S +2, B·D −1), 소울비트(A·B·C·D·S +1)
    - 저주(고스트 타입이 아닌 사용자만, A+1·B+1·S−1)
    - 정리정돈(A+1·S+1), 성장(A+1·C+1, 날씨 없음 기준)
    - 멀리짖기(A+1), 플레어송(C+1)
    - 니트로차지·개척하기·아쿠아스텝(S+1)
    - 가속(특성, S+1)
- **제외**
  - 확률 부가효과(문포스 30% 등)
  - 엔진이 스스로 적용하는 것(메테오빔·일렉트로빔의 특공 +1)
  - 조건부 도구
  - 같은 수단의 반복 사용과 수단 조합(행 하나 = 수단 하나 1회)
  - 순풍(별도 토글)
- **점유율:** 상대는 메타 항목 분포(특성·기술·도구)에서 그 id의 점유율이 랭크 기준 이상일 때 행을 낸다. 메가 항목의 특성 분포는 메가 폼 기준이다(선행 계약). 내 세트는 기술 목록·계산 특성(메가면 메가 폼 특성)에 있으면 "내 세트"로 표시하고 점유율은 없다.
- **적용 탭 규칙(표 대신 규칙):** 반응까지 적용한 뒤 랭크가 바뀐 능력치가 그 카드 판정의 참조 능력치에 하나라도 들면, 그 카드의 기본 행마다 랭크 행을 하나 더한다.
  - 참조 능력치: 공격 탭은 내 공격·상대 방어 능력치, 방어 탭은 상대 공격·내 방어 능력치, 스피드 탭은 양쪽 S다.
  - 예: 상대 위협 → 공격 탭 물리. 상대 칼춤 → 방어 탭 물리. 상대 명상 → 방어 탭 특수와 공격 탭 특수(상대 D). 상대 용의춤 → 방어 탭 물리와 스피드 탭. 내 칼춤 → 공격 탭 물리 전 카드. 내 얼어붙은바람 → 스피드 탭 전 카드(상대 S−1).
- **반응(받는 쪽의 계산 특성, 메가면 메가 폼 특성):** 다음 순서로 적용한다.
  1. 차단
     - 모든 하락 차단: 클리어바디·하얀연기·미러아머(반사는 다루지 않고 차단만)
     - 괴력집게: A 하락 차단, 부풀린가슴: B 하락 차단
     - 위협만 차단: 정신력·마이페이스·둔감·배짱
     - 파수견: 위협을 받으면 A+1로 바뀐다.
  2. 변환: 심술꾸러기는 부호를 뒤집는다.
  3. 반응
     - 상대가 낮춘 하락이 실제로 적용되면 오기는 A+2, 승기는 C+2다. 수단 하나당 한 번이다.
     - 위협을 받으면 주눅은 S+1이다.
     - 하양허브는 하락분을 한 번 되돌린다(자기 기술의 하락 포함).
  4. 기존 랭크에 더해 −6~+6으로 자른다.
  - 자기 기술의 자기 하락(껍질깨기 B·D)은 오기·승기를 부르지 않는다.
  - 목록에 없는 특성은 반응이 없다. 단순·메탈프로텍트·클리어참·비상한구슬은 현재 스냅샷 게임 데이터에 없어 넣지 않는다. 생기면 목록에 더한다.
  - 수단·반응별 단위 테스트를 둔다. 기준은 Showdown 동작이다.

#### 스카프 행과 목록 밖 프리셋

- **스카프 행:** 스피드 탭에서 상대 도구 분포의 구애스카프 점유율이 스카프 기준 이상이면, 그 종의 점유율 최대 S 묶음 카드에 "구애스카프" 행을 더한다. 대표 도구가 구애스카프면 "스카프 아닌 최다 도구"("도구 없음" 포함) 행을 더한다. 메가 항목은 대상이 아니다(메가스톤 고정, 강제로 스카프를 씌우면 코어가 거부).
- **목록 밖 프리셋:** (로스터 id, 탭, 분류, 프리셋 번호, 사용자 편집값) → 커스텀 출처 가정(근거 "출처 그대로")을 만든다. 메타 계약의 가정 해석 경로를 그대로 지난다.
  - 특성: 원종 첫 슬롯
  - 도구: 없음. 메가 폼이 타겟이면 원종 + 메가스톤 + 메가 지정이다.
  - 프리셋이 정하지 않은 SP: 0
  - 보정 없는 성격: 노력. 상승 성격은 고집(A+)·조심(C+)·장난꾸러기(B+)·신중(D+)·명랑(S+)이다.
  - 방어 탭은 사용자가 상대 기술을 고르기 전에는 행 작업 없이 "기술을 선택하세요" 상태다.
  - 메타 목록 안의 종은 목록 밖 타겟으로 받지 않는다.

#### 코어 계약 확장

- **예산 무시 평가 옵션:** 세트 검증·단건 대미지·스피드 비교에 선택 인자를 더한다. 켜면 SP 합계 상한 검사만 건너뛴다. 능력치별 0~32와 종·특성·도구·기술 합법성 검사는 그대로다. 기본은 꺼짐이라 기존 호출·테스트·확인 페이지 동작이 바뀌지 않는다.
- **스윕 예산 밖 칸 판정 옵션:** 켜면 예산 밖 칸도 판정한다. 그 칸은 판정 칸에 "예산 밖" 표시를 달고, 경계는 예산 밖 칸까지 포함해 계산한다. 끄면(기본) 지금처럼 판정하지 않는 칸이다.
- **대미지 스윕 허용 능력치:** 기술 참조 조회로 정한다. 공격측은 그 기술이 참조하는 자기 공격 능력치(자기 참조일 때), 방어측은 H·참조 방어 능력치이고, 대상 참조 공격 기술이면 A도 허용한다. 일반 기술에서는 지금의 고정 목록과 같은 결과다. 판정 범주는 지금처럼 측(공격측 → 공격 관점, 방어측 → 방어 관점)으로 정한다.
- **선행 계약과의 정합**
  - 코어 ADR 결정 2의 "SP 범위와 합계 검증"은 기본 동작으로 남는다. 확장은 명시적으로 켜는 가상 평가다. `minSpToOutspeed`가 이미 예산 초과 SP를 판정하는 선례다.
  - "엔진에는 스냅샷 수치만 주입" 불변식은 위력·타입·분류·타수·대상 수치에 관한 것이다. 참조 재정의는 선행 ADR이 엔진 데이터 의존으로 남긴 기술 고유 효과 범주라 이 불변식을 어기지 않는다.
  - 앱 스피드 공식, 1타 확률 자체 분포 합성 경로는 바뀌지 않는다.
  - 목록 밖 종은 커스텀 출처 가정만 받는다(메타 불변식).
  - 이 확장은 선행 ADR 본문을 고치지 않고 이 ADR에 후속 결정으로 남긴다.

### 결정 3. 계산 전략과 반응성: 메인 스레드 시간 분할 실행기 + 점진 표시 + 정규화 키 메모 캐시, Web Worker는 보류

- **실측 근거(notes "ADR 근거 실측")**
  - 브라우저 33칸 스윕 중앙값은 1.30ms, Node는 0.77ms다(비 약 1.7).
  - Bo1 상위 30 기준 Node 시뮬레이션에서 방어 탭은 극단 필터가 기술×묶음의 84~95%를 빼 스윕 42~132회(52~121ms)다. 공격 탭(4기술)은 스윕 298회(223ms), 스피드 탭은 11ms다.
  - 브라우저로 환산하면 최악인 공격 탭이 약 0.38s, 내 랭크 수단 행이 붙으면 약 0.76s다. 탭 하나를 한 번에 동기 계산하면 100ms 막힘 기준을 넘는다.
- **실행기(앱 계층 `src/app/`)**
  - 카드 모델의 행 작업을 카드 순서대로 돈다. 한 조각에서 약 12ms 일한 뒤 브라우저에 양보한다. 양보는 `scheduler.yield`가 있으면 그것을, 없으면 MessageChannel을 쓴다.
  - 작업 단위가 스윕 1회(최대 약 2ms)라 조각이 길어지지 않는다.
- **우선순위:** 현재 탭을 사용률 순으로 먼저 계산한다. 끝나면 나머지 두 탭을 같은 실행기로 이어 계산해, 탭을 바꾸면 바로 보이게 한다.
- **점진 표시:** 조각이 끝날 때마다 조립 결과를 외부 저장소에 넣는다. 화면은 끝난 앞쪽 카드부터 확정 표시하고 진행(끝난 수/전체)을 보인다.
- **취소:** 입력(내 세트·메타 선택·조건·표시 기준·필터·목록 밖 타겟)이 바뀌면 세대 번호를 올린다. 진행 중이던 조각은 결과를 버리고 새 계획으로 다시 시작한다. 캐시는 유지한다.
- **메모 캐시**
  - **키:** 정규화한 코어 호출 입력이다. 레귤레이션, 호출 종류, 측·능력치, 공격·방어 세트, 기술, 조건, 구간 임계값을 넣는다. 스윕하는 능력치의 SP는 키에서 뺀다. 스윕 결과(예산 밖 표시 포함)가 그 값과 무관하고 다른 능력치 SP로만 정해지기 때문이다.
  - **효과:** 가장 흔한 조작(공격 탭에서 내 A만 바꾸기)이 A 스윕 전부 캐시 적중이 된다.
  - **값:** 행 모델용 축약 칸(범주·1타 확률·% 범위·스피드·예산 밖)만 둔다. 난수 배열은 버려 메모리를 줄인다.
  - **상한:** 항목 수 상한(초기 5,000)을 넘으면 오래 쓰지 않은 것부터 버린다. 레귤레이션이 바뀌면 비운다.
  - 캐시 없이 일괄 계산한 결과와 캐시를 거친 결과가 같아야 한다(재현성 테스트).
- **사전 가지치기**
  - PRD 규칙인 방어 극단 필터가 가장 큰 절감이다.
  - 양 끝 칸만 비교해 변화 없음을 미리 판단하는 단축은 채택하지 않는다. 단조성 실측(904개 위반 0)이 있지만, 이미 실측 비용으로 기준을 만족하고 "전 칸이 같음" 정의를 그대로 계산하는 편이 재현성 검증이 단순하다. 기준을 못 맞추게 되면 단조성 속성 테스트와 함께 도입하는 예비 수단으로 남긴다.
- **렌더 비용 제한:** 카드는 접힌 상태가 기본이고, 0~32 칸 띠는 펼칠 때만 그린다.
- **달성 근거**
  - 첫 카드: 스냅샷·메타 로드(메타 파싱~대표 가정 0.7ms 실측) 뒤 첫 카드의 행 작업은 수 ms다. 500ms에 큰 여유가 있다.
  - 전체: 최악 약 0.76s에 상대 랭크·스카프 행을 더해도 3초의 3배 이상 여유다.
  - 막힘: 조각 약 12ms + 스윕 1회 + 조각당 렌더로 100ms 미만이다.

### 결정 4. 앱 진입 구조와 상태 모델: 단일 HTML + 해시 경로 `#/dev`, 제품 상태는 `useReducer` 하나, 계산 결과는 `useSyncExternalStore`, 라이브러리 추가 없음

- **진입:** `index.html` 하나에 해시 경로를 둔다. 해시가 `#/dev`로 시작하면 개발 확인 페이지, 그 밖은 제품 화면이다.
  - 개발 페이지는 동적 import로 지연 로드해 제품 첫 번들에서 뺀다. `hashchange`를 구독하고 경로 라이브러리는 쓰지 않는다.
  - 문서 제목은 제품 이름으로 바꾼다.
- **e2e·성능 훅**
  - 기존 dev 스펙의 진입 helper를 `/#/dev`로 바꾼다.
  - 오프라인 스펙은 제품 화면과 dev 페이지 모두 외부 요청 0건을 확인한다.
  - `window.__perf` 훅은 진입과 무관하게 지금처럼 설치하고, 제품 반응성 측정 함수를 더한다(결정 3 검증).
- **제품 상태 소유:** 제품 루트 컴포넌트의 `useReducer` 하나가 소유한다. 상태 타입·초기 상태(예시 포켓몬)·리듀서·입력 변환은 React 없는 순수 모듈(`src/app/state.ts`)로 두어 단위 테스트한다.
  - 상태 항목: 레귤레이션, 메타 선택(매치 방식·월), 내 세트 초안(입력 문자열), 조건(내·상대 순풍), 활성 탭, 표시 기준 4개, 필터(상위 N·선택 종), 목록 밖 타겟(종, 탭·분류·프리셋별 편집값, 방어 탭 선택 기술).
  - 카드 펼침 같은 표시 국소 상태는 카드 컴포넌트 자신의 상태로 둔다.
- **파생과 구독**
  - 상태 → 카드 모델 입력은 순수 함수다.
  - 계산 결과(진행·탭 뷰)는 실행기가 소유하는 외부 저장소에 있고, 화면은 React 내장 `useSyncExternalStore`로 구독한다.
  - 스냅샷·메타는 기존 데이터 접근층의 지연 로드 캐시를 그대로 쓴다.
  - 저장·URL 공유는 비목표라 상태를 URL·브라우저 저장소에 쓰지 않는다.
- **라이브러리:** 추가하지 않는다(react·react-dom만).
- **층 경계와 공용 모듈**
  - 의존 방향: core ← meta ← cards(순수) ← app(상태·실행기·화면). dev 확인 페이지는 core·meta·data만 쓴다.
  - 제품이 쓸 한국어 라벨·이름 색인·세트 초안 변환(`src/dev/labels.ts`·`names.ts`·`draft.ts`의 해당 부분)은 공용 위치(`src/ui/`)로 옮기고 dev도 그것을 import한다. 제품 코드는 `src/dev`를 import하지 않는다.

## 선택지

### 결정 2 (카드 모델 계층)

#### 선택지 2-A: `src/cards/` 순수 도메인 모듈 + 계획/행 작업/조립 계약 (채택)

- 장점: PRD 재현성 요구(화면 없이 같은 카드 목록)를 일괄 함수로 바로 테스트한다. 행 작업 단위라 결정 3의 시간 분할·캐시가 계약 위에서 자연스럽다. 화면이 판정을 계산하지 않는다는 경계가 import 방향으로 강제된다.
- 단점: 계획·작업·조립 세 단계라 단일 함수보다 계약이 넓다.

#### 선택지 2-B: React 컴포넌트·훅 안에서 코어를 직접 호출

- 장점: 파일이 적고 처음 구현이 빠르다.
- 단점: 묶음·필터·랭크 규칙이 화면 코드에 흩어져 화면 없는 재현성 테스트가 불가능하다. 점진 계산·캐시를 렌더 주기와 섞게 된다.

#### 선택지 2-C: 카드 모델을 단일 동기 함수(입력 → 탭 뷰) 하나로만 노출

- 장점: 계약이 가장 작다.
- 단점: 실측상 탭 하나가 브라우저 약 0.4~0.8s라 한 번에 부르면 막힘 기준을 넘는다. 점진 표시를 하려면 결국 내부를 쪼개야 한다.

#### 코어 계약 확장의 대안 (예산 밖 칸·극단 필터)

- **코어에 예산 무시 평가 옵션 + 스윕 예산 밖 판정 옵션 추가 (채택):** 판정 원천이 코어 하나로 남는다. 기본값이 꺼짐이라 기존 계약·테스트가 그대로다. 단점은 코어 공개 인자가 늘고, 옵션 조합 테스트가 필요하다는 것이다.
- **카드 모델이 다른 능력치를 임시로 줄인 가상 세트로 계산:** 코어를 안 바꾼다. 그러나 "무관해 보이는" 능력치가 실제로 판정에 들어가는 경우가 실측·코드로 확인된다(속임수의 대상 A, 자이로볼·일렉트릭볼의 S, 셸암즈의 B/D). 줄일 능력치 선택도 임의라 결과가 조용히 틀릴 수 있다. H32·B32 극단 판정은 다른 능력치를 합 2 이하로 강제로 바꿔야 해 PRD의 "다른 능력치는 현재 값"을 지키지 못한다.
- **스윕만 예산 무시로 확장:** 칸 판정은 풀리지만 극단 필터는 두 능력치를 함께 바꾸는 단건 판정이라 여전히 거부된다. 스윕으로 우회하면 필터 비용이 16배가 된다(실측 단건 0.02ms 대 스윕 0.77ms).

#### 참조 능력치 판별의 대안

- **코어가 엔진 기술 데이터의 참조 재정의 필드를 읽음 (채택):** 엔진이 계산에 쓰는 값과 같은 원천이다. 스냅샷·메타를 다시 만들 필요가 없다. 원천 모드(@pkmn/dex)의 같은 필드와 스냅샷 전 공격기를 대조하는 테스트로 차이를 잡는다.
- **스냅샷 기술 항목에 참조 필드를 추가해 생성:** 데이터 계약으로는 깔끔하다. 그러나 `data.json` 해시가 바뀌어 최신 월 메타를 강제로 다시 만들어야 하고(메타 불변식), 엔진이 실제로 쓰는 값과 별개 원천이 생긴다.
- **카드 모델에 기술 id 목록 하드코딩:** 가장 빠르다. 그러나 레귤레이션에 기술이 추가되면 조용히 빠진다.
- **능력치를 흔들어 보는 런타임 판별:** 원천이 필요 없지만 기술마다 판정을 여러 번 더 돌린다. 면역·고정 대미지에서 판별이 흐려진다.

#### 랭크 변화 적용의 대안

- **카드 모델이 수단·반응을 계산해 `boosts`로 넘김 (채택):** 엔진이 위협·반응을 적용하지 않는다는 실측과 맞는다. 규칙이 한 모듈의 데이터 상수와 테스트에 모인다.
- **엔진의 위협 처리(`abilityOn`)를 켬:** 위협과 그 반응만 다루고 기술 수단은 못 다룬다. 엔진 내부 동작에 기대게 된다(선행 ADR의 얇은 래퍼 원칙과 어긋남).

### 결정 3 (계산 전략)

#### 선택지 3-A: 메인 스레드 시간 분할 + 점진 표시 + 메모 캐시 (채택)

- 장점: 실측상 최악 탭도 1초 안팎이라 분할만으로 세 기준을 모두 만족한다. 스냅샷을 한 번만 로드한다. 오류 객체를 그대로 다루고, 기존 동기 코어 계약을 그대로 쓴다. 테스트·디버깅이 쉽다.
- 단점: 메인 스레드 총 작업량은 줄지 않는다(분할만). 다음 단위(파티 6마리)처럼 작업량이 몇 배가 되면 다시 검토해야 한다.

#### 선택지 3-B: Web Worker 백그라운드 계산

- 장점: 메인 스레드 막힘이 원천적으로 없다.
- 단점
  - 워커가 게임 데이터(903KiB)와 메타(622KiB)를 따로 로드·파싱해야 한다.
  - 메시지 프로토콜·취소·오류 직렬화(코어 오류 클래스가 경계를 넘으면 프로토타입을 잃는다)가 필요하다.
  - e2e·성능 측정이 복잡해진다.
  - 이 단위의 실측 작업량에는 과하다. 파티 분석 단위의 예비안으로 남긴다.

#### 선택지 3-C: 동기 일괄 계산(분할 없음) + 캐시만

- 장점: 가장 단순하다.
- 단점: 최악 탭 약 0.4~0.8s 동안 입력이 멈춰 100ms 막힘 기준을 어긴다.

#### 선택지 3-D: 양 끝 칸 비교로 변화 없음 행을 미리 건너뜀

- 장점: 실측상 공격 탭 행의 96%가 변화 없음이라 스윕을 크게 줄인다.
- 단점: 단조성 가정에 기대는 단축이다(실측 위반 0이지만 증명은 아님). 현재 비용으로 기준을 이미 만족하므로 보류하고, 예비 수단으로 둔다.

#### 캐시 키 설계의 대안

- **정규화 입력 키, 스윕 능력치 SP 제외 (채택):** 가장 흔한 SP 조작에서 적중한다.
- **세트 전체를 키로:** 단순하지만 SP 하나만 바꿔도 그 탭이 전부 다시 계산된다.
- **캐시 없음:** 매 변경마다 0.4~0.8s 재계산이 되어, 입력 중 화면이 계속 깜빡이며 다시 채워진다.

### 결정 4 (앱 진입과 상태)

#### 진입 선택지

- **해시 경로 `#/dev` + 지연 로드 (채택):** 정적 호스팅에서 서버 설정 없이 동작한다. 빌드 설정을 바꾸지 않고, 하위 경로 배포에서도 깨지지 않는다. 다음 단위 화면도 같은 방식으로 늘릴 수 있다.
- **쿼리 `?dev`:** 해시와 거의 같다. 다만 이후 화면 상태를 쿼리로 공유하게 되면 충돌하고, 서버 요청에 실린다.
- **별도 엔트리 HTML(`dev.html`, Vite 다중 페이지):** 번들이 완전히 분리된다. 그러나 빌드 입력 설정이 늘고, 성능 훅·공용 CSS 진입을 두 곳에서 관리해야 한다. 지연 로드로도 제품 번들 분리는 얻는다.
- **경로 라우팅(`/dev`):** 정적 호스팅에서 새로고침 시 404를 막으려면 서버 재작성 규칙이 필요해 기각한다.

#### 상태 선택지

- **루트 `useReducer` + 순수 리듀서 모듈 + 실행기 외부 저장소를 `useSyncExternalStore`로 구독 (채택):** 라이브러리 없이 상태 전이를 단위 테스트한다. 계산 진행은 렌더 주기와 분리된다.
- **여러 `useState`(현재 dev 페이지 방식):** 상태가 열 가지가 넘고 서로 묶여 바뀐다(메타 선택 → 필터 초기화 등). 전이 규칙이 컴포넌트에 흩어진다.
- **외부 스토어 라이브러리(zustand·redux 등):** 구독 최적화가 편하지만 의존성 추가 금지 기본값에 어긋나고, 이 규모에는 React 내장으로 충분하다.
- **Context만으로 전역 상태:** 값이 바뀔 때 하위 전체가 다시 렌더된다. 계산 결과처럼 자주 바뀌는 값에는 맞지 않는다.

## 선택 근거

왜 이 선택지를 채택했는가?

- 카드 모델을 순수 모듈로 두면 PRD의 재현성·"화면은 표시만" 요구가 구조로 강제된다. 계획/행 작업/조립 계약은 실측된 계산량(브라우저 최악 약 0.4~0.8s)을 막힘 없이 나누는 데 필요한 최소 분해다.
- 예산 밖·극단 판정은 판정 원천을 코어 하나로 유지하는 확장이 가장 안전하다. 가상 세트 방식은 실측으로 확인된 숨은 능력치 의존(속임수·자이로볼·셸암즈) 때문에 조용히 틀릴 수 있다. 확장은 기본값이 꺼짐이라 선행 계약을 깨지 않는다.
- 참조 능력치는 엔진이 실제 계산에 쓰는 같은 필드를 읽어야 판별과 계산이 어긋나지 않는다. 데이터 재생성 연쇄(게임 데이터 해시 → 최신 월 메타 재생성)도 피한다.
- 계산량이 1초 안팎이라 Web Worker의 비용(데이터 이중 로드·직렬화·측정 복잡도)을 정당화하지 못한다. 시간 분할과 SP 제외 캐시 키로 기준과 조작감을 함께 얻는다.
- 해시 경로와 React 내장 상태 도구로, 정적·오프라인 배포와 라이브러리 무추가를 유지하면서 제품·dev 화면을 공존시킨다.

## 결과

이 결정으로 인해 예상되는 영향은 무엇인가?

### 긍정적 영향

- 카드·행·판정·경계·변화 없음 요약을 Vitest만으로 검증할 수 있다(화면 없음).
- 코어의 판정 원천이 하나로 유지되고, 예산 밖·극단 판정과 바디프레스 스윕이 같은 경로로 계산된다.
- SP 하나를 바꾸는 흔한 조작이 캐시 적중으로 즉시 반영된다. 탭 전환은 백그라운드 선계산으로 바로 보인다.
- 다음 단위(파티 분석)가 같은 카드 모델·실행기·해시 경로 위에 얹힌다.

### 부정적 영향 / 트레이드오프

- 코어 공개 계약이 넓어진다(평가 옵션 2개, 참조 조회 1개, 스윕 허용 능력치 규칙). 옵션 조합 테스트가 늘어난다.
- 참조 판별이 엔진 데이터에 의존한다. 엔진 버전을 올릴 때 원천 대조 테스트가 깨지면 확인해야 한다.
- 랭크 수단·반응표는 앱이 직접 유지한다. 목록에 없는 수단은 행이 생기지 않는다(점유율이 높아도). 새 레귤레이션마다 notes 방식의 실태 점검이 필요하다.
- 메인 스레드 총 작업량은 그대로다. 작업량이 몇 배가 되는 단위에서는 Web Worker를 다시 검토해야 한다.
- 알려진 단순화: 상대 속임수의 내 A는 현재 값 고정, 스피드 의존 기술은 묶음 대표의 S, 셸암즈는 계산 불가, 미러아머는 반사 없이 차단만.
- dev 공용 모듈 이동으로 dev 페이지 import 경로가 바뀐다(동작 변화 없음).

## 검증

- [ ] 코어: 기존 테스트 전부 통과(기본값 무변경). 예산 무시 옵션을 켜면 합계 초과 세트는 판정되고 능력치별 범위·합법성 위반은 여전히 거부된다. 스윕 예산 밖 판정 칸의 범주가 같은 SP를 예산 안에서 단건 판정한 결과와 같다.
- [ ] 참조 조회: 스냅샷 전 공격기에서 엔진 참조 필드와 @pkmn/dex 원천 필드가 일치한다. 사이코쇼크·바디프레스·속임수 섭동 테스트(참조 능력치만 대미지를 바꾼다)를 통과한다.
- [ ] 카드 모델(합성 메타 + 실제 스냅샷 예시): 묶음 합산·기준·상한·소수 배분, 참조 기준 분류(사이코쇼크 물리 카드), 극단 필터 세 경우, 변화 없음 집계, n 정의식(잔여 0 / 0 초과), 스카프 행 유무, 위협·오기 반응 차이, 내 칼춤 행 유무, 목록 밖 프리셋 3장이 PRD 수용 기준과 맞는다.
- [ ] 재현성: 같은 입력으로 일괄을 두 번 부른 결과가 같다. 캐시를 거친 점진 계산의 최종 탭 뷰가 캐시 없는 일괄 결과와 같다. 입력 변경 후 취소된 세대의 결과가 섞이지 않는다.
- [ ] 반응성(Playwright Chromium, 프로덕션 빌드, 기본 설정 상위 30, 10회 중앙값): 첫 카드 ≤ 500ms, 탭 전체 ≤ 3초. Long Tasks API로 잰 계산 중 최대 태스크가 100ms 미만이다.
- [ ] 진입: `/`에서 제품 화면, `/#/dev`에서 기존 dev 스펙 전부 통과. 두 화면 모두 외부 요청 0건이다. 제품 첫 번들에 dev 페이지 모듈이 들어가지 않는다(빌드 산출물 확인).
- [ ] 상태: 리듀서 단위 테스트(메타 선택 변경·필터 비우기 → 상위 N 복귀·표시 기준 변경)를 통과한다. 새 런타임 의존성이 없다(`package.json` dependencies 무변경).
